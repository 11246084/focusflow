# 對話功能優化設計決策

這份文件記錄學生網頁版對話功能（看影片時向 AI 提問的那一欄）的優化討論：現況、和市面產品的差距、可參考的開源專案，以及要逐題定案的問題。它讓接手的人或 AI 不用重讀對話就能接續；目前第一輪題目還沒回答，請 Weihao 逐題回覆。功能是否完成只看[目前狀態](../../current-status.md)。

範圍只含網頁版的對話欄，不含 LINE 對話、檢索方法（見[多模態檢索](../Multimodal_Retrieval/decisions.md)）與播放器章節（見[學生端播放介面](../Student_Player_UX/decisions.md)）。

## 名詞

- **串流輸出**：回答邊產生邊顯示，不是等整段寫完才一次出現。
- **追問**：依賴前文才看得懂的問題，例如上一題問「什麼是監督式學習」，下一題問「那它的缺點呢」。
- **追問改寫**：檢索前先把追問補成完整的問題，例如把「那它的缺點呢」改成「監督式學習的缺點是什麼」。
- **FAQ 快取**：相似的問題已經答過時，直接回傳之前的回答，不再呼叫模型。

## 和市面產品的差距

比較對象是通用聊天產品（ChatGPT、Gemini、Claude）與資料或影片問答產品（NotebookLM、Perplexity、YouTube 影片問答、Coursera Coach）。這部分依 Claude 既有的了解整理，沒有逐一查證各產品的最新版本；要引用到報告或系統手冊前須先查證。

依對使用感受的影響排序：

1. 沒有串流輸出。
2. 追問改寫靠規則，沒涵蓋的說法（例如「再講詳細一點」「舉個例子」）會被當成獨立問題去檢索。
3. 系統不知道學生正在看哪支影片的哪一秒，答不出「剛剛這段在講什麼」。
4. 回答的操作少：不能複製、評分、對成功的回答重新產生、編輯問題或中止。
5. 沒有範例問題與建議追問。
6. 輸入框不能換行。
7. 對話不能改名、刪除、搜尋。
8. 回答不支援表格、程式碼區塊與公式。

「點來源直接跳到影片那一秒」是通用聊天產品沒有的，屬於本系統的特色，優化時保留。

Weihao 希望用**一天**把對話功能優化完，範圍除了上面列的差距，還要具備三類能力。下表把每一類換成這個系統裡具體可做的東西，並標出要不要改回答的提示詞（給模型的指示）或回傳格式。

| 能力 | 在本系統的具體做法 | 改提示詞或回傳格式 |

| 行內互動元件 | **小測驗卡**：學生要求出題時，回答變成可以作答的選擇題 | 是 |

| 多模態輸入 | **上傳圖片或截圖提問** | 是，而且要新增上傳與圖片理解的費用 |

| 猜你想問（回覆後） | 在同一次回答呼叫多回傳一個「建議追問」欄位，不多呼叫一次模型 | 是 |
| 問題模糊時先確認 | 在同一次回答呼叫讓模型可以改回傳「選擇題」，學生點選後再回答 | 是 |
| 進度提示 | 後端在每個實際步驟完成時通知前端：理解問題 → 搜尋課程片段 → 找到 N 個片段 → 撰寫回答 | 否，但要新增一條會持續傳送事件的 API |

### 兩個會影響排程的限制

1. **改提示詞或回傳格式的項目，需要 Gemini 可用才能驗證。** 這類變更可能讓原本答得好的題目變差，上線前要用[問答品質評測](../QA_Evaluation/README.md)的題庫重跑比較。目前 Gemini 專案達每月花費上限，無法執行。這類變更還要同步檢查 FAQ 快取命中路徑與 LINE（兩者共用同一套回答流程）。
2. **回答目前不能真的逐字串流。** 模型回傳的是一整包 JSON，要等整包回來才能解析出回答文字與引用。要逐字顯示就得改變回答的產生方式，屬於上面第 1 類。進度提示不受這個限制。

### Claude 的評估

全部項目無法在一天內做完並驗證。寫程式本身也許趕得完，但改提示詞的項目卡在 Gemini 無法驗證，硬上線有讓回答品質變差而沒人發現的風險。建議依「要不要改提示詞」切成兩批，見 Q1。

## 目前這一輪待答題目

2026-11-15 依 Weihao 的新目標重擬，取代同日稍早的第一輪題目（原 Q1～Q5 尚未回答，其中「重新產生是否扣額度」併入 Q1 的「之後」清單）。每題的編號對應上方表格的項目。

### Q1：一天的範圍怎麼切

**問題**：是否把工作切成兩批，第一批用一天完成，第二批等 Gemini 可用後另排一天？

**建議答案**：是。

- **第一批（一天，不改提示詞）**：複製回答、多行輸入、開場猜你想問、問目前這段、進度提示、語音輸入、朗讀回答、來源時間軸。
- **第二批（Gemini 可用後）**：回覆後的建議追問、問題模糊時先確認、小測驗卡。三項一起改提示詞與回傳格式，只跑一次評測。
- **之後再評估**：上傳圖片提問、逐字串流、用模型改寫追問、讚／倒讚、對話改名刪除、成功的回答重新產生（含是否扣額度）、編輯問題、表格與程式碼排版。

第一批若當天做不完，依上面列的順序做到哪算哪，排在後面的三項（語音輸入、朗讀、來源時間軸）順延。

**理由**：第一批的每一項都不會改變回答內容，用模擬資料與現有測試就能驗證，不必等 Gemini。第二批三項都要改同一段提示詞，合在一起做只需要評測一次。

### Q2：成功標準

**問題**：第一批的驗收是否訂為下面四條？

**建議答案**：是。①空白對話看得到至少 3 個可點的問題，點了直接送出；②送出後 1 秒內出現第一個進度提示，之後的提示對應後端實際完成的步驟；③播放到某一段時按「這段在講什麼」，回答的來源落在目前這支影片的附近時間；④既有的後端與前端測試全數通過，LINE 問答行為不變。

**理由**：四條都能在沒有 Gemini 的情況下用模擬回答檢查。第③條的「附近」範圍留到細部設計時定。

### Q3：進度提示的做法

**問題**：進度提示是否只顯示後端實際發生的步驟，不做固定秒數輪播的假進度？回答文字維持整段出現？

**建議答案**：是。新增一條用 SSE（伺服器持續推送事件的標準做法）的問答 API，原本的 API 保留給 LINE 與舊版前端。FAQ 快取命中時沒有檢索與撰寫步驟，直接顯示回答。逐字串流列入「之後」。

**理由**：假進度和實際狀況對不上時反而降低信任，例如顯示「撰寫回答中」但其實還卡在檢索。保留舊 API 可以讓新功能出問題時前端直接退回舊做法。這一題定案後，Claude 在凍結期間唯讀研究 LibreChat 的 SSE 連線、中止與錯誤處理寫法，作為實作參考。

### Q4：猜你想問（開場）的來源

**問題**：開場的建議問題是否用「這門課被問最多次的 3 題」，沒有資料時改用固定的通用題？

**建議答案**：是。通用題用「這支影片的重點是什麼？」「幫我整理這段的關鍵名詞」「這段和前面的內容有什麼關係？」這類搭配目前播放位置就能回答的題目。

**理由**：常見問題的資料與 API 已經有，不花模型費用；而且點了大多會命中 FAQ 快取，回答快、不耗 Gemini 用量。要確認的一點是，點選建議問題要不要扣每日提問額度；建議照一般提問處理，不另開例外。

### Q5：語音輸入與朗讀

**問題**：語音輸入與朗讀是否用瀏覽器內建功能，不經過後端、不使用付費的語音服務？

**建議答案**：是。瀏覽器不支援時不顯示按鈕。

**理由**：不增加費用，也不用新增後端。要先讓你知道的限制有兩個，都需要實作時實測確認：各瀏覽器的支援程度不同（Firefox 可能不支援語音輸入）；部分瀏覽器會把錄音送到瀏覽器廠商的伺服器做辨識，介面上要有一句說明。

### Q6：問題模糊時先確認（第二批）

**問題**：是否採「由模型在同一次回答呼叫判斷要不要先確認，最多確認一次，選項最多 4 個並附一個『都不是，我自己說明』」？

**建議答案**：是。確認的那一次不扣每日提問額度，學生選完後產生的回答才扣。確認的回覆不存進 FAQ 快取。LINE 維持現況、不出現選擇題。

**理由**：在同一次呼叫判斷不會多花一次模型費用。限制一次是避免學生被連續反問。確認本身沒有回答到問題，扣額度不合理；每日只有 5 次，被扣會讓學生不敢問。這題現在先定方向，細節等第二批開始前再確認。
