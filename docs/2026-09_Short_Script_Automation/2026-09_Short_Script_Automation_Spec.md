## 這份文件在講什麼（先讀這頁）

### 現在的做法

短影片腳本目前是純人工：組員手動查資料庫、挑逐字稿片段、寫成一份 13 節的腳本文件。已經產出兩份範例（大語言模型、OpenCV vs YOLO）與一份空白模板，放在 `docs/short-video-examples/teacher-avatar-track/`。

一份腳本大約要花掉：找題目、查片段、比對原文、設計敘事弧線、寫 8 拍口白、填模板固定章節。其中**只有中間三件事是因主題而異**，其餘都是重複勞動。

### 這一輪要做什麼

把「選題 → 找證據 → 生成腳本 → 老師審核 → 通過或退回重生」這條路自動化，但**產出的是結構化資料（JSON），不是完整的腳本 markdown**。

模板的固定章節（分身規格、配樂、字卡、ffmpeg、驗收清單）不由系統生成。系統只產出證據表、敘事設定、8 拍口白與 B-roll 隱喻建議。

### 為什麼不直接生成完整 markdown

三個理由：

1. 模板固定章節在既有兩份範例之間幾乎逐字相同，讓 LLM 每次重寫是浪費，也多開一個出錯面。
2. 腳本模板目前是舊版（見附錄 H.3），之後要修。輸出 JSON 可以讓自動化與模板版本解耦——模板改版時換 renderer 就好，不必回頭改 prompt。
3. 生成範圍越小，幻覺面越小。

### 這一輪不做什麼

不做影片產製（B-roll 生成、語音合成、ffmpeg 合成）、不做 YouTube 上架、不做前端頁面、不修改既有腳本範例與模板。

### 最重要的一條線

**腳本裡的每一句話都必須追得回課程逐字稿。** 這不是品質建議，是本功能能否成立的前提。教師的臉與聲音是複製的，如果講的內容還是編的，這個功能不能上線。實作方式見附錄 E。

## 1. 這一輪要證明什麼

要證明的是**一件事**：系統自動選出的題目與證據，跟人工判斷的品質是否可比。

不是要證明「系統能生成腳本」——LLM 當然能生出文字。要證明的是生出來的東西**追得回資料庫、而且老師願意用**。

因此驗收分兩階段，先驗證資料，再驗證生成。詳見第 7 章。

## 2. 教師從頭到尾會經過什麼

```text
① 教師開啟課程的「短影片腳本」頁
      ↓
② 系統顯示候選主題清單（依熱門提問聚合，同義題已合併）
      ↓
③ 教師勾選一個主題            ← 人工決定，系統不自動選
      ↓
④ 系統撈出證據片段並凍結快照，顯示 A~F 對照表（含 STT 原文）
      ↓
⑤ 教師確認證據正確            ← 人工關卡，這裡擋掉的成本遠低於生成後才發現
      ↓
⑥ 系統生成 8 拍口白 + 敘事設定 + 2~3 組 B-roll 隱喻建議
      ↓
⑦ 系統自動執行引用驗證：每一拍的依據必須在④的證據包內
      ↓
⑧ 教師審核
      ├─ 通過 → 狀態轉 approved，套用腳本模板產出可執行腳本（本輪人工套）
      └─ 退回 → 填回饋並標記類型
                  ├─ retrieval（講錯了／漏了）→ 回到 ④ 重撈證據
                  └─ narrative（開頭不吸引人／節奏）→ 回到 ⑥ 重生腳本
```

### 2.1 兩個人工關卡不可省略

**第 ③ 步（選題）**：目前資料量下最高熱度僅個位數（實測全庫最高的一題被問過 8 次），排名的統計意義薄弱。系統只提供候選，不自動決定。

**第 ⑤ 步（確認證據）**：STT 逐字稿錯字很重（實例：`雀的gp` 應為 ChatGPT、`OvenCV` 應為 OpenCV、`優龍` 應為 YOLO、`Opens TV` 應為 OpenCV）。人要看過才知道系統是不是撈到對的東西。等腳本生成完才發現引用錯，重生成成本高得多。

### 2.2 回饋為什麼要分流

若不分流、一律回到生成，遇到「講錯了」這類回饋時，模型會在**錯誤的證據**上反覆重寫，結果是越改越像編的。回饋類型由教師在退回時指定，不由系統猜。

## 4. 輸出契約

系統的產出是下列 JSON。這是本功能的核心需求定義。

```text
{
  scriptId, courseId, topic, status,

  evidence: [                       // 凍結快照，不可即時重查
    { code: 'A', chunkId, videoId, videoTitle, startSec, endSec, rawText }
  ],
  evidenceFrozenAt,

  globalSettings: {
    coreEvent,                      // 核心事件：觀眾原本的認知 vs 實際狀況
    coreView,                       // 核心觀點
    audienceAssumption,             // 觀眾原本可能以為
    audienceTakeaway,               // 觀眾看完後應該發現
    targetAudience
  },

  writingFourQuestions: [ ... ],    // 動筆前四題

  visualMetaphorOptions: [          // 2~3 組供教師挑選
    { label, s1, s2, s3 }
  ],

  shots: [                          // 8 拍
    {
      shotNo, arcRole, timeRange,
      narration, subtitle, editing, sfx,
      basedOn: ['chunk_0038'] | 'template'
    }
  ]
}
```

### 4.1 `basedOn` 的語意

| 值 | 意義 | 允許時機 |
|----|------|----------|
| chunkId 陣列 | 這句話改寫自這些片段 | 任何有內容的口白 |
| `'template'` | 不給答案的反問或懸念 | **僅限**結尾收尾拍 |

既有兩份範例的鏡 08 都是這個用法（「那你，說得出幾個大語言模型的名字嗎？」／「那你的任務，你會選哪一個？」），共同特徵是**不提供資料庫沒確認過的答案**。

### 4.2 `evidence[].rawText` 必須是未修飾原文

不得在此階段自動糾錯後覆蓋。理由有二：

1. 糾錯本身會引入幻覺（模型可能把 `優龍` 改成錯的東西）。
2. 糾錯後的文字無法比對回 `video_segments_text` 的原始片段，可追溯性斷掉。

糾錯屬於教師套用腳本時的人工步驟，不屬於系統職責。

## 5. 安全紅線

以下每一條，違反即視為本功能不可上線，不接受「先做出來再說」。

### R-01 不得產出追不回資料庫的內容

每一拍必須帶 `basedOn`，且所引 chunkId 必須存在於本次證據包。任一項對不上，**整份退回重生**，不接受部分採用。詳見附錄 E。

### R-02 不得放寬跨課程隔離

範圍建構一律沿用 `bridgeScope.service.js`。跨課程 allowlist 的 fail-closed 語意是學生試用版 Phase 1 已收斂的安全邊界，不得為了讓腳本「有更多素材可用」而放寬。

### R-03 不得寫入唯讀 collection

| Collection | 權限 |
|------------|------|
| `shortscripts` | 讀寫（本輪新增） |
| `faqs`、`questions`、`video_segments_text`、`videos`、`courses` | **唯讀** |
| `usagelogs` | 只寫新增的 event 型別，且不得計入既有統計（見附錄 G.2） |
| `shortassets` | 本輪不碰 |

任何工作項若發現需要寫入唯讀 collection，停止該項並回報，不得自行放寬。

### R-04 不得把「最常問」直接當成「已選定主題」

必須經教師確認。系統輸出的是候選清單。

### R-05 不得對 STT 原文做自動糾錯後覆蓋

見 4.2。

### R-06 弧線不適用時不得硬生成

8 拍標準弧線的核心是「反轉」。既有兩份範例的反轉都是**逐字稿原句就有的**（V4 的「不是只有 ChatGPT」出自 chunk_0106；V5 的「CPU 版效果非常差、速度很慢」出自 chunk_0003+0004）。證據包內找不到轉折句時，硬套只會逼出兩種結果：編一個假反轉（就是幻覺），或鉤子空轉。此時必須回報不適用，交由教師改用其他手法。判定方式見附錄 D。

### R-07 產製與發布的前置門檻不由系統代勞

教師數位分身需要**書面同意**（載明用途、範圍、期限、可撤回），成品需要**全片常駐的 AI 揭露標示**。這兩項是流程門檻，系統不檢查也不代為取得，但腳本輸出時須在模板套用階段提醒。本輪不做上架，因此不涉及，但規格記錄此邊界以免日後遺漏。

## 6. 錯誤碼

依 `.claude/rules/api-design.md`，使用 SCREAMING_SNAKE_CASE，並須於實作時補進該規則檔的表格。

| 錯誤碼 | HTTP | 情境 |
|--------|------|------|
| `SHORT_SCRIPT_NOT_FOUND` | 404 | 腳本不存在 |
| `SHORT_SCRIPT_EVIDENCE_EMPTY` | 422 | 檢索不到可用片段，無法凍結證據 |
| `SHORT_SCRIPT_CITATION_INVALID` | 502 | 生成結果引用了證據包外的 chunkId，重試上限內未通過 |
| `SHORT_SCRIPT_ARC_NOT_APPLICABLE` | 422 | 證據包無轉折句，不適用 8 拍弧線 |
| `SHORT_SCRIPT_STATE_INVALID` | 409 | 狀態轉換不合法 |

沿用既有錯誤碼：`VALIDATION_ERROR`、`INVALID_ID`、`COURSE_NOT_FOUND`、`COURSE_MANAGE_DENIED`、`UNAUTHORIZED`、`FORBIDDEN`。

## 7. 驗收條件

### 7.1 階段 A：資料階段（對應施工單停止點 SP-1）

**目的**：驗證「系統選的題目與證據，跟人工判斷可比」。這是整條路最便宜的可行性驗證。

**執行方式**：對至少 2 門課各跑一次候選聚合與證據凍結，與人工撰寫 V4／V5 時實際採用的題目與片段做人工比對。

**必須通過**：

- [ ] 同義題確實合併（以 V5 的實例驗證：「open cv 跟 yolo 的關係是甚麼?」「YOLO跟opencv的具體差異是什麼？」「opencv跟yolo有什麼差異?」三者須併為一個候選）
- [ ] 候選清單不含拒答題
- [ ] 跨課程負向測試：其他課程的片段一筆都不得出現在證據包
- [ ] 證據包在來源影片刪除後仍完整可讀
- [ ] 全程未寫入任何唯讀 collection（以查詢前後筆數比對證明）
- [ ] backend 全套測試通過，測試總數不減少

**明確失敗條件**（出現任一項即階段 A 未通過，須回頭調整參數，不得往下做）：

- 系統撈出的證據包，**完全不包含**人工版本採用的核心片段
- 同義題分群把明顯不同主題的問題併在一起

**比對結果須存入** `evidence/`，並記錄使用的分群門檻值。

### 7.2 階段 B：生成階段（對應施工單停止點 SP-2）

**必須通過**：

- [ ] 注入含捏造 chunkId 的假生成結果，驗證器必須攔下並整份退回（不得部分採用）
- [ ] 證據包無轉折句時，回報 `SHORT_SCRIPT_ARC_NOT_APPLICABLE`，而非硬生成
- [ ] `'template'` 只出現在結尾收尾拍
- [ ] provider 未設定時 fail-fast，不得靜默 fallback
- [ ] 版本可逐版取出並比對差異
- [ ] `retrieval` 類回饋確實重新凍結證據，並在新版本標記證據已更換
- [ ] 每條路由涵蓋成功、未授權、無權限、資源不存在
- [ ] backend 全套測試通過，測試總數不減少

### 7.3 不列入驗收的事

「腳本好不好看」「敘事夠不夠吸引人」不列入本規格的驗收條件——沒有客觀判準，且屬於教師的專業判斷。系統的責任止於**追得回資料庫**與**流程走得完**。品質標準若要納入，須由指導教授另行定義（見 8.2）。

## 8. 已定案與待決

### 8.1 本規格定案項目

| 編號 | 議題 | 決議 | 理由 |
|------|------|------|------|
| DR-01 | 輸出格式 | JSON 結構化資料，不產出 markdown | 與模板版本解耦；縮小生成面 |
| DR-02 | 選題自動化程度 | 只出候選清單，教師勾選 | 資料量下排名統計意義薄弱 |
| DR-03 | 熱度最低門檻 | `hitCount >= 2`，低於門檻不列入候選；候選為空時回傳明確 zero-state | 問過一次不構成「常問」 |
| DR-04 | Parent 多層級檢索 | 本輪不納入，沿用 leaf 檢索 | 相關 flag 目前關閉；不在本輪引入未驗收的檢索路徑 |
| DR-05 | B-roll 隱喻 | 產出 2–3 組選項供教師挑，且須避開該課程既有腳本用過的隱喻 | 模板明訂「新主題要換新隱喻，不要重複用過的」，避免不同影片看起來像換皮 |
| DR-06 | 生成成本記錄 | 寫入 `usagelogs`，但使用新的 event 型別，**不得**計入 `teacherStats` 的 `queriesCount` | 要能追成本，但不能污染既有問答統計 |
| DR-07 | 引用驗證重試上限 | 重試 2 次（共 3 次生成），仍失敗回 `SHORT_SCRIPT_CITATION_INVALID`，並保留最後一次原始輸出供人工檢視 | 保留輸出才能診斷是 prompt 問題還是證據問題 |
| DR-08 | 證據凍結時機 | 教師選定主題當下凍結，之後不再即時重查 | 影片可能被刪除或重跑，可追溯性必須綁在當下的快照 |
| DR-09 | 回饋分流 | 由教師在退回時指定 `retrieval` / `narrative`，系統不猜 | 猜錯會讓模型在錯證據上反覆重寫 |

### 8.2 仍待決事項

**四項皆不擋 v1.0 Frozen**，但各自擋不同的下游關卡：

| 編號 | 議題 | 需要誰決定 | 擋什麼 |
|------|------|------------|--------|
| P-01 | 同義題分群門檻定版值 | 由階段 A 證據決定，非人工判斷 | 擋**正式產出**，不擋實作與驗收 |
| P-02 | 腳本品質標準 | 指導教授 | 擋**開放給教師使用**，不擋實作與驗收 |
| P-03 | 教師數位分身書面同意書格式 | 專題負責人 / 指導教授 | 擋**產製與上架**（R-07），本輪不涉及 |
| P-04 | 腳本模板修訂時程 | 專題負責人 | 擋**套用階段**（見附錄 H.3），不擋本功能 |

#### P-01 的循環相依與解法

P-01 表面上是「開工前該定的參數」，但它**只能靠跑批次 A 拿到實際資料才能校準**——而批次 A 需要施工單核准，施工單又需要規格書 Frozen。若把 P-01 列為 Frozen 的前置條件，會形成解不開的循環。

**解法**：P-01 定位為**校準參數，不是規格決策**。

- v1.0 Frozen 時 P-01 維持預設值 `0.85`，並標記為「未校準」。
- 批次 A 完成後，以階段 A 的比對證據定版，回填至附錄 B 並記入附錄 J。此屬參數回填，**不觸發規格書退回**。
- 校準完成前，本功能不得用於正式產出，但可用於實作與階段 A 驗收。

#### P-02 為什麼不擋驗收

第 7.3 節已說明：本規格的驗收條件不包含「腳本好不好看」。系統的責任止於「追得回資料庫」與「流程走得完」，這兩項都有客觀判準且已寫入第 7 章。P-02 是**開放給教師實際使用**的門檻，不是實作完成的門檻。

## 附錄 B：候選主題聚合規則

**資料來源**：`faqs` collection。既有欄位已足夠，不需新增。

| 欄位 | 用途 |
|------|------|
| `question` / `normalizedQuestion` | 顯示與精確去重 |
| `questionEmbedding` | 同義題分群（不需重跑 embedding，省 token） |
| `hitCount` | 熱度排序，已有索引 `{ courseId: 1, hitCount: -1 }` |
| `matches` | 預覽該題目前撈到哪些片段 |

**分群規則**

1. 先以 `normalizedQuestion` 精確合併。
2. 再以 `questionEmbedding` 做 cosine 分群，門檻見 P-01。門檻必須**低於** `FAQ_CACHE_SIMILARITY_THRESHOLD`（預設 0.95）——那個門檻是用來判定「同一題可以直接回快取答案」，比「同一題可以合成同一支影片」嚴格得多。
3. 合併後：`totalHitCount` 為各筆加總，`variants[]` 保留全部原始問句（教師需要看到學生實際怎麼問）。

**拒答題排除**

被 `answerGeneration.service.js` 的 `isNoAnswerReply()` 判定的回答不會存進 `faqs`，因此以 `faqs` 為唯一來源時天然已排除。**此依賴須在程式註解標明**——若日後改以 `questions` 為來源，必須自行套用同一判定，否則會把「資料庫答不出來的題」選成影片主題。

## 附錄 C：證據包契約

```text
evidence: [
  {
    code:        'A' | 'B' | ...     // 對應模板 §2 的代號
    chunkId:     String              // 必填，引用驗證的比對基準
    videoId:     String
    videoTitle:  String
    startSec:    Number
    endSec:      Number
    rawText:     String              // 未修飾 STT 原文，不得糾錯
  }
]
```

**凍結語意**：寫入後即為不可變快照。來源影片被刪除、重新處理或自課程移除，皆不影響已凍結的證據包內容。

**重新凍結的唯一時機**：教師以 `retrieval` 類回饋退回時。此時產生新的證據包，並在新版本記錄「證據已更換」。

## 附錄 D：弧線適用性判定

**判定對象**：證據包內是否存在可作為「反轉」的轉折句。

**參考實例**（兩份既有腳本的反轉句都在資料庫原句中）：

| 腳本 | 轉折句出處 | 原句要點 |
|------|-----------|----------|
| V4 大語言模型 | `chunk_0106`+`0107` | 「大語言模型不是只有切gbt啦 除了他之外還有很多大語言模型」 |
| V5 OpenCV vs YOLO | `chunk_0003`+`0004` | 「是可以找到有搭配一個版本 就是用CPU用的優龍 不過那個效果非常非常的差 速度很慢」 |

兩者的共同特徵：**原句本身就帶有「你以為 X，其實不是 X」的語意**，不是作者外加的詮釋。

**不適用的典型情況**：純操作步驟、純名詞定義、平鋪直敘的流程說明。這些主題沒有可用的反轉，硬套弧線會使鏡 01 的鉤子與鏡 06 的揭曉失去呼應對象。

判定為不適用時回報 `SHORT_SCRIPT_ARC_NOT_APPLICABLE`，並在回應中附上證據包，讓教師自行判斷改用哪種手法（`docs/short-video-examples/` 另有十種手法可選）。

## 附錄 E：引用驗證規則

1. 解析生成結果，取出每一拍的 `basedOn`。
2. 缺少 `basedOn` 的拍 → 驗證失敗。
3. `basedOn` 為 chunkId 陣列時，逐一比對是否存在於本次 `evidence[].chunkId` 集合。任一不存在 → 驗證失敗。
4. `basedOn` 為 `'template'` 時，檢查該拍是否為結尾收尾拍。否則 → 驗證失敗。
5. 驗證失敗即**整份退回重生**（不得部分採用），重試上限見 DR-07。

**為什麼不允許部分採用**：部分採用等於預設「其他拍是對的」，但同一次生成裡出現一個捏造引用，代表模型當次的 grounding 已經不可信。

## 附錄 F：狀態機

|------|----------|----------|
| 建立腳本並凍結證據 | （無） | `evidence_ready` |
| 生成 | `evidence_ready` 或 `changes_requested` | `generated` |

## 附錄 G：環境設定與既有系統邊界

### G.1 Feature flag

新增 `SHORT_SCRIPT_AUTOMATION_ENABLED`，**預設 `false`**。為 `false` 時所有新增路由回 404。

須同步更新 `backend/.env.example` 與 `/health` 的 runtime 區塊。依 CLAUDE.md：判斷 runtime 狀態一律看 `/health`，不看 `.env`。

**部署提醒**：`.env` 不進版控，部署不會同步。新增變數後 VM 上必須以 `sudo -u focusflow` 手動維護 `backend/.env`，否則本機可跑不代表 VM 可跑。

### G.2 `usagelogs` 寫入邊界

依 DR-06 使用新的 event 型別。`teacherStats.service.js` 的 `queriesCount` 目前以 `USAGE_LOG_EVENTS.ASK` 計數，新 event 不得使用該值，否則教師儀表板的「問答次數」會被腳本生成次數污染。

### G.3 與 QA 主線的邊界

腳本檢索走**只檢索、不生成答案**的路徑：

- 不觸發 LLM 答案生成
- 不寫入 `faqs`（不得因為腳本檢索而產生新的 FAQ 快取）
- 不寫入 `questions`
- `askQuestion` 的回應格式零變更

### G.4 與 `ShortAsset` 的邊界

`ShortAsset` 是既有的短影片資產 model，本輪不碰。腳本（`shortscripts`）與資產（`shortassets`）是兩個階段：腳本 `approved` 之後才會進入產製與上架，那部分另案。

`ShortAsset` 的 `createShortAsset`（`shortAsset.service.js:110`）與 `updateShortAsset`（同檔 `:119`）沒有掛任何 HTTP route，目前只有測試在呼叫。學生端只有 `GET /api/v1/youtube/shorts`。此缺口屬上架功能範圍，另案處理。

### H.3 腳本模板為舊版

`docs/short-video-examples/teacher-avatar-track/4ish_腳本架構模板_教師數位分身x標準敘事弧線.md` 仍寫著三項與 MiniMax H3 官方規格不符的假設：

| 位置 | 現況 | 實際 |
|------|------|------|
| 第 107、281 行 | `Reference-to-Video` | H3 沒有這個模式名稱，應為「全能參考」 |
| 第 397 行 | 「一次產出 30 秒」 | 官方規格 5–15 秒／次，須分段生成後拼接 |
| 第 284 行 | 「驅動音軌…用於對嘴」 | H3 沒有餵外部音檔驅動嘴型的功能 |

使用者 2026-09-03 決定本輪不修。因為本功能輸出 JSON 而非 markdown，**不阻塞本規格**，但套用階段前必須修正，否則組員依模板填出來的每一支都會複製同樣的錯誤假設。對應待決事項 P-04。

### H.4 兩套腳本體系並存

`docs/short-video-examples/` 的十支範例（v8）刻意用同一觀念、同一組資料庫來源，只換呈現手法，目的是 A/B 比較，並有 G1 溯源／G2 字面驗證／G3 語音驗證三道閘。`teacher-avatar-track/` 是後加的教師數位分身手法，未收進該目錄 README、也未對齊 `_shared-conventions.md`。

本規格不處理兩套體系的整併，但實作時須知悉：本功能的引用驗證（附錄 E）在概念上等同十支體系的 G1 溯源閘。
