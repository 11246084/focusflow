# 製圖前檢查清單

> 在寫任何圖源之前，先完成 `references/diagram-brief.md`，再逐項確認。任一硬性資訊答不出來就先查證；只有會 materially 改變成果且無法由現有來源判定時才詢問使用者。

## 0. Diagram brief

- [ ] 讀者與閱讀目的已確認
- [ ] 只用一句話描述本圖要回答的設計問題
- [ ] 系統／子系統邊界與明確不納入範圍已寫出
- [ ] 主情境、必要替代／錯誤情境已列出；無關分支已排除
- [ ] 每個候選元素都能指出證據來源或明確標示 `planned`
- [ ] 新增／重繪版本已在建立檔案前判定
- [ ] 已依 `references/source-format-selection.md` 選擇 PlantUML 或 Mermaid，並記錄 renderer；沒有只因 agent 偏好而轉換既有圖源

## 1. 脈絡

- [ ] 這張圖屬哪個 OOAD 階段？（需求分析／物件分析／系統設計／物件設計／實作／測試）
- [ ] 要放在哪一章節？
- [ ] **這張圖回答什麼問題？**（一句話。答不出來 → 不畫）

## 2. 選圖

- [ ] 是否在系統手冊脈絡中？
  - 是 → 已查 `references/local/ntub-chapter-contract.md`？
  - 否 → 已走 SKILL.md 的自由決策樹？
- [ ] 若該章節有官方**指定**圖 → 直接採用，**不得**用 heuristic 否決
- [ ] 若該章節有官方**延伸**圖 → 已判斷是否值得畫
- [ ] 這個圖種是否真的適合表達這件事？（見 `references/diagram-catalog.md` 的「常見誤用」）

## 3. 該不該畫（僅在無章節契約時適用）

`[DOC:HEURISTIC]` 以下為提示，不是否決依據：

- [ ] 循序圖：協作物件是否有三個以上？
- [ ] 活動圖：流程是否有分支／並行／多參與者？
- [ ] 狀態機圖：建模對象是否為單一 classifier 且有可辨識的狀態？
- [ ] 元件圖：是否畫得出提供／需求介面？（畫不出 → 退回套件圖）
- [ ] 是否已有其他圖表達了同樣的資訊？

## 4. 事實來源

- [ ] `source` 是什麼？（程式碼／schema／現況文件）
- [ ] 來源層級是否夠高？（**不得**使用歷屆手冊、初評舊圖、舊會議紀錄）
- [ ] `verified` 日期？（實際查證的日期，不是今天）
- [ ] `implemented` 狀態？（`yes` / `partial` / `planned`）
- [ ] 若為分析層（分析類別圖、分析物件圖）→ **確認未使用反向工程**

## 5. 追溯

- [ ] `realizes` 填什麼？（`UC-xx` 或 `FR-xx`）
- [ ] 若填不出來 → 這張圖是孤兒，先確認它為何存在
- [ ] 若為內部技術流程 → 對應的 `FR-xx` 是否已在需求清單登錄？

## 6. 分析／設計層級（僅類別圖與物件圖）

- [ ] 這張圖放 5-4 還是 6-2？（章節位置即層級宣告）
- [ ] 分析層 → 已確認不會出現**實作洩漏強證據**：技術 stereotype、技術後綴類別名、框架／語言／資料庫型別、儲存細節、具體技術產物命名
- [ ] 分析層 → 若打算使用型別／可見性／操作記法，已確認它們仍屬概念層級（弱訊號，非禁用）
- [ ] 設計層 → 能說明「分析責任由誰承擔、以什麼方式承擔」（記法形式不拘）
- [ ] 設計層 → **未為了「通過規則」而預先計劃製造多餘的類別、型別標註、拆分或設計模式**
- [ ] 是否可能其實是資料庫綱要？（見判別器 D）

## 7. 使用個案（僅使用個案圖）

- [ ] 系統邊界框的名稱是什麼？
- [ ] 每個 actor 都在系統邊界之外？
- [ ] 沒有 actor 是本系統的模組、服務、資料庫或佇列？
- [ ] 每個 UC 名稱是「動詞 + 名詞」且從使用者角度？
- [ ] 被排除的內部流程已改列 `FR-xx`？

## 8. 編號與命名

- [ ] 圖號 `圖{章}-{節}-{序}` 是多少？（同節內從 1 起編）
- [ ] 圖名是什麼？（檔名與 `title` 須一致）
- [ ] 領域名詞已查過專案詞彙表？（未收錄者沿用程式碼命名，**不得自創譯名**）
- [ ] 術語使用 preferred term？（佈署圖、循序圖、狀態機圖⋯⋯）

## 9. 版面預估

`[DOC:HEURISTIC]`

- [ ] 預估元素數量是否超過約 20 個？
- [ ] 若是 → 已規劃拆圖策略與總覽圖？
- [ ] 循序圖／通訊圖：這張圖是否涵蓋兩個以上彼此獨立的觸發情境（反模式 D9）？例如「頁面載入時的自動查詢」與「使用者稍後主動送出的操作」是不同觸發，不應畫進同一張圖
- [ ] 若是 → 依觸發情境拆成多張；FocusFlow 專案已將此列為 `[FF:SHOULD]`，見 `references/local/focusflow-conventions.md` 的「循序圖拆圖粒度」一節

## 10. 圖族規則

- [ ] 已依圖種載入 `references/diagram-guides/` 中對應指南
- [ ] 循序圖／通訊圖：參與者、訊息、同步性與組合片段皆有來源
- [ ] 類別圖／物件圖：層級、責任、關係語意、多重性與快照情境已確認
- [ ] 活動圖／狀態機圖：流程控制與 classifier 生命週期未混淆
- [ ] 套件圖／元件圖／佈署圖：分群、介面與執行節點三種視角未混在同一張圖
