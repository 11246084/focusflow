FocusFlow 資料庫現況交接給後端
最後更新：2026-07-24

2026-07-24 補充：notifications 與 avatar
1. notifications 是 backend app-owned collection，STT / embedding uploader 不得寫入。
2. repo bootstrap 已加入 notifications 與三個 indexes：
   - recipientId + createdAt desc + _id desc
   - recipientId + readAt + createdAt desc + _id desc
   - recipientId + dedupeKey 的 partial unique index，只索引 string dedupeKey
3. 共享 Atlas 唯讀實查仍沒有 notifications；這是 live readiness 缺口，不代表可由本機自動建立。正式建立前需 DB owner 核准並核對 listIndexes。
4. User avatar 是 nullable nested metadata：filename、mimeType、updatedAt。filename 是單一部署儲存目錄的私有 key，不是公開 URL。
5. local-to-Atlas user sync 會保留 target avatar，不會把來源機器的 local filename 寫入目標環境。
6. Release E2E 必須覆寫到隔離 DB，並使用位於 UPLOAD_DIR 外的唯一 AVATAR_UPLOAD_DIR；不得 fallback 到共享 focusflow DB。

用途
這份純文字檔是給 backend 同學的現況摘要，目的是統一目前真正可採用的資料庫口徑，避免再被舊版 snake_case 文件誤導。

先看結論
1. video_segments_text 目前在 MongoDB 裡是 camelCase，不是 snake_case。
2. backend 的 VideoSegment model 已經和目前 DB 結構對齊。
3. 現在唯一應該使用的匯入工具是 mongodb_uploader.py。
4. import_video_segments_text.py 是舊腳本，因為會寫 snake_case，所以不能再用。
5. 目前主要風險已不是 video_segments_text 本身，而是 bridge 對應、videos ownership 邊界，以及 video_segments_video 還沒補齊 vector index。

已確認的現況
1. 2026-04-19 快照的 video_segments_text 為 105 筆；2026-07-24 唯讀實查總數為 313。
2. 105 筆 camelCase／來源拆分是 2026-04-19 快照；新增資料的欄位分布需另行重新統計。
3. snake_case 文件（chunk_id）目前是 0 筆。
4. mongodb_uploader.py 目前寫入的 text segment 欄位為：
   - chunkId
   - videoId
   - segmentId
   - startSec
   - endSec
   - text
   - embedding
   - courseId（只有設定 FOCUSFLOW_COURSE_ID 時才會寫入）
5. video_segments_text 目前 regular indexes 為：
   - _id_
   - courseId_1
   - segmentId_1
   - videoId_1
   - courseId_1_videoId_1
6. 目前文字 QA 使用的 Atlas vector index 為：
   - text_embedding_index
   - path = embedding
   - numDimensions = 3072
   - filter fields = courseId, videoId

backend 目前可以安全假設的事情
1. VideoSegment model 應繼續讀 camelCase 欄位：
   - segmentId
   - chunkId
   - videoId
   - startSec
   - endSec
2. buildSegmentLookupQuery 目前用 courseId 或 videoId 查詢，和現在的 DB README 及 uploader 行為一致。
3. normalizeSegment 回傳的 backend response shape 也是建在 camelCase segment 欄位上。
4. qa.service 目前的 Atlas filter 相容欄位也是 courseId + videoId。

關於 videos collection 的補充
1. videos 目前仍是 mixed collection。
2. app-owned videos 和 pipeline metadata 目前共存在同一個 collection。
3. backend 現在是靠 record shape 去分辨，不是靠完全定版的 ownership contract。
4. 這仍然是 backend 和資料層之間的真實邊界問題。

目前仍存在的問題
1. Bridge course 的對應還不算完全乾淨。
   - 目前 pipeline bridge course 的 video.video_id 和 segment.videoId 並不是直接對上的。
   - 現在能運作，是因為 segment 同時也有靠 courseId 在做 scope。
   - 如果之後 pipeline 換影片，courseId 或 videoId 的對應要一起更新。
2. video_segments_video 還沒有 ready 的 Atlas vector index。
   - 文字 QA 已可用。
   - multimodal QA 目前還不能算 ready。
3. videos ownership 仍未完全定版。
   - pipeline-owned metadata 和 app-owned uploaded videos 仍共存在同一個 collection。
   - sourceType / ownership contract 還需要後續釐清。
4. repo 裡仍保留 legacy 腳本。
   - 最危險的是 database/tools/legacy/import_video_segments_text.py，因為它會寫 snake_case，和目前 backend model 不相容。
5. repo 裡有幾份文件仍把 snake_case 寫成現行口徑。
   - 這些文件不應再被當作 video_segments_text 的當前真相。

為什麼說它們過期
因為這些文件仍描述 video_segments_text 目前使用 snake_case，但現在的 uploader、backend model、bridge lookup、database README 都已對齊到 camelCase text segment 結構。

建議 backend 接下來怎麼做
1. 在舊文件更新前，video_segments_text 的 live handoff 先以 database/README.md 為準。
2. 不要再根據舊文件直接把 videoId_1 當成孤立索引處理，除非先重新確認 DB 現況。
3. 匯入流程統一只用 mongodb_uploader.py。
4. 如果要更新文件，優先修正以下幾份裡的 snake_case 舊說法：
   - backend/docs/current-state.md
   - backend/docs/handoff-known-issues.md
   - docs/90_Archive/superseded/MongoDB_契約定版_v1_已過期.md
5. 如果後續要進 Phase 2，建議先把這三件事講清楚：
   - bridge course mapping contract
   - videos ownership contract
   - video_segments_video 的 vector index contract

對 backend 來說，今天的 video_segments_text 應視為一個已經和 uploader、model、query 邏輯對齊的 camelCase collection；目前真正該補的是文件同步，以及 bridge / multimodal / ownership 這三個剩餘邊界。
