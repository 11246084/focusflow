# 第7章 實作模型

## 7-1 佈署圖（Deployment diagram）

FocusFlow 由四個可獨立啟動的部分構成：在瀏覽器中執行的 React SPA、以 PM2 常駐的 Node.js／Express API、由 API 以子程序啟動的 Python AI Pipeline，以及外部受管的 MongoDB Atlas。瀏覽器與 LINE 都不直接讀寫資料庫；課程權限、影片管理與問答請求一律先進入 API，由 API 驗證身分與授權後再存取資料或呼叫外部服務。外部服務的憑證、Atlas 索引與正式主機的連線狀態屬執行環境事實，本章列出 2026-09-26 對正式環境的實測結果；環境設定會隨部署變動，實際狀態以 `/health` 端點為準。

判讀重點如下：

- **網頁請求路徑**：瀏覽器以 HTTPS 443 連到 Nginx，Nginx 直接回應 `frontend/focus-flow/dist` 靜態檔，並把 `/api/` 開頭的請求轉給本機 `localhost:4000` 上的 `focusflow-backend`。學生觀看影片時，瀏覽器另以 YouTube IFrame 直接向 YouTube 取得串流，不經過 FocusFlow 主機。
- **LINE 路徑**：LINE Platform 把使用者訊息以 HTTPS webhook（附 `X-Line-Signature`）送到 `ngrok.service` 的公開通道，再轉到本機 4000 埠的 `/api/v1/line/webhook`，不經過 Nginx 的 443；後端回覆時再以 HTTPS 呼叫 LINE Messaging API。通道網址屬部署變動項，不列入圖中。
- **短影音生成端**：ComfyUI 與 MiniMax H3 執行於教授主機，屬校內外部的地端元件，不在圖7-1-1 的 FocusFlow 佈署範圍內，已可運作；FocusFlow 目前沒有呼叫 ComfyUI 的程式碼，腳本與成品都由教師人工搬運（複製腳本、上傳成品）。系統串接規劃中：由教授主機上的小程式主動領取工作，再呼叫本機 ComfyUI 的 HTTP API，且只有一台 GPU，工作需排隊。
- **影片處理路徑**：API 收到上傳影片後寫入 `backend/uploads`，再以 `child_process.spawn` 啟動 `STT_Whisper/src/main.py`（多影片批次為 `batch_main.py`）。Pipeline 讀取來源影片、呼叫 Gemini 產生 embedding、以 pymongo 把片段寫入 Atlas，處理的開始、完成與失敗則以 HTTP 呼叫本機 `/api/v1/internal/*`，並以 `X-Processing-Secret` 驗證身分。
- **外部服務**：API 以 MongoDB 協定（TLS）存取 Atlas，以 HTTPS 呼叫 Gemini（回答生成可依設定切換為 OpenAI）、LINE 與 YouTube Data API（OAuth 2.0），以 SMTP 寄送驗證信。
- **自動部署**：`.github/workflows/deploy.yml` 定義 push 到 `main` 後，由虛擬機上的 self-hosted runner 取得工作，在 `/opt/focusflow` 執行 `git pull`、安裝後端相依套件、建置前端、以 `restorecon` 修正 SELinux context，接著 `pm2 restart focusflow-backend` 並 `systemctl reload nginx`；最後在主機內檢查 `/health` 的問答就緒狀態與 Nginx 的 API 代理。
- **對外連接埠**：依部署紀錄，對外僅 443 提供 HTTPS，80 埠由學校防火牆阻擋，Nginx 的 80 轉址只在主機內部生效；HTTPS 憑證由 acme.sh 以 TLS-ALPN-01 簽發並自動續約。2026-09-26 從校外實測：443 可連線並提供 Let's Encrypt 憑證（效期至 2026-12-09），HTTP 80 連線逾時無回應，並回應 HSTS 等安全標頭；非白名單來源的 CORS 預檢不回 `Access-Control-Allow-Origin`。憑證首次自動續約尚未發生，預計於 2026-11 中旬前後。

文件不記錄 IP、token、連線字串或其他環境秘密。

### 向量化流程與參數調整

FocusFlow 能回答「影片裡講了什麼」，前提是先把影片內容轉成電腦可以比對的形式。本小節說明三件事：一支影片如何變成可檢索的資料、學生提問時系統如何找出相關片段，以及開發過程中為了回答品質調整過哪些參數。

先說明幾個名詞：

- **片段（chunk）**：把整支影片的逐字稿切成數十字、十幾秒長的小段，每段記錄文字與在影片中的起訖秒數。片段是檢索與引用的最小單位，學生點選引用時，影片會跳到該片段的起點。
- **向量（embedding）**：由 AI 模型把一段文字轉成一串數字（本系統為 3072 個數字）。意思相近的文字，轉出的數字串在方向上也相近，因此可以用數學方法比較兩段文字的語意是否接近。
- **向量索引**：MongoDB Atlas（本系統使用的雲端資料庫服務）提供的功能，能在大量向量中快速找出與問題最接近的幾筆。
- **提示詞（prompt）**：系統交給回答生成模型的指示與資料，其中包含檢索到的片段。

圖7-2-6 左右兩欄分別是兩段流程：右側是影片上傳後，由 AI Pipeline 執行一次的「建立索引」；左側是學生每次提問時，由後端執行的「查詢」。兩者透過 Atlas 的向量索引銜接。此圖為資料流程示意，不屬於 UML 圖種。

| ⑦ 問題向量 | 以同一個模型把學生的問題轉成 3072 維單位向量 | 問題文字 → 向量 | `queryEmbedding.service.js` |
| ⑧ 課程範圍向量搜尋 | 只在該學生有權限的課程影片中搜尋，依餘弦相似度（計算方式見本小節後段）由高到低取前 15 筆片段 | 問題向量 → 15 個片段 | `qa.service.js` |
| ⑨ 回答生成 | 把 15 個片段依序編號為 S1～S15 放進提示詞，生成模型必須依片段作答，並回報實際採用了哪些編號 | 片段 → 答案與採用的片段 | `answerGeneration.service.js` |
| ⑩ 回答附引用 | 每個採用的片段顯示為一張引用卡，註明影片與時間，點選後影片跳到該片段 | 採用的片段 → 引用卡 | `qa.service.js`、前端課程頁 |

片段與問題雖然使用同一個模型，但送入模型時加上不同的前置說明（片段標為「文件內容」、問題標為「搜尋查詢」），這是 `gemini-embedding-2` 為檢索用途建議的用法。此外，學生提問時系統會先查詢常見問題快取（FAQ 快取，見圖6-1-4c）：與過去問題的文字完全相同，或問題向量的相似度達 0.95 以上，就直接沿用先前的答案，不再執行 ⑧、⑨。

語音辨識模型有 tiny、small 等不同大小，模型越大辨識越準確，但在 CPU 上處理越慢；beam size 是辨識時同時比較的候選句數，數值越大結果越穩定、也越慢。

兩種設定不同的原因是：資料庫中大部分既有片段，是團隊在開發用電腦上處理後上傳的，當時使用較小的 tiny 模型、beam size 1 與較短的片段上限；正式環境主機則沿用程式預設值。片段較短時，每個向量代表的內容較集中，但單一片段不一定足以回答問題，因此系統一次取 15 個片段送入提示詞（見表7-2-5）。目前尚未用同一批影片比較兩種設定的回答品質，因此無法斷定哪一種較佳。

#### 餘弦相似度如何計算

評審所問的「特徵值」，在本系統中就是步驟 ⑤、⑦ 產生的向量：由 `gemini-embedding-2` 模型把逐字稿片段或學生問題轉成的 3072 個數字，代表這段文字的語意。這些數字由模型產生，不是人工設計的特徵（例如關鍵字出現次數），也不是從影片畫面擷取的特徵；目前問答只比對文字的向量。

設問題向量為 $\mathbf{q}$、片段向量為 $\mathbf{d}$，兩者的餘弦相似度為兩向量夾角的餘弦值，如式7-2-1：

$$
\cos(\mathbf{q},\mathbf{d})=\frac{\mathbf{q}\cdot\mathbf{d}}{\lVert\mathbf{q}\rVert\,\lVert\mathbf{d}\rVert}=\frac{\sum_{i=1}^{3072} q_i d_i}{\sqrt{\sum_{i=1}^{3072} q_i^{2}}\;\sqrt{\sum_{i=1}^{3072} d_i^{2}}}
$$

式7-2-1 餘弦相似度

其中 $q_i$、$d_i$ 分別是兩個向量的第 $i$ 個數字。結果介於 $-1$ 與 $1$ 之間，越接近 1 代表兩段文字的語意越接近。由於步驟 ⑤、⑦ 已把向量調整為長度 1，式7-2-1 的分母等於 1，計算可簡化為兩向量對應數字相乘後加總，如式7-2-2：

$$
\lVert\mathbf{q}\rVert=\lVert\mathbf{d}\rVert=1\;\Rightarrow\;\cos(\mathbf{q},\mathbf{d})=\mathbf{q}\cdot\mathbf{d}=\sum_{i=1}^{3072} q_i d_i
$$

式7-2-2 單位向量的餘弦相似度

正式環境由 Atlas 的向量索引計算相似度並排序。Atlas 回傳的分數 $s$ 不是餘弦值本身，而是依式7-2-3 換算到 0～1 之間的值；兩者的排序結果相同。

$$
s=\frac{1+\cos(\mathbf{q},\mathbf{d})}{2},\qquad 0\le s\le 1
$$

式7-2-3 資料庫相似度分數與餘弦相似度的換算

常見問題快取的相似度比對，以及開發測試時不連接 Atlas 的情況，則由後端程式依式7-2-1 自行計算（程式見第 9 章表9-1-34）。

提問先經前置檢查：問題超過字數上限、今日提問次數用完或沒有課程權限時直接回傳 4xx，這屬於正常拒絕，不寫入 `questions`。通過檢查後，沒有對話歷史且 FAQ 快取啟用時先比對快取，命中且引用片段重新驗證通過即回傳快取答案；未命中或有對話歷史時進入檢索，以 query embedding 在課程範圍內搜尋片段。課程沒有可搜尋片段或找不到足夠相關片段時結果為 `no_match`；有命中片段則交由回答 provider 生成答案，若回覆為「片段不足」的固定文字也記為 `no_match`，否則為 `answered`，並在符合條件時寫入 FAQ 快取。檢索或生成過程中發生 provider 或系統錯誤（5xx）時結果為 `failed`，由 `recordFailedAsk` 留下失敗紀錄。三種結果都會寫入 `questions` 與 `usage_logs`，供統計與後台查詢。

### LINE 對話範圍

圖7-4-5 描述 `User` 文件中 `lineUserId`、`lineConversationState` 與 `activeCourseId` 三個欄位共同形成的 LINE 對話範圍。

![LINE對話範圍狀態機圖](../images/圖7-4-5-LINE對話範圍狀態機圖-v3-1.png)

圖7-4-5 LINE對話範圍狀態機圖

所有 LINE 事件都須先通過 `X-Line-Signature` 驗簽。使用者在 LINE 傳送有效且未過期的一次性綁定碼後，系統寫入 `lineUserId` 並刪除綁定碼，進入「已綁定、未選課」；若綁定連結同時帶有課程且可提問，則直接進入「已選課」。輸入「切換課程」時，系統列出有效修課且已發布的課程（最多 4 門按鈕）並進入 `awaiting_course_selection`；此時一般文字提問只會收到提示。點選的課程若有效修課、已發布且有影片，就設定 `activeCourseId` 進入「已選課」；課程沒有影片則回到 `idle`。從網頁「詢問助教」帶入課程也可直接進入「已選課」。已選課時一般文字訊息會呼叫共用 QA 服務，並保留最近 8 則訊息作為多輪對話脈絡（`MAX_CONVERSATION_TURNS` 預設 4 輪）。老師撤銷修課，或提問時發現修課或課程已失效，系統清除 `activeCourseId` 與對話歷史並回到「已綁定、未選課」。使用者在網站解除綁定，或同一 LINE 帳號改綁其他系統帳號時，回到「未綁定」。

### 修課

圖7-4-6 描述學生與課程之間的修課紀錄（`Enrollment`）如何建立、撤銷與恢復；它決定學生能否存取課程影片、問答、LINE 課程範圍與短影音。

![修課狀態機圖](../images/圖7-4-6-修課狀態機圖-v2-0.png)

圖7-4-6 修課狀態機圖

- **建立（→ `active`）**：課程教師或管理員以 Email 指派，或以名單匯入；對象必須是啟用中的學生帳號。系統以 `(studentId, courseId)` upsert 建立紀錄，重複指派只更新指派者與指派時間，不會產生第二筆。
- **觀看進度（`active` 自我轉換）**：學生觀看影片達門檻時更新 `watchedVideoIds` 與 `progress`，狀態不變。
- **撤銷（`active` → `revoked`）**：必須存在 `active` 紀錄，否則回 404 `ENROLLMENT_NOT_FOUND`。撤銷時記錄撤銷者與時間，並清除該學生在這門課的 LINE 選課與對話歷史（對應圖7-4-5 回到「已綁定、未選課」）。
- **恢復（`revoked` → `active`）**：再次指派或匯入同一位學生時沿用原紀錄，清除撤銷資訊，保留原本的觀看進度。
- **刪除（→ 終止）**：課程被刪除時，該課程的全部修課紀錄一併刪除。

### 短影音腳本

圖7-4-7 描述短影音腳本（`ShortScript`）自凍結證據到上架或放棄的生命週期，轉換以 `shortScript.service.js` 的 `ALLOWED_TRANSITIONS` 為準。

![短影音腳本狀態機圖](../images/圖7-4-7-短影音腳本狀態機圖-v2-0.png)

圖7-4-7 短影音腳本狀態機圖

- **建立（→ `evidence_ready`）**：教師選擇或接受系統推薦的提問主題；必須有通過篩選的候選且檢索到足夠片段，系統才凍結 Leaf 片段與鄰接片段作為證據，否則回 422，不建立腳本。
- **生成（`evidence_ready` → `generated`）**：以 LLM 生成腳本，引用只能來自凍結證據；生成失敗（含證據包不適用敘事弧線的 422 `SHORT_SCRIPT_ARC_NOT_APPLICABLE`）時狀態不變。
- **要求修改（`generated` → `changes_requested`）**：教師必須指定回饋類型（retrieval 或 narrative）並填寫回饋。
- **重新生成（`changes_requested` → `generated`）**：retrieval 類回饋先重新凍結證據，narrative 類沿用原證據改寫，新增下一個版本。
- **上架（`generated`／`changes_requested` → `approved`）**：只有該腳本的成品成功上架（圖7-4-8 進入 `published`）時，系統才把腳本標為 `approved`；教師審核介面沒有「核准」選項。
- **退回（`approved` → `changes_requested`）**：成品審核被退回時，系統依退回理由決定回饋類型（「內容有誤」為 retrieval，其餘為 narrative）；教師也可主動要求修改。
- **放棄（進行中任一狀態 → `dismissed`）**：教師放棄主題並記錄理由；`dismissed` 為終態，之後任何轉換都回 409 `SHORT_SCRIPT_STATE_INVALID`。

### 短影音成品

圖7-4-8 以 `status` 與 `reviewStatus` 兩個欄位的組合描述短影音成品（`ShortAsset`）的生命週期：`draft` 為複合狀態，內含審核的 `pending`、`approved`、`rejected`；`published` 時 `reviewStatus` 必為 `approved`。

![短影音成品狀態機圖](../images/圖7-4-8-短影音成品狀態機圖-v2-0.png)

圖7-4-8 短影音成品狀態機圖

- **上傳（→ `draft`／`pending`）**：教師依腳本上傳成品檔案，必須勾選 AI 揭露與書面同意；系統建立第 1 代（`generationVersion = 1`）並排程以 unlisted 上傳 YouTube 供預覽。
- **審核通過（`pending` → `approved`）**：審核時送出的版本必須等於目前版本，且該版本尚未審核；否則回 409 `SHORT_ASSET_REVIEW_STALE` 或 `SHORT_ASSET_REVIEW_CONFLICT`。
- **審核退回（`pending` → `rejected`）**：至少附一項退回理由；系統同時把對應腳本退回 `changes_requested`（圖7-4-7），並把 YouTube 影片轉為 private。
- **重新上傳（`rejected`／`approved` → `pending`）**：尚未上架的成品重新上傳時換代，`generationVersion` 加 1 並清除審核結果；已上架的成品不會換代。
- **上架（`approved` → `published`）**：審核通過、YouTube 已上傳完成且已確認揭露時，系統設定 `publishedAt` 並把腳本標為 `approved`；審核比上傳早完成時，會在上傳完成後補做這一步。未通過當代審核即上架回 409 `SHORT_ASSET_NOT_APPROVED`。
- **封存（`draft`／`published` → `archived`）**：課程刪除時，該課程尚未封存的成品全部改為 `archived` 並記錄封存前狀態；若課程刪除失敗，系統以 best-effort 還原為封存前狀態。來源影片刪除不會觸發封存。
- **`ready`**：此值定義於 `SHORT_ASSET_STATUSES`，但目前沒有任何路由或排程寫入它，只有未被呼叫的通用更新函式 `updateShortAsset` 能接受，因此圖中以獨立狀態標示為保留值。

### YouTube 上傳

圖7-4-9 描述教師上傳的課程影片自動上傳到 YouTube 的過程，記錄在 `Video` 的 `youtubeUpload` 子文件；此功能由 `YOUTUBE_UPLOAD_ENABLED` 控制，預設關閉。

![YouTube上傳狀態機圖](../images/圖7-4-9-YouTube上傳狀態機圖-v2-0.png)

圖7-4-9 YouTube上傳狀態機圖

- **開始上傳（未上傳 → `uploading`）**：影片處理完成（圖7-4-3 進入 `completed`）後，若上傳已啟用且 OAuth 憑證完整、影片尚無 `youtubeVideoId`，系統以條件更新搶佔這支影片，避免重複上傳，並把嘗試次數加 1。
- **上傳成功（`uploading` → `uploaded`）**：寫入 `youtubeVideoId` 與影片網址；`uploaded` 為終態。
- **可重試的失敗（`uploading` → `failed`／可重試）**：錯誤發生在影片內容尚未送出前等可安全重試的情況，且未達次數上限（預設 3 次）時，記錄錯誤與下次重試時間（指數退避）。
- **需人工確認的失敗（`uploading` → `failed`／需人工確認）**：本機檔案遺失、失敗且不可安全重試或已達上限時進入此狀態；開機復原若發現 `uploading` 超過逾時門檻，也會隔離為此狀態，因為遠端可能已上傳成功，需先到 YouTube Studio 確認。
- **重試（`failed`／可重試 → `uploading`）**：課程教師或管理員手動重試，或開機復原在下次重試時間到達後自動重試；開機復原由 `YOUTUBE_UPLOAD_RECOVERY_ENABLED` 控制，預設關閉。手動重試不符條件時依序回 409 `YOUTUBE_UPLOAD_ALREADY_COMPLETED`、`YOUTUBE_UPLOAD_RETRY_NOT_ALLOWED`、`YOUTUBE_UPLOAD_RETRY_UNSAFE` 或 `YOUTUBE_UPLOAD_RETRY_LIMIT_REACHED`。
