# httpOnly cookie 登入設計決策

這份文件記錄登入憑證從 localStorage 改存 httpOnly cookie 的設計，2026-10-21～25 與使用者逐題討論後**全部定案**，供實作與審查使用，不必重讀對話。這項工作必須在「系統設定」功能上線前完成。功能完成與驗收只看[目前狀態](../../current-status.md)。

## 已定案與前提

| # | 決策 | 理由 |
|---|---|---|
| 1 | **一般登出要在伺服器端立即撤銷**（原 Q10 選 b）：新增 `authSessions` collection，每次登入寫一筆、以 `sid` 識別；登出刪除該筆，`authenticate` 每次確認紀錄仍存在。細節見第 2～5 項。使用者 2026-10-24 同意 | 使用者認為這是資安問題，不接受「登出後被複製的 token 仍可用到過期（admin 12 小時、學生 7 天）」的空窗。代價是多一個 collection、每個請求多一次以 `_id` 查詢 |
| 2 | **authSessions 只存最少欄位，登出直接刪除**（原 Q13）：collection 名稱固定為 `authSessions`（model 明確寫 `collection: 'authSessions'`）。欄位只有 `_id`（即 `sid`，`crypto.randomBytes(16)` 的 hex）、`userId`、`createdAt`、`expiresAt`（等於 JWT 到期時間）、`userAgent`（截斷 200 字）；**不存 `role`**，角色與帳號狀態每次請求都以 `users` 為準。每個受保護的請求（cookie 與 Bearer 都一樣）都要確認紀錄存在且 `expiresAt > now`。登出、全裝置登出直接刪除，不留撤銷標記。不記 IP 與 `lastSeenAt`。使用者 2026-10-24 同意，並依審查意見調整 | 欄位越少，外洩時暴露越少；刪除比標記簡單。`role` 若存在 session 裡，容易被誤用成權限來源，被降級的人可能沿用舊角色，所以不存（`authenticate` 本來就每次重查 User）。不記 IP 是因為**目前沒有業務需求**，也少存一項個人資料；若日後需要，先確認 nginx 有傳 `X-Forwarded-For`，再設 `app.set('trust proxy', 'loopback')`，不能設成 `true`（資安審查第 5 項）。`lastSeenAt` 會讓每個請求都多一次寫入 |
| 3 | **index 定義在 model，正式環境由 ensure 腳本在授權後建立**（原 Q14）：`{ userId: 1 }`（全裝置登出、改密碼時刪除其他 session）與 TTL `{ expiresAt: 1 }, { expireAfterSeconds: 0 }`；TTL 約每 60 秒才清一次，`authenticate` 仍檢查 `expiresAt > now`。比照 `db:ensure-questions` 新增可重複執行的 `npm run db:ensure-auth-sessions`，只建缺少的 index。正式 Atlas 於部署當天經使用者授權、確認目標後執行，再用唯讀 MongoDB MCP 的 `collection-indexes` 查證；route 測試沿用 `backendTestHarness.js` 的記憶體 model stub（新增 `AuthSession` stub）；index、TTL 與原子更新的實際行為，另在隔離的本機 Mongo 驗證，不碰 Atlas（第 15 項）。**Atlas 準備狀態**：使用者 2026-10-24 已建立自訂角色 `authSessionsIndexer`，只有 `createCollection`、`createIndex`、`listIndexes`，範圍限 `focusflow.authSessions`；使用它的資料庫帳號（Temporary User，1 天）與獨立的可寫 MCP 連線部署當天才建立，原本的 MongoDB MCP 維持唯讀。使用者 2026-10-24 同意 | 沿用專案既有的 ensure 腳本與「Atlas index 變更需明確授權」規則；index 定義留在程式裡，換環境可重建、可在 PR 審查。執行帳號只能動這一個 collection，也不能刪 index 或資料，誤操作的影響範圍最小 |
| 4 | **所有 session token 都經 `issueSession` 建紀錄，寫入失敗不發 token，每人最多 20 筆**（原 Q15）：簽發與建紀錄合成 `issueSession(user, { expiresIn, userAgent })`，網頁 cookie、腳本 Bearer、部署探測都只能用它。**先寫紀錄、成功後才簽 JWT**；寫入失敗回 503，不回任何 token。上限：新紀錄寫入後，查該使用者依 `createdAt`、`_id` 由新到舊排序、第 21 筆以後的紀錄並刪除；同時登入時兩邊各自整理一次，全部完成後一定回到 20 筆以內，過程中短暫多出幾筆可以接受，不用 transaction。**部署探測改用獨立帳號**（例 `deploy-probe@focusflow.local`），只有 student 角色、只選修探測需要的課程、密碼設成無法登入的隨機值、標記為已完成信箱驗證（系統設定第 34 項）；deploy.yml 兩處改查這個帳號並呼叫 `issueSession`，期限維持 5 分鐘。建立這個帳號屬於正式 Atlas 寫入，部署前另行授權。使用者 2026-10-24 同意，並依審查意見調整 | 只要有一種 token 不查紀錄，登出撤銷就有缺口；先簽後寫則會在寫入失敗時留下查不到、也撤銷不了的 token。上限用「寫入後整理」而不是「寫入前檢查」，才不會因為同時登入而互相擋掉。目前探測用的是展示用學生帳號 `student@focusflow.local`，部署探測寫入的紀錄可能把正在展示的 session 擠掉，也會混進該帳號的用量統計，所以改用專用帳號並給最小權限 |
| 5 | **session 紀錄與 `tokenVersion` 並用，先遞增版本再刪紀錄**（原 Q16）：一般登出只刪這一筆、不遞增；登出所有裝置遞增並刪全部；重設密碼、被停用、被降級、**實際升為 admin** 遞增並刪全部。**升為 admin**：角色變更與版本遞增在同一次更新中完成，刪除該帳號全部 session，pending、step-up 與信任裝置一併作廢；目標帳號必須重新走 admin 登入與信箱兩段式驗證，新 session 為 12 小時。只編輯原 admin 的姓名、角色未改變時不撤銷。此補充由使用者 2026-10-25 定案。**自己改密碼**：遞增版本 → 用 `issueSession` 建一筆**新的 `sid`** → 刪除這個使用者「新 `sid` 以外」的所有紀錄（含原本這台的舊紀錄），當下裝置換上新 cookie，舊 step-up cookie 一併清除。版本以 `$inc` 原子遞增。**所有憑證都檢查版本**：session、pending、step-up 的 JWT 都帶 `ver`，驗證時一律和資料庫目前的 `User.tokenVersion` 比對。已登入裝置清單畫面不在本次範圍。使用者 2026-10-24 同意，並依審查意見調整 | session 紀錄負責撤銷「這一張」，版本負責撤銷「這個帳號的所有憑證」；pending 與 step-up 沒有 session 紀錄，只能靠版本作廢。先遞增版本，刪紀錄失敗時舊憑證也已失效。改密碼換新 `sid`，符合 OWASP 工作階段指引「權限或憑證變更後重發 session 識別碼」的建議，舊 `sid` 綁的 step-up 也一起失效；審查也接受沿用舊 `sid`，但換新的語意較單純 |
| 6 | **session cookie 名稱、屬性與效期**（原 Q1）：production 一律 `__Host-ff_session`，`HttpOnly; Secure; SameSite=Strict; Path=/`、不設 Domain，只依 `NODE_ENV` 判斷，**不提供關閉安全屬性的環境變數**；本機 http 用 `ff_session`、不加 Secure。效期：admin 12 小時，教師與學生 7 天。cookie 期限跟著 JWT 剩餘效期：Express `res.cookie()` 的 `maxAge` 單位是**毫秒**，JWT 的 `exp` 是**秒**，由共用函式換算並有單元測試。設 cookie 與清 cookie 共用同一組選項（名稱、`Path=/`、Secure、SameSite、HttpOnly），`clearCookie()` 才能在正式與本機都清得掉。瀏覽器驗收實測：從 LINE 內建瀏覽器、Email 連結與跨站轉址進站後，`/auth/me` 能恢復登入。使用者 2026-10-24 同意，並依審查意見補充實作與驗收細節 | `__Host-` 讓瀏覽器強制 Secure、Path=/、不帶 Domain，學校其他 `*.ntub.edu.tw` 網站無法寫入同名 cookie 蓋掉登入狀態。安全屬性不能用設定關掉，避免正式環境因設錯而退回。教師不碰系統設定，高風險操作另有 step-up，所以和學生同為 7 天。Strict 只影響外部連結的第一次頁面載入，SPA 載入後的 API 請求仍會帶 cookie，但 LINE 內建瀏覽器的行為必須實測，不能只靠推論 |
| 7 | **CSRF 防護與腳本模式**（原 Q2）：新增 `CSRF_TRUSTED_ORIGINS`，獨立於 CORS 的 `ALLOWED_ORIGINS`，正式環境只填 `https://focusflow.ntub.edu.tw`；production 缺 `CSRF_TRUSTED_ORIGINS` 或 `ALLOWED_ORIGINS` 都拒絕啟動。**以 cookie 驗證的寫入請求**（POST、PUT、PATCH、DELETE）須 `Origin` 完全符合信任來源且帶 `X-Requested-With: FocusFlow`，否則回 `403 CSRF_REJECTED`；GET、HEAD、**OPTIONS（CORS 預檢）**不檢查。**會發 cookie 的入口一律經同一個 `setAuthCookie`**，它只在請求已通過「Origin 在信任來源內」檢查時才設 cookie，否則丟錯，避免新增入口時漏掉。入口清單：login、register、pending 的送驗證碼／重寄／設定新密碼（`admin_2fa`、`email_verify`、`first_login`）、自己改密碼後重簽、`POST /auth/step-up`；密碼重設 confirm 只改密碼、不發 session，使用者要重新登入。**沒有 Origin 的匿名請求**視為腳本模式：只在 body 回 token、完全不帶 Set-Cookie；`Origin: null` 或不在名單內則拒絕。**Bearer 例外以驗證成功為準**：帶 `Authorization` 就只驗 Bearer，失敗回 401、不改用 cookie；只有驗證成功才免 CSRF 檢查。LINE webhook 與 `/internal/*` 沿用各自的驗證、不讀 cookie。實作時檢查所有 GET 路由都不改資料並列入測試。使用者 2026-10-24 同意，並依審查意見補充 | 學校其他 `*.ntub.edu.tw` 網站對我們算同站，SameSite 擋不住，所以要再檢查 Origin 與自訂 header（OWASP CSRF 指引）。缺少 Origin 不一定是腳本，瀏覽器也可能省略；但惡意網站用 fetch 跨來源送出時一定帶自己的 Origin，會被拒絕，拿不到 token；CORS 也必須是白名單而不是 `*`，所以 production 要求兩個設定都存在。發 cookie 集中在一個函式，比逐一檢查每個入口可靠 |
| 8 | **瀏覽器與腳本拆成兩個登入端點**（原 Q3 選 b）：`POST /auth/login` 保留給腳本，路徑與回應格式不變，只回 body token、不設 cookie；請求只要帶 `Origin`、`Sec-Fetch-Site` 或 `Sec-Fetch-Dest` 任一個 header 就拒絕；**不檢查 `Sec-Fetch-Mode`**。新增 `POST /auth/session` 給瀏覽器，`Origin` 須在信任來源內，只設 cookie；登出用 `DELETE /auth/session`。register、pending 驗證、step-up 只走 cookie 模式。**所有瀏覽器用的端點都不在 body 回正式 JWT**，列入測試。腳本登入的帳號需要信箱驗證時回 `403 VERIFICATION_REQUIRED`，不發 pending cookie。所有登入、驗證相關回應加 `Cache-Control: no-store`。不使用原本設計的 `X-Auth-Transport` header。使用者 2026-10-24 同意，並依審查意見調整 | 只用 `Origin` 分流時，少數省略 `Origin` 的瀏覽器會在 body 收到 JWT，違背改用 httpOnly 的目的。拆成兩個端點後，正常的瀏覽器流程（網頁上的 fetch 或表單 POST 一定帶 `Origin`，現代瀏覽器另帶 `Sec-Fetch-Site` 等來源資訊）不會拿到 token；但缺少這些 header 不能證明對方不是瀏覽器，所以這是「降低風險」，**不是絕對保證**。三支腳本與測試維持使用 fetch。2026-10-24 使用者確認：瀏覽器的 `Sec-Fetch-Site` 是此分流的判斷訊號；本機 Node.js 22.23.4 fetch 只自動帶 `Sec-Fetch-Mode: cors`，不帶 Origin、Sec-Fetch-Site 或 Sec-Fetch-Dest，所以不能把 Mode 當成拒絕依據 |
| 9 | **舊 JWT 由伺服器拒收，所有簽發點集中**（原 Q4）：`authenticate` 要求 JWT **payload** 帶 `typ: 'session'`、`ver`、`sid`（`typ` 放在 payload，和 JWT header 原本的 `typ: 'JWT'` 是不同欄位），`ver` 等於資料庫目前的 `tokenVersion`，且 `authSessions` 查得到 `sid`；缺任一項就拒收，所以上線後所有舊 JWT 立即失效，不做舊 token 換 cookie 的 API，使用者重新登入一次。簽發只能透過三個函式：session 用 `issueSession`（第 4 項），pending 用 `signPendingToken`，step-up 用 `signStepUpToken`。2026-10-24 搜尋 repo，直接呼叫 `jwt.sign` 的地方有 `backend/src/services/auth.service.js:67`、`.github/workflows/deploy.yml:113` 與 `:201`、`backend/tests/auth.routes.test.js:430`，全部改用上述函式或改寫成「舊 token 被拒收」的測試；`.claude/rules/security.md` 的 JWT 流程同步更新。前端刪除 `ff_token`，`ff_user` 只作畫面顯示快取。**部署順序**：`authSessions` 的 index 先建好再部署新版驗證（見第 16 項）。**前端驗收**：移除 `ff_token` 後所有 API 都走 cookie、重新整理頁面能經 `/auth/me` 恢復登入（見第 15 項）。使用者 2026-10-24 同意，並依審查意見補充 | 只清 localStorage 不會撤銷已被複製的 JWT；簽發與驗證必須一起換，否則腳本或部署探測會被新版後端拒收。集中簽發才能確保每張 session token 都有紀錄可撤銷 |

**httpOnly** 表示網頁 JavaScript 不能直接讀取 cookie；**CSRF** 是攻擊者誘使瀏覽器帶著登入 cookie 發出操作；**JWT** 是後端簽發的登入憑證。cookie 防止直接讀取憑證，仍須搭配來源檢查，且不能單獨防住 XSS 代使用者操作。

例：瀏覽器呼叫 `POST /auth/session` → 後端寫入 `authSessions`、設 `__Host-ff_session` cookie，body 不回 token → 重新整理時前端呼叫 `/auth/me` 恢復身分。腳本呼叫 `POST /auth/login`（不帶 `Origin`）→ 取得 body token，之後送 Bearer，回應不設 cookie。使用者按「登出」→ `DELETE /auth/session` 刪掉這筆紀錄並清 cookie，被複製出去的同一張 token 也立即失效。
