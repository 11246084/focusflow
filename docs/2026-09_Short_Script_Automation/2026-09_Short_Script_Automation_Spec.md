## 這份文件在講什麼（先讀這頁）

### 現在的做法

短影片腳本目前是純人工：組員手動查資料庫、挑逐字稿片段、寫成一份 13 節的腳本文件。已經產出兩份範例（大語言模型、OpenCV vs YOLO）與一份空白模板，放在 `docs/short-video-examples/teacher-avatar-track/`。

一份腳本大約要花掉：找題目、查片段、比對原文、設計敘事弧線、寫 8 拍口白、填模板固定章節。其中**只有中間三件事是因主題而異**，其餘都是重複勞動。

### 這一輪要做什麼

把「選題 → 找證據 → 生成腳本 → 老師審核 → 通過或退回重生」這條路自動化，但**產出的是結構化資料（JSON），不是完整的腳本 markdown**。

模板的固定章節（分身規格、配樂、字卡、ffmpeg、驗收清單）不由系統生成。系統只產出證據表、敘事設定、8 拍口白與 B-roll 隱喻建議。

### 為什麼不直接生成完整 markdown

三個理由：

1. 模板固定章節在既有兩份範例之間幾乎逐字相同，讓 LLM 每次重寫是浪費，也多開一個出錯面。
2. 腳本模板目前是舊版（見附錄 H.3），之後要修。輸出 JSON 可以讓自動化與模板版本解耦——模板改版時換 renderer 就好，不必回頭改 prompt。
3. 生成範圍越小，幻覺面越小。

### 這一輪不做什麼

不做影片產製（B-roll 生成、語音合成、ffmpeg 合成）、不修改既有腳本範例與模板。影片仍由教師以外部工具產出，系統只負責教師**審核成品通過之後**的自動上架。

### 最重要的一條線

**腳本裡的每一句話都必須追得回課程逐字稿。** 這不是品質建議，是本功能能否成立的前提。教師的臉與聲音是複製的，如果講的內容還是編的，這個功能不能上線。實作方式見附錄 E。

## 1. 這一輪要證明什麼

要證明的是**一件事**：系統自動選出的題目與證據，跟人工判斷的品質是否可比。

不是要證明「系統能生成腳本」——LLM 當然能生出文字。要證明的是生出來的東西**追得回資料庫、而且老師願意用**。

因此驗收分三階段：先驗證資料，再驗證生成，最後驗證上架。詳見第 7 章。

## 2. 教師從頭到尾會經過什麼

```text
① 系統自動選題（排序規則見 DR-12），撈出證據片段並凍結快照
      ↓
② 系統生成 8 拍口白 + 敘事設定 + 2~3 組 B-roll 隱喻建議
      ↓
③ 系統自動執行引用驗證：每一拍的依據必須在①的證據包內
      ↓
④ 教師在腳本頁檢視證據與分鏡，複製完整腳本      ← 不是審核關卡，見 2.0
      ↓
⑤ 教師依腳本產出影片                            ← 人工，系統不代勞
      ↓
⑥ 教師把影片上傳到 FocusFlow
      ↓
⑦ 教師審核成品影片                              ← 唯一的審核關卡
      ├─ 通過 → 上架
      └─ 退回 → 依退回理由回到 ② 重生腳本
                  ├─ contentIncorrect → retrieval（重撈證據）
                  └─ 其餘 → narrative（同一份證據重寫敘事）
      ↓
⑧ 系統自動上傳到 YouTube 並建立 ShortAsset，學生端 Shorts 可見
```

系統做的是**選題、找證據、生成腳本、上架**。教師做的是**產出影片、上傳、審核成品**。

> **⑦ 的回饋迴圈已於 2026-09-09 補上（DR-20）。** 成品審核頁由組員完成（`ShortAsset` + `/shorts/:id/review`）；
> `ShortAsset` 新增 `sourceScriptId` / `sourceVersionNo` 指回腳本與版本，成品退回時會把退回理由寫回該版腳本
> 並將腳本轉為 `changes_requested`。⑧ 的上架自動化（WO-08）本身仍未實作。

### 2.0 腳本預審：保留設計，本輪不做（2026-09-09 決議）

規格書原本在生成後、產片前加了一道「教師審核腳本」。使用者 2026-09-09 判斷**對教師太麻煩**，決定保留想法但不實作為教師的必經步驟。

- 前端不提供腳本審核介面，教師拿到腳本直接複製去製作。
- 後端的 `submitReview`／回饋分流／版本紀錄**保留且仍然需要**——成品審核退回時要靠這套機制驅動腳本重生。它從「教師的一道手續」變成「成品審核的後端支援」。

### 2.1 教師必須看得到證據，不能只看口白

即使腳本不再有預審關卡，教師複製腳本前仍會看到內容。**只看口白無法判斷引用是否正確**——口白讀起來通順，不代表撈對了片段。

前端頁面必須同時呈現：`selectionReason`（為什麼選這一題、哪些候選因證據不足被跳過）、**完整的證據對照表含未修飾的 STT 原文**、以及每一拍的 `basedOn`。缺少任何一項，教師就無法判斷引用是否正確。

原因：STT 逐字稿錯字很重（實例：`雀的gp` 應為 ChatGPT、`OvenCV` 應為 OpenCV、`優龍` 應為 YOLO、`Opens TV` 應為 OpenCV）。只看口白無法判斷系統是不是撈錯片段——口白讀起來通順，不代表引用正確。

### 2.2 回饋為什麼要分流

若不分流、一律回到生成，遇到「講錯了」這類回饋時，模型會在**錯誤的證據**上反覆重寫，結果是越改越像編的。回饋類型由教師在退回時指定，不由系統猜。

### 2.3 上架為什麼綁在成品審核之後

上傳到 YouTube 是**不可逆的對外動作**，因此觸發點是「教師審核成品通過」。

原規格把觸發點寫成「教師上傳影片檔」，理由是「上傳的動作本身就是確認」。這條理由不成立：**教師是先上傳才看得到成品**，上傳當下還沒看過影片，不可能構成對內容的確認。照這個寫法，教師上傳完影片就直接發布到 YouTube，審核頁形同虛設。

系統不會自己產生影片、不會在教師沒上傳的情況下發布任何東西，也不會在教師沒按下通過之前發布任何東西。詳見附錄 K。

## 4. 輸出契約

系統的產出是下列 JSON。這是本功能的核心需求定義。

```text
{
  scriptId, courseId, topic, status,

  evidence: [                       // 凍結快照，不可即時重查；含鄰接擴展（附錄 C.1）
    { code: 'A', chunkId, videoId, videoTitle, startSec, endSec, rawText }
  ],
  evidenceFrozenAt,

  globalSettings: {
    coreEvent,                      // 核心事件：觀眾原本的認知 vs 實際狀況
    coreView,                       // 核心觀點
    audienceAssumption,             // 觀眾原本可能以為
    audienceTakeaway,               // 觀眾看完後應該發現
    targetAudience
  },

  writingFourQuestions: [ ... ],    // 動筆前四題

  visualMetaphorOptions: [          // 2~3 組供教師挑選
    { label, s1, s2, s3 }
  ],

  shots: [                          // 8 拍
    {
      shotNo, arcRole, timeRange,
      narration, subtitle, editing, sfx,
      basedOn: ['chunk_0038'] | 'template'
    }
  ]
}
```

### 4.1 `basedOn` 的語意

| 值 | 意義 | 允許時機 |
|----|------|----------|
| chunkId 陣列 | 這句話改寫自這些片段 | 任何有內容的口白 |
| `'template'` | 不給答案的反問或懸念 | **僅限**結尾收尾拍 |

既有兩份範例的鏡 08 都是這個用法（「那你，說得出幾個大語言模型的名字嗎？」／「那你的任務，你會選哪一個？」），共同特徵是**不提供資料庫沒確認過的答案**。

### 4.2 `evidence[].rawText` 必須是未修飾原文

不得在此階段自動糾錯後覆蓋。理由有二：

1. 糾錯本身會引入幻覺（模型可能把 `優龍` 改成錯的東西）。
2. 糾錯後的文字無法比對回 `video_segments_text` 的原始片段，可追溯性斷掉。

糾錯屬於教師套用腳本時的人工步驟，不屬於系統職責。

## 5. 安全紅線

以下每一條，違反即視為本功能不可上線，不接受「先做出來再說」。

### R-01 不得產出追不回資料庫的內容

每一拍必須帶 `basedOn`，且所引 chunkId 必須存在於本次證據包。任一項對不上，**整份退回重生**，不接受部分採用。詳見附錄 E。

### R-02 不得放寬跨課程隔離

範圍建構一律沿用 `bridgeScope.service.js`。跨課程 allowlist 的 fail-closed 語意是學生試用版 Phase 1 已收斂的安全邊界，不得為了讓腳本「有更多素材可用」而放寬。

### R-03 不得寫入唯讀 collection

| Collection | 權限 |
|------------|------|
| `shortscripts` | 讀寫（本輪新增） |
| `faqs`、`video_segments_text`、`videos`、`courses` | **唯讀** |
| `questions` | **唯讀，唯一例外是 `questionEmbedding` 欄位**（DR-14）。兩條允許的寫入路徑：(1) QA 既有的 `recordQuestion`，向量在該時點已算好、不額外呼叫 API；(2) 一次性 backfill 腳本補齊舊資料。**其餘欄位一律不得寫入**，也不得新增或刪除 `questions` 文件 |
| `usagelogs` | 只寫新增的 event 型別，且不得計入既有統計（見附錄 G.2） |
| `shortassets` | 讀寫（上架流程需要，見附錄 K） |

任何工作項若發現需要寫入唯讀 collection，停止該項並回報，不得自行放寬。

### R-04 自動選題必須確定性且可追溯

選題改為自動（DR-02）後，這條紅線改為：排序規則必須是確定性的、不使用 LLM 判斷，且腳本紀錄須保存 `selectionReason`（當時的熱度、涵蓋度、排名與被淘汰者）。教師必須能回答「為什麼系統選了這一題」。

候選全被過濾掉時回報 `SHORT_SCRIPT_NO_CANDIDATE`，**不得降低門檻硬選**。

### R-05 不得對 STT 原文做自動糾錯後覆蓋

見 4.2。

### R-06 弧線不適用時不得硬生成

8 拍標準弧線的核心是「反轉」。既有兩份範例的反轉都是**逐字稿原句就有的**（V4 的「不是只有 ChatGPT」出自 chunk_0106；V5 的「CPU 版效果非常差、速度很慢」出自 chunk_0003+0004）。證據包內找不到轉折句時，硬套只會逼出兩種結果：編一個假反轉（就是幻覺），或鉤子空轉。此時必須回報不適用，交由教師改用其他手法。判定方式見附錄 D。

### R-07 產製與發布的前置門檻不由系統代勞

教師數位分身需要**書面同意**（載明用途、範圍、期限、可撤回），成品需要**全片常駐的 AI 揭露標示**。這兩項是流程門檻，系統不檢查也不代為取得。**上架 API 須要求教師明示確認已完成這兩項並記錄確認時間**，未確認時回 `SHORT_ASSET_DISCLOSURE_REQUIRED`。詳見附錄 K.5。

### R-08 未經成品審核通過的影片不得上架

上傳 YouTube 是不可逆的對外動作，因此**上架的閘門是成品審核，不是教師上傳**：

```text
教師上傳影片檔 → 建立 ShortAsset（draft）→ 教師審核成品
                                              ├─ 通過 → 上傳 YouTube、上架
                                              └─ 退回 → 不上架，回饋寫回腳本（DR-20）
```

只有 `reviewStatus = approved` 且 `reviewedGenerationVersion` 等於當前 `generationVersion` 的 `ShortAsset` 可以進入上架流程。系統不自行發布任何內容。

「教師上傳＝教師確認」不成立：教師是**先上傳才看得到成品**，上傳當下還沒看過影片。詳見附錄 K。

## 6. 錯誤碼

依 `.claude/rules/api-design.md`，使用 SCREAMING_SNAKE_CASE，並須於實作時補進該規則檔的表格。

| 錯誤碼 | HTTP | 情境 |
|--------|------|------|
| `SHORT_SCRIPT_NOT_FOUND` | 404 | 腳本不存在 |
| `SHORT_SCRIPT_EVIDENCE_EMPTY` | 422 | 檢索不到可用片段，無法凍結證據 |
| `SHORT_SCRIPT_CITATION_INVALID` | 502 | 生成結果引用了證據包外的 chunkId，重試上限內未通過 |
| `SHORT_SCRIPT_ARC_NOT_APPLICABLE` | 422 | 證據包無轉折句，不適用 8 拍弧線 |
| `SHORT_SCRIPT_STATE_INVALID` | 409 | 狀態轉換不合法 |
| `SHORT_SCRIPT_NO_CANDIDATE` | 422 | 自動選題後沒有任何候選通過過濾（DR-12），不得降低門檻硬選 |
| `SHORT_ASSET_NOT_APPROVED` | 409 | 成品尚未通過審核（或審核的不是當前 `generationVersion`），不得進入上架流程 |
| `SHORT_ASSET_DISCLOSURE_REQUIRED` | 400 | 上架請求未確認 AI 揭露標示與書面同意（附錄 K.5） |

沿用既有錯誤碼：`VALIDATION_ERROR`、`INVALID_ID`、`COURSE_NOT_FOUND`、`COURSE_MANAGE_DENIED`、`UNAUTHORIZED`、`FORBIDDEN`、`UPLOAD_ERROR`、`YOUTUBE_UPLOAD_NOT_CONFIGURED`、`YOUTUBE_UPLOAD_FAILED`。

## 7. 驗收條件

### 7.1 階段 A：資料階段（對應施工單停止點 SP-1）

**目的**：驗證「系統選的題目與證據，跟人工判斷可比」。這是整條路最便宜的可行性驗證。

**執行方式**：對至少 2 門課各跑一次候選聚合與證據凍結，與人工撰寫 V4／V5 時實際採用的題目與片段做人工比對。

**必須通過**：

- [ ] 同義題確實合併（以 V5 的實例驗證：「open cv 跟 yolo 的關係是甚麼?」「YOLO跟opencv的具體差異是什麼？」「opencv跟yolo有什麼差異?」三者須併為一個候選）
- [ ] 候選清單不含拒答題
- [ ] 跨課程負向測試：其他課程的片段一筆都不得出現在證據包
- [ ] 證據包在來源影片刪除後仍完整可讀
- [ ] 全程未寫入任何唯讀 collection（以查詢前後筆數比對證明）
- [ ] backend 全套測試通過，測試總數不減少

**明確失敗條件**（出現任一項即階段 A 未通過，須回頭調整參數，不得往下做）：

- 系統撈出的證據包，**完全不包含**人工版本採用的核心片段
- 同義題分群把明顯不同主題的問題併在一起

**比對結果須存入** `evidence/`，並記錄使用的分群門檻值。

### 7.2 階段 B：生成階段（對應施工單停止點 SP-2）

**必須通過**：

- [ ] 注入含捏造 chunkId 的假生成結果，驗證器必須攔下並整份退回（不得部分採用）
- [ ] 證據包無轉折句時，回報 `SHORT_SCRIPT_ARC_NOT_APPLICABLE`，而非硬生成
- [ ] `'template'` 只出現在結尾收尾拍
- [ ] provider 未設定時 fail-fast，不得靜默 fallback
- [ ] 版本可逐版取出並比對差異
- [ ] `retrieval` 類回饋確實重新凍結證據，並在新版本標記證據已更換
- [ ] 每條路由涵蓋成功、未授權、無權限、資源不存在
- [ ] 自動選題在同一資料庫狀態下**重跑兩次選出同一題**，且 `selectionReason` 記錄了被淘汰者
- [ ] 候選全被過濾時回報 `SHORT_SCRIPT_NO_CANDIDATE`，未降低門檻硬選
- [ ] backend 全套測試通過，測試總數不減少

### 7.3 階段 C：上架（新增）

**必須通過**：

- [ ] 成品未經審核通過時不觸發 YouTube 上傳，回 `SHORT_ASSET_NOT_APPROVED`
- [ ] 成品被退回時**不上架**，且退回理由寫回 `sourceVersionNo` 指定的那一版腳本，腳本轉 `changes_requested`（DR-20）
- [ ] 退回理由含 `contentIncorrect` 時回饋類型為 `retrieval`，其餘為 `narrative`
- [ ] 腳本連結失敗時成品審核仍成立（fail soft），不回傳錯誤
- [ ] `YOUTUBE_UPLOAD_ENABLED=false` 時 fail-fast 回 `YOUTUBE_UPLOAD_NOT_CONFIGURED`，不得靜默略過
- [ ] 未確認 AI 揭露與書面同意時被拒，回 `SHORT_ASSET_DISCLOSURE_REQUIRED`
- [ ] YouTube 上傳失敗時 `ShortAsset` 維持 `draft` 並記錄原因，可重試，不留下半完成狀態
- [ ] 上傳成功後學生端 `GET /api/v1/youtube/shorts` 撈得到，且只有該課程的學生撈得到
- [ ] live 驗收須實際上傳一支到 YouTube 並確認可播放（不可只用 mock 通過）

### 7.4 不列入驗收的事

「腳本好不好看」「敘事夠不夠吸引人」不列入本規格的驗收條件——沒有客觀判準，且屬於教師的專業判斷。系統的責任止於**追得回資料庫**與**流程走得完**。品質標準若要納入，須由指導教授另行定義（見 8.2）。

#### DR-20 補充：退回理由如何對應到腳本回饋

六種成品退回理由全部追得回腳本——**沒有實拍環節，畫面與音訊都是照腳本生成的**——差別只在追到腳本的哪一部分：

| 退回理由 | 對應回饋類型 | 為什麼 |
|----------|--------------|--------|
| `contentIncorrect` | `retrieval` | 「講錯了」的根因是撈錯證據，必須重撈。在錯的證據上重寫敘事只會越改越像編的 |
| `incomplete` | `narrative` | 證據沒問題，是腳本沒把話講完 |
| `subtitleIssue` | `narrative` | 字幕由腳本的 `subtitle` 欄生成（DR-19） |
| `audioIssue` | `narrative` | 語音由腳本的口白生成，唸得不對就是口白寫法要改 |
| `visualQuality` | `narrative` | 畫面依腳本的視覺隱喻與分鏡生成 |
| `other` | `narrative` | 保守選擇：重撈證據的代價與風險都高於重寫敘事 |

同時勾選多項且含 `contentIncorrect` 時以 `retrieval` 為準——證據錯是更根本的問題。

**連結失敗必須 fail soft。** 成品審核在寫回腳本之前就已寫入資料庫，此時再拋錯會讓 API 回錯誤但審核其實已成立，教師重送會撞上 `SHORT_ASSET_REVIEW_CONFLICT`。連結失敗只記 log，代價是腳本狀態沒跟著改，教師仍可在腳本頁自行重新生成。

#### DR-12 排序規則

自動選題必須是**確定性的**：同樣的資料庫狀態一定選出同一題，且能對教師解釋原因。因此不使用 LLM 判斷「哪個主題比較值得做」。

**先過濾**（不符合者直接不列入）：

1. 被提問次數 >= 2（DR-03，以 `questions` 筆數計算）
2. 該主題沒有 `approved` 或 `dismissed` 的既有腳本紀錄（附錄 F）
3. 證據涵蓋度 ≥ 最低片段數。兩份手寫腳本各用 6 個片段，因此門檻定為 **6**
4. 通過弧線適用性判定（附錄 D）——沒有轉折句的主題不自動選，避免自動產出必然被退回的腳本

**再排序**：

1. **提問人數（`uniqueAskerCount`）由高到低**（DR-17）
2. 同分時，提問次數由高到低
3. 再同分時，證據涵蓋度高者優先
4. 再同分時，最近一次被提問的時間較新者優先
5. 全部同分時，取正規化問句的字典序，確保結果可重現

**不設最低人數門檻**：目前資料的提問者僅 2～3 人，若要求「至少 2 人問過」會讓幾乎所有候選被淘汰。人數只用於排序，不用於過濾；熱度過濾仍依 DR-03 的提問次數 >= 2。

**第 3 層的淘汰行為**：候選依排序**逐一評估**，證據不足 6 筆者淘汰後換下一名，**不是撞到第一名就整個失敗**。被淘汰者記入 `selectionReason.rejectedForEvidence`（排名、主題、實際證據數、淘汰原因），否則教師看到系統選了第 N 名卻不知道前面幾名為何出局。全部候選都不足時才回 `SHORT_SCRIPT_EVIDENCE_EMPTY`。

**選出後**：取第一個通過全部層級的候選建立腳本。系統須在腳本紀錄中保存 `selectionReason`（當時的 `totalHitCount`、涵蓋度、排名、以及被淘汰的前幾名與原因），教師審核時看得到，否則「為什麼是這一題」無法追溯。

**候選全被過濾掉時**：不建立腳本，回報 zero-state，不得降低門檻硬選。

#### DR-12 的已知限制

目前資料量下最熱門的題也僅被問過個位數次，且提問者僅 2～3 人（見 DR-17），次數差異沒有統計意義，因此排序第一名**不代表它客觀上最值得做**，只代表它在現有規則下排最前面。這是接受的取捨：教師的審核關卡（第 2 章第 ④ 步）與 `dismissed` 機制負責攔下不合適的選題。

待 P-02 有了品質判準、且資料量成長後，本規則應重新檢討。

當初把它列為待決而非 Frozen 前置條件，是因為它有循環相依：門檻只能靠跑批次 A 拿實際資料才能校準，而批次 A 需要施工單核准，施工單又需要規格書 Frozen。解法是把它定位為**校準參數而非規格決策**——Frozen 時維持預設值並標記未校準，取得證據後回填。此流程已完整走過一次，結果見 [校準證據](evidence/2026-09-04_p01-threshold-calibration.md)。

**校準前必須先修掉三個 bug**（詳見證據檔）：backfill 與向量查詢都以原始字串比對、但分群以正規化文字為鍵，導致同一題的不同寫法只有一種拿到向量；以及證據依時間排序後直接截斷，使後段高分命中整批遺失。首次執行的門檻比較結果因此不可採信。

#### P-02 為什麼不擋驗收

第 7.4 節已說明：本規格的驗收條件不包含「腳本好不好看」。系統的責任止於「追得回資料庫」與「流程走得完」，這兩項都有客觀判準且已寫入第 7 章。P-02 是**開放給教師實際使用**的門檻，不是實作完成的門檻。

## 附錄 B：候選主題聚合規則

**資料來源**：`questions` collection（2026-09-04 由 `faqs` 改為 `questions`，見 DR-14）。

| 欄位 | 用途 |
|------|------|
| `question` | 原始問句，顯示用 |
| （新增）`questionEmbedding` | 同義題分群。QA 流程本來就會算 query embedding，順手存下即可，不額外呼叫 API |
| `courseId` + 筆數 | 熱度＝該問句在該課程出現的次數，`group by` 正規化問句後計數 |
| `status` / `answer` / `runtime` | 過濾用，見下方 |
| `matches` | 預覽該題當時撈到哪些片段 |

### B.1 為什麼不用 `faqs`

原設計以 `faqs` 為來源，2026-09-04 實測後推翻。三個理由：

**一、`hitCount` 不是「被問過幾次」。** `saveFaqEntry` 建立新 FAQ 時 `$setOnInsert: { hitCount: 0 }`，只有後續**快取命中**才由 `recordFaqHit` 遞增。因此 `hitCount` 的語意是「快取命中次數」，實際提問次數是 `hitCount + 1`。原本 DR-03 的門檻 `hitCount >= 2` 實際等於「問過 3 次以上」，比規格書自述的「問過一次不構成常問」嚴格了一級。

**二、`faqs` 的累計會歸零。** FAQ 快取是事件驅動失效：影片刪除、影片重新處理完成、影片掛載／自課程移除、課程刪除，都會整批清除該課程的 FAQ。清掉後重新累計，`hitCount` 從 0 開始——**過去的提問熱度全部消失**。另有容量淘汰：超過 `FAQ_CACHE_MAX_ENTRIES_PER_COURSE` 時砍 `hitCount` 最低者，冷門題會被直接刪除。

**三、涵蓋不完整。** `shouldSaveFaq` 要求 `!(conversationHistory?.length)`，而 LINE Bot 的提問多帶對話歷史，因此**學生在 LINE 上問的題目大部分不會進 `faqs`**。

快取本來就該能被清掉，`faqs` 的設計沒有錯；**錯的是把快取當成統計來源**。`questions` 是逐筆追加、不隨影片異動刪除的紀錄，才是熱度的正確來源。

### B.2 改用 `questions` 後必須自行套用的過濾

`faqs` 原本替我們擋掉的三類資料，改用 `questions` 後要自己擋：

| 要排除 | 判斷依據 |
|--------|----------|
| 「答不出來」的題 | `answerGeneration.service.js` 的 `isNoAnswerReply(answer)` |
| runtime 降級時的回答 | `runtime.degraded === true` |
| 沒撈到片段的題 | `status` 為 `no_match` |

漏掉任一項，就會把「資料庫答不出來的題」選成影片主題。

### B.3 分群規則

1. 先以正規化問句（比照 `normalizeFaqQuestion`：轉小寫、去除非文字數字字元）精確合併並計數。這一層零成本。
2. 再以 `questionEmbedding` 做 cosine 分群，門檻 **0.90**（DR-15，已校準）。門檻必須**低於** `FAQ_CACHE_SIMILARITY_THRESHOLD`（預設 0.95）——那個門檻判定「同一題可直接回快取答案」，比「同一題可合成同一支影片」嚴格得多。
3. 為控制成本，**只對前 M 名（依第 1 層計數）計算或讀取向量**，其餘不處理。
4. 合併後：`totalAskCount` 為各筆加總，`variants[]` 保留全部原始問句（教師需要看到學生實際怎麼問）。

### B.4 舊資料的向量補齊

`questions` 新增 `questionEmbedding` 只對**之後**的提問有效，既有紀錄沒有向量。補齊方式：對去重後的問句做一次性 backfill（同類工具已有先例：`scripts/backfillQuestionsFromUsageLogs.js`）。未補齊前，沒有向量的問句依 B.3 第 1 層精確合併處理，不與其他問句語意合併。

## 附錄 C：證據包契約

```text
evidence: [
  {
    code:        'A' | 'B' | ...     // 對應模板 §2 的代號
    chunkId:     String              // 必填，引用驗證的比對基準
    videoId:     String
    videoTitle:  String
    startSec:    Number
    endSec:      Number
    rawText:     String              // 未修飾 STT 原文，不得糾錯
  }
]
```

**凍結語意**：寫入後即為不可變快照。來源影片被刪除、重新處理或自課程移除，皆不影響已凍結的證據包內容。

**重新凍結的唯一時機**：教師以 `retrieval` 類回饋退回時。此時產生新的證據包，並在新版本記錄「證據已更換」。

### C.1 鄰接擴展（必做）

檢索取得 TopK 之後，**必須**把命中片段往前後擴展再凍結，不得只取 TopK 原樣。

**理由：STT 是按時間切 chunk，不是按語意切的，一句完整的話常常斷在兩格之間。** 兩份手寫腳本的證據表可以直接驗證這件事：

| 腳本 | 證據代號與 chunkId | 觀察 |
|------|------------------|------|
| V4 大語言模型 | A=`chunk_0038`、B=`0039`、C=`0040`、D=`0041` | **連續四格**，同一支影片 |
| V4 | F=`chunk_0106`+`0107` | 相鄰合併 |
| V5 OpenCV vs YOLO | A=`chunk_0001`、B=`0002`、C=`0003`+`0004`、D=`0005`+`0006` | 連續六格，其中 C、D 各為兩格合併 |

V5 的 C 是最清楚的例子：`chunk_0003` 只講到「它是必須用GPU的」，要接上 `chunk_0004` 的「不過那個效果非常非常的差 速度很慢」才構成完整的轉折。只取 top-1 會讓整支片的反轉消失。

**與命中上限的關係（DR-16）**

命中片段依優先序佔用證據名額（見下方規則 5），因此**腳本檢索的命中上限必須低於證據上限**，否則擴展片段一個都進不來。預設搭配為命中 6、證據上限 12，實測結果為 6 命中 + 6 擴展。

**擴展規則**

1. **只在同一 `videoId` 內擴展。** 跨影片的 chunk 沒有連續關係——V4 的 E 來自 `aiA10_1140119_2`，與 A~D 所在的 `aiA10_1140119_1` 是不同影片。
2. **鄰接判定以同一 `videoId` 內的 `startSec` 排序為準**，不解析 `chunkId` 的數字後綴。`videoSegment` schema 沒有 `chunkIndex` 欄位，`chunkId` 只是字串（`chunk_0038` 這種格式），依賴其命名格式不穩。既有複合索引 `{ courseId: 1, videoId: 1 }` 足以支撐此查詢。
3. **擴展窗口可配置，不得寫死 N+1。** V4 的 A–D 是連續四格，固定只擴一格會漏。
4. **擴展後必須去重併段。** 若 `chunk_0003` 與 `chunk_0005` 同時命中 TopK，各自擴展會讓 `0004` 重複出現；重疊區間須合併為單一證據項。
5. **所有命中片段優先於所有擴展片段**。證據超過上限時，先砍擴展片段，不得砍掉命中片段——鄰居只是補上下文，不該擠掉命中。實作上依「檢索分數順序」截斷，再排回時間順序顯示；若依時間排序後直接截斷，會只留下最早的片段，後段高分命中整批遺失。
6. 擴展來的片段與原命中片段在 `evidence[]` 中**地位相同**，皆可被 `basedOn` 引用（僅以 `expandedFrom` 標記來源供診斷）。

**與既有服務的區別**：`childExpansion.service.js` 做的是 Parent→Leaf 展開，**不是**鄰接展開，不可直接沿用。

### C.2 涵蓋度即時計算，不累積

「這個主題目前有多少 supporting chunks」**是當下資料庫狀態的純函數，不是累積量**，因此不存入任何 collection。

- 新影片上傳後，同一問句自然會撈到更多片段，重算即為最新值。
- 反之，累積的計數在影片刪除、重新處理或自課程移除後不會自行減回，會停留在已不成立的數字。

此原則與 `faqs` 快取的已知缺口同源：存了衍生值又沒有完整失效機制，就會回舊答案。

**效能取捨（DR-02 改為自動選題後的作法）**：自動選題需要涵蓋度才能排序與過濾，但對每一筆候選都算涵蓋度等於跑 N 次檢索，再加上弧線判定會更貴。因此採**分層淘汰，不對全部候選做完整評估**：

```text
第 1 層｜零成本過濾
  hitCount >= 2、無 approved / dismissed 紀錄
  → 用 faqs 既有欄位與一次 shortscripts 查詢即可，不跑檢索
      ↓
第 2 層｜依 totalHitCount 排序，只取前 M 名（預設 M = 10）
      ↓
第 3 層｜對這 M 名依序算涵蓋度，淘汰不足 6 個片段者
      ↓
第 4 層｜對存活者依序做弧線適用性判定，第一個通過的即為選中主題
  → 一旦選中就停止，不評估其餘候選
```

最壞情況跑 M 次檢索，實務上通常在前幾名就選出。M 為可配置值。

## 附錄 D：弧線適用性判定

**判定對象**：證據包內是否存在可作為「反轉」的轉折句。

**參考實例**（兩份既有腳本的反轉句都在資料庫原句中）：

| 腳本 | 轉折句出處 | 原句要點 |
|------|-----------|----------|
| V4 大語言模型 | `chunk_0106`+`0107` | 「大語言模型不是只有切gbt啦 除了他之外還有很多大語言模型」 |
| V5 OpenCV vs YOLO | `chunk_0003`+`0004` | 「是可以找到有搭配一個版本 就是用CPU用的優龍 不過那個效果非常非常的差 速度很慢」 |

兩者的共同特徵：**原句本身就帶有「你以為 X，其實不是 X」的語意**，不是作者外加的詮釋。

**不適用的典型情況**：純操作步驟、純名詞定義、平鋪直敘的流程說明。這些主題沒有可用的反轉，硬套弧線會使鏡 01 的鉤子與鏡 06 的揭曉失去呼應對象。

判定為不適用時回報 `SHORT_SCRIPT_ARC_NOT_APPLICABLE`，並在回應中附上證據包，讓教師自行判斷改用哪種手法（`docs/short-video-examples/` 另有十種手法可選）。

## 附錄 E：引用驗證規則

1. 解析生成結果，取出每一拍的 `basedOn`。
2. 缺少 `basedOn` 的拍 → 驗證失敗。
3. `basedOn` 為 chunkId 陣列時，逐一比對是否存在於本次 `evidence[].chunkId` 集合。任一不存在 → 驗證失敗。
4. `basedOn` 為 `'template'` 時，檢查該拍是否為結尾收尾拍。否則 → 驗證失敗。
5. 驗證失敗即**整份退回重生**（不得部分採用），重試上限見 DR-07。

**為什麼不允許部分採用**：部分採用等於預設「其他拍是對的」，但同一次生成裡出現一個捏造引用，代表模型當次的 grounding 已經不可信。

## 附錄 F：狀態機

| 操作 | 前置狀態 | 目標狀態 |
|------|----------|----------|
| 建立腳本並凍結證據 | （無） | `evidence_ready` |
| 生成 | `evidence_ready` 或 `changes_requested` | `generated` |
| 教師退回 | `generated` | `changes_requested` |
| 教師通過 | `generated` | `approved` |
| **教師在候選清單否決** | （無） | `dismissed` |
| **判定不適用 8 拍弧線** | `evidence_ready` | `dismissed` |
| **教師審核時直接否決整個主題** | `generated` | `dismissed` |
| **放棄已退回的腳本** | `changes_requested` | `dismissed` |
| **成品影片被退回**（DR-20） | `approved` | `changes_requested` |
| **放棄已核准的腳本** | `approved` | `dismissed` |

`dismissed` 是終態，不得再轉出。

**`approved` 不是終態（2026-09-09 修正）。** 原本列為終態，但整支影片都是從腳本生成的：成品審核退回時，唯一能改的就是腳本。若 `approved` 不得轉出，教師只剩「否決整個主題重新來過」一條路，等於丟掉已凍結的證據與既有版本。因此 `approved` 可再轉出到 `changes_requested`（成品退回或教師自行退回）與 `dismissed`（放棄）。

非法轉換回 `SHORT_SCRIPT_STATE_INVALID`（409），沿用既有影片處理狀態機的錯誤慣例。

### F.1 `dismissed` 為什麼存在

候選清單的排除條件不能只看「已經做過」。教師可能**連腳本都不想生成就否決**某個候選（判斷它不適合做影片），這種情況不會產生任何腳本紀錄；若不留痕，下次候選清單又會把它推到最上面，教師每次都要重新否決一次。

`dismissed` 紀錄允許 `evidence` 為空——從候選清單直接否決時，只需 `courseId`、`sourceQuestions`、`status`、`dismissReason`。

### F.2 為什麼不為此另立 collection

「主題被問過幾次」與「累積多少 supporting chunks」都不需要新增儲存（前者由 `questions` 筆數計算，後者依 C.2 即時算）。**唯一無法重算的是教師的判斷**——否決與不適用判定不存就永遠消失。

判斷是否需要新增儲存的通則：**能從現有資料重算出來的值不要存**。存了就要維護一致性。

依此通則，本輪需要持久化的只有否決紀錄，量級是每門課個位數到十幾筆，以 `shortscripts` 的 `dismissed` 狀態承載即可，不值得獨立 collection。

**日後應獨立出去的條件**：若主題層級開始需要掛載更多狀態（優先度標記、製作排程、指派負責人、跨課程主題合併），`shortscripts` 會變成兩種東西的混合體，屆時才是拆分時機。現在拆屬過早最佳化。

## 附錄 G：環境設定與既有系統邊界

### G.1 Feature flag

新增 `SHORT_SCRIPT_AUTOMATION_ENABLED`，**預設 `false`**。為 `false` 時所有新增路由回 404。

須同步更新 `backend/.env.example` 與 `/health` 的 runtime 區塊。依 CLAUDE.md：判斷 runtime 狀態一律看 `/health`，不看 `.env`。

**部署提醒**：`.env` 不進版控，部署不會同步。新增變數後 VM 上必須以 `sudo -u focusflow` 手動維護 `backend/.env`，否則本機可跑不代表 VM 可跑。

### G.2 `usagelogs` 寫入邊界

依 DR-06 使用新的 event 型別。`teacherStats.service.js` 的 `queriesCount` 目前以 `USAGE_LOG_EVENTS.ASK` 計數，新 event 不得使用該值，否則教師儀表板的「問答次數」會被腳本生成次數污染。

### G.3 與 QA 主線的邊界

腳本檢索走**只檢索、不生成答案**的路徑：

- 不觸發 LLM 答案生成
- 不寫入 `faqs`（不得因為腳本檢索而產生新的 FAQ 快取）
- 不寫入 `questions`
- `askQuestion` 的回應格式零變更

### G.4 與 `ShortAsset` 的邊界

`ShortAsset` 是既有的短影片資產 model，本輪不碰。腳本（`shortscripts`）與資產（`shortassets`）是兩個階段：腳本 `approved` 之後才會進入產製與上架，那部分另案。

## 附錄 K：上架契約

### K.1 觸發與流程

```text
教師依腳本產出影片
      ↓
教師上傳影片檔到 FocusFlow（multipart，沿用既有 upload middleware）
      ↓
系統建立 ShortAsset（status = draft，reviewStatus = pending）
      ↓ 記錄 sourceScriptId / sourceVersionNo（DR-20）
教師審核成品（POST /api/v1/shorts/:id/review）
      ├─ rejected → 不上架；退回理由寫回該版腳本，腳本轉 changes_requested（DR-20）
      └─ approved ↓
系統呼叫 youtubeUpload.service 自動上傳
      ↓
成功 → 回寫 youtubeVideoId / youtubeUrl，status = published
失敗 → status 維持 draft，記錄失敗原因，可重試
      ↓
學生端 GET /api/v1/youtube/shorts 可見
```

**上架的閘門是成品審核（R-08）。** 教師上傳只建立 `draft`，不觸發任何對外動作；未經成品審核通過的影片不得上傳 YouTube。

### K.2 可複用的既有資產

| 資產 | 位置 | 狀態 |
|------|------|------|
| YouTube 上傳原語 | `youtubeUpload.service.js` 的 `uploadLocalVideo` | 2026-08-02 已用真實 OAuth 憑證完成 live 端對端驗證。**`autoUploadVideoToYouTube` 不可複用**——它綁死 `Video` model（讀 `video.filePath`、寫 `video.youtubeUpload`），對 `ShortAsset` 無效；可複用的是它底下的 `uploadLocalVideo`（2026-09-09 實作時發現，原表格寫錯） |
| 刪除時轉 private | 同檔 `privatizeVideoOnDelete` | 同日 live 驗證通過 |
| 上傳狀態快照 | 同檔 `buildYouTubeUploadSnapshot` | 可直接用於 `ShortAsset` |
| 短影片資產 model | `shortAsset.model.js` | 已有 `youtubeVideoId`、`youtubeUrl`、`youtubeAvailability`、`youtubePrivacyStatus`；2026-09-09 補上 `filePath`、`disclosure`、`youtubeUpload` 稽核區塊 |
| 學生端 Shorts feed | `youtube.routes.js:9` | 已存在 |
| 資產 CRUD service | `shortAsset.service.js:110 / :119` | **存在但沒有掛任何 HTTP route**，本輪須補 |

### K.3 硬性前置條件

| 條件 | 現況 | 說明 |
|------|------|------|
| `YOUTUBE_UPLOAD_ENABLED=true` | **預設 `false`** | 為 `false` 時上架流程須 fail-fast 回 `YOUTUBE_UPLOAD_NOT_CONFIGURED`，不得靜默略過 |
| OAuth refresh token（含 `youtube.force-ssl` scope） | VM 上已設定 | 判斷是否可用一律看 `/health.runtime.youtubeUpload`，不看 `.env` |
| nginx `client_max_body_size` | VM 已設 500M | 沒有它影片上傳會被 nginx 以 413 擋掉 |

### K.4 不能誤稱的邊界

- **上傳預設 unlisted 是架構限制，不是疏漏。** private 影片無法用 iframe 嵌入播放，學生端會全部掛掉。unlisted 代表「拿到連結就能看」，**不能說成「只有修課學生看得到」**。
- **刪除時轉 private 不保證下架。** 轉 private 失敗只記 log 不中斷刪除，因此不能說「刪除必定讓 YouTube 影片下架」。
- OAuth 同意畫面雖已發布為正式版，但未送 Google 驗證（授權時仍顯示未驗證警告、有 100 使用者上限），且尚未經長期運行觀察，**不得說成「已長期穩定運作」**。

### K.5 AI 揭露與授權（R-07 的落地點）

短影片使用教師數位分身時，成品須帶全片常駐的 AI 揭露標示，且教師須已簽署書面同意（P-03）。系統**不檢查也不代為取得**，但須要求教師明示確認已完成這兩項，並記錄確認時間。

**確認收在「上傳影片檔」那一步，上架前再檢查一次**（`ShortAsset.disclosure`：`aiDisclosureConfirmed`、`consentConfirmed`、`confirmedBy`、`confirmedAt`）。收在成品審核那一步會改動組員負責的審核 request 契約，連帶要改他的前端；而上傳是教師對這支影片的第一個動作，收在那裡不會晚於任何對外動作。未確認就上傳即回 `SHORT_ASSET_DISCLOSURE_REQUIRED`，publish 路徑也會再擋一次（含重試路徑）。
