## 一、核心訊息

> 我們不是一開始就規劃好全部，而是用看板把問題攤開、每週和教授檢視，**讓外部變化與測試結果決定下一步**；每一步都留下證據，也誠實標出還沒做到的地方。

評審要判斷的是「敏捷有沒有真的改善產品」。每一頁都回答：發生了什麼變化 → 我們怎麼決定 → 做了什麼 → 結果用什麼證明。

## 三、目前最薄弱的三項證據

| # | 弱點 | 影響 | 簡報策略 |
|---|---|---|---|
| 1 | **CI Gate 與自動回滾不存在**，測試只在本機跑 | Technical 30% | 放「目前做到／還沒做到」對照；把 09-09 加入的部署後健康檢查當成「已補上的一步」，CI Gate 列為下一步並說明設計（PR 觸發、跑三端測試、失敗擋合併） |

## 六、表達原則

- 不做 Notion 或 GitHub 功能介紹；工具只在證據截圖中出現。
- 每個數字標日期與範圍；447、168、14、514 不相加。
- 不說「完整 CI/CD」「全組 Sprint」「回顧會議」「正式上線」（試用是「開放學生試用」）。
- 截圖優先順序：Notion 任務原文 → GitHub PR／Actions → repo 文件。
- 成員以「組員一～四」或姓名呈現，需與 v9 一致；先解決部署負責人不一致（[07](07_資料缺口與評審追問.md) #7）。
