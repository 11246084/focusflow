## 文件分類（草稿）

這份分類用來決定內容應放在哪裡，避免規則、技術細節與歷史結果混在一起。請先依主要用途選一類，再用下表決定寫法；完整寫作要求見 [AGENTS.md](../AGENTS.md#文件寫作規則)。

| 類型 | 定義與例子 | 寫法 |
|---|---|---|
| ① 給人看 | 安裝與導覽 README、狀態、待辦、交接、架構概覽 | 完整套用寫作規則；先白話說明用途，流程附實例，進度只寫[狀態正本](current-status.md)。 |
| ② AI 指令 | AGENTS、CLAUDE、rules、skills 與 AI 設定 | 只放規則、邊界與流程；專案事實連到①或③，歷史證據連到④。JSON／YAML 等工具設定保留必要欄位與原格式，不塞進度說明。 |
| ③ 技術參考 | API 契約、功能開關、資料模型與整合流程 | 第一段白話說明用途，欄位、型別、參數與行為以精確為先；附程式依據，實作進度連到①。API 是程式互相呼叫的介面，契約是雙方約定的資料格式。 |
| ④ 歷史紀錄 | 封存原件、實作紀錄、會議原文、驗收報告與盤點快照 | 不再修改原文、日期或數字；現行文件用連結追查，不把舊結果當成目前狀態。 |
| ⑤ 交付文件 | 學校公告、系統手冊、系統簡介與競賽資料 的手冊、簡介、繳交與競賽資料 | 依對應交付要求與模板撰寫，保留版本與證據來源；交付內容不作功能狀態正本。 |

分類以主要用途判斷：學校公告、系統手冊、系統簡介與競賽資料 歸⑤，封存與歷史原文歸④；其他索引、空白模板與操作文件不因位於紀錄資料夾就當成歷史原文。程式狀態機屬③，功能完成度屬①。例：AI 指令中的「影像查詢如何運作」→ 改連③功能開關說明；「是否已驗收」→ 改連①狀態正本，原始測試結果留④。

## 文件責任

根目錄 [README](../README.md) 負責啟動導覽，[PROJECT](../PROJECT.md) 負責產品範圍，[ARCHITECTURE](../ARCHITECTURE.md) 負責穩定架構，[AGENTS](../AGENTS.md) 負責代理工作入口。技術細節仍由 [Backend](../backend/docs/)、[Pipeline](../STT_Whisper/README.md)、[Database](../database/README.md) 維護。進度與狀態只寫在狀態正本。

共用圖依種類放圖庫，手冊專用圖與原始碼同放 `05_圖庫/系統手冊/chNN/`；章節直接引用，不複製。功能規格留在功能目錄，被取代版本才封存；歷史原文與會議紀錄不改內文。

例：需要修改使用個案圖 → 從圖庫找到第 5 章原始碼 → 更新同一處成品 → 由手冊章節引用。

ESG 論文各版、投稿格式、簡報與壓縮檔在雲端「學校專題/02_競賽資料/2026永續研討會_論文投稿/」；雲端「2026永續研討會_論文初稿.docx」為原 `2026ESG_V2.docx`，不推定哪份已投稿。入口見[永續研討會 ESG 投稿](03_競賽/2026_永續研討會ESG投稿/README.md)。
