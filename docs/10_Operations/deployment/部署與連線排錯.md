# 部署與連線排錯

這份文件說明 FocusFlow 在 VM（執行服務的虛擬主機）上的部署流程與連線排錯方法，供維運時查閱。實際主機、網址、憑證與驗收結果只看[目前狀態](../../current-status.md)；排錯時以程序實際設定與 `/health` 回應為準。

## 部署流程

[部署流程設定](../../../.github/workflows/deploy.yml)在 push 到 `main` 時觸發：進入 `/opt/focusflow` 拉取程式 → 安裝後端套件 → 打包前端 → 執行 `restorecon` 還原檔案的安全標記 → 以 PM2（管理 Node.js 程序的工具）重啟後端，並讓 nginx（提供網頁與 API 轉送的伺服器）重讀設定。流程也傳入部分環境設定並做服務檢查；設定檔存在不代表部署成功。

- `.env` 不隨 Git 同步；主機上的設定檔與部署流程傳入的環境變數都要核對。
- 在主機內可用 `curl localhost:4000/health`，或由管理員「系統服務」頁呼叫 `GET /api/v1/admin/system-status`；外部 `/health` 是否轉送須核對 nginx 設定。

## Cookie 認證的部署與退回

此節是操作順序，不代表已部署或已授權寫入。依 [cookie 決策](../../04_Features/HttpOnly_Cookie/decisions.md)第 16、21 項，前後端、workflow 與 tokenVersion 必須同一次發布；11/13 前完成驗收，遵守 11/16～11/27 部署凍結。維護前一天通知所有使用者重新登入一次，記下目前正式版 commit SHA 並保留上一版 dist。

每一步由使用者明確授權或親自操作，不能由本機測試自動執行：

1. 核對目標資料庫。使用限 `focusflow.authSessions` 的 authSessionsIndexer 臨時帳號設定 `AUTH_SESSIONS_MONGODB_URI`，在 backend 執行 `npm run db:ensure-auth-sessions -- --database focusflow`。腳本先建 collection，只補缺少的 userId 與 expiresAt TTL 索引；設定衝突就停止，不刪除或重建。完成後以唯讀 MongoDB MCP 的 collection-indexes 查證。
2. 用另行授權、可建立 adminAuditLogs 的帳號設定 `AUTH_AUDIT_MONGODB_URI`，執行 `npm run db:ensure-auth-audit -- --database focusflow`。authSessionsIndexer 不包含這個集合的權限。兩個新 model 均關閉啟動時 autoCreate／autoIndex。
3. 建立獨立 `deploy-probe@focusflow.local`，role=student、isActive=true、mustChangePassword=false、emailVerifiedAt 有值，只選修探測課程；密碼使用 repo 外的隨機值雜湊，不允許人工登入。workflow 只查這個帳號、用 issueSession 發五分鐘 token，不建立或修正帳號。
4. 唯讀確認正式 `DEMO_SEED_ENABLED=false`，避免重新啟動時重建 repo 展示帳號；正式環境不要執行 `seed` 或 `seed:reset`。經授權將正式三個測試帳號改為 `focusflow115413+admin@gmail.com`、`focusflow115413+teacher@gmail.com`、`focusflow115413+student@gmail.com`，密碼換成 repo 外的值。這是正式 Atlas 寫入，不把密碼放進 workflow、指令歷史或文件。確認 SMTP 已設定、每位 admin 的真實信箱能收到信後，才開啟正式兩段式驗證。舊帳號沒有 mustChangePassword 時一律先驗證再改密碼，不跑資料遷移；正式帳號沒有驗證例外。
5. VM backend/.env 設 `CSRF_TRUSTED_ORIGINS=https://focusflow.ntub.edu.tw`，確認 `ALLOWED_ORIGINS` 明確包含正式來源、不用萬用字元；任一缺少會拒絕啟動。`ADMIN_EMAIL_2FA_ENABLED`、`EMAIL_VERIFICATION_ENABLED` 預設 true，env 是兩層開關的總開關；確認其實際值及 runtimesettings 中的 auth.* 開關，不沿用舊快照。
6. 唯讀確認 HTTP 轉 HTTPS、nginx 轉送 /api 與 /uploads，以及所有 Vite 設定來源（含 .env.production 與執行環境）沒有覆寫成絕對 API 網址。前端 build 只接受空值或 /api/v1；build 後 dist 掃描不得含 localhost、127.0.0.1 或絕對 http(s)://…/api。兩道檢查都在 PM2 重啟之前，失敗中止。
7. 在公告維護時段合併及部署。立刻執行健康檢查、部署探測，再做下列瀏覽器驗收，任一失敗啟動退回。不要只看 CI exit code 0。

正式瀏覽器驗收保留環境、時間與結果：session／pending／step-up／信任裝置 cookie 的 HttpOnly、Secure、SameSite=Strict、Path=/、無 Domain；Network 所有 API 同來源；重新整理、登入登出、所有裝置登出、admin 驗證與 first_login、step-up、上傳、頭像、回饋附件、多分頁換帳號。另實測 LINE 內建瀏覽器、Email 連結與跨站轉址進站後 /auth/me 能恢復登入。模擬另一來源送表單應拒絕，舊 JWT 與已登出的 sid 不能使用。

**緊急停用 admin 信箱兩段式驗證**：僅維運人員可在 VM 設 `ADMIN_EMAIL_2FA_ENABLED=false` 並重啟；畫面及 API 不提供安全屬性降級。這只略過 admin_2fa，不略過尚未完成的 first_login。寄信失敗不自動放行；修好 SMTP 後改回 true 並重驗。教師／學生的信箱驗證另由 EMAIL_VERIFICATION_ENABLED 控制，必要的首次改密碼仍須完成。

**退回順序不可顛倒**：先在 VM backend/.env 換新的 JWT_SECRET，再部署 revert 後的後端及保留的前端版本；確保舊版第一次啟動就讀到新密鑰，全部新舊 token 同時失效。不能先啟動不查 ver／sid 的舊版再換密鑰。新增 authSessions、tokenVersion、pendingVerification、trustedDevices 等資料保留，不為退回刪除。退回後重做健康、登入與瀏覽器流程驗收，不能用「所有人重新登入」取代驗收證據。

## 部署前檢查：YouTube 憑證權限

YouTube 上傳用的 OAuth refresh token（長期有效、用來換取短期存取權的授權碼）必須包含 `youtube.force-ssl` 權限。只有 `youtube.upload` 時仍能上傳，但管理員「YouTube 上傳管理」的「查詢 YouTube」會退回手動輸入、「確認套用」會失敗（`502 YOUTUBE_QUARANTINE_VERIFY_FAILED`），刪除影片時也無法轉成私人影片；理由見[設計決策](../../04_Features/YouTube_Lifecycle/decisions.md)「風險與授權點」。

1. 部署後先讓後端換過一次 token：完成一次上傳（例如在測試課程上傳一支影片）。剛重啟時 `credentialCheck.status` 是 `unknown`，代表這次啟動後還沒換過，看不出權限。
2. 在主機內執行 `curl localhost:4000/health`，查看 `runtime.youtubeUpload`：
   - `credentialCheck.status` 為 `ok`；
   - `credentialCheck.grantedScopes` 含 `https://www.googleapis.com/auth/youtube.force-ssl`（或涵蓋它的 `auth/youtube`）；
   - `privatizeScopeSatisfied` 為 `true`。只有 `youtube.upload` 時為 `false`，`readiness` 會變成 `degraded`。
3. 權限不足時，用頻道擁有者的 Google 帳號重新跑一次 OAuth 授權並勾選 `youtube.force-ssl`，把新的 refresh token 寫入主機 `.env` 的 `YOUTUBE_REFRESH_TOKEN`，重啟後端後回到第 1 步。

例：`grantedScopes` 只有 `.../auth/youtube.upload` → 重新授權取得含 `youtube.force-ssl` 的 refresh token → 更新 `.env` 並重啟 → 上傳一支測試影片 → `/health` 顯示 `privatizeScopeSatisfied: true`。

## 主機上操作後端（PM2 與 `.env`）

PM2 是讓後端在背景持續執行的工具。主機上的後端由 **`focusflow` 使用者**的 PM2 管理（`/home/focusflow/.pm2`），不是 root。用 root 直接下 `pm2` 會另外啟動一個空的 PM2，並顯示 `Process or Namespace focusflow-backend not found`。

- 重啟、查狀態、看日誌都加上 `sudo -u focusflow -i`，例：`sudo -u focusflow -i pm2 restart focusflow-backend --update-env`、`sudo -u focusflow -i pm2 logs focusflow-backend --lines 20 --nostream`。
- 不小心用 root 啟動了空的 PM2 時，先用 `ps -eo user,cmd | grep -i "[p]m2"` 確認有兩個 God Daemon，再以 root 執行 `pm2 kill`；它只會關掉 `/root/.pm2`，不影響網站。
- 修改後端 `.env` 的機密（例如 `SMTP_PASS`）時，不要把值寫在 `sed`、`echo` 指令裡，否則會留在 shell 歷史紀錄；改用 `nano`，或用 `read -rsp` 從畫面讀入再寫入。改完重啟後端才會生效。

例：更換 Gmail 應用程式密碼 → 以 `read -rsp` 寫入 `/opt/focusflow/backend/.env` 的 `SMTP_PASS`，確認長度為 16 → `sudo -u focusflow -i pm2 restart focusflow-backend --update-env` → 狀態為 `online`、日誌出現 `listening on port 4000`。

## nginx 與憑證

- nginx 參考位置為 `/etc/nginx/conf.d/focusflow.conf`；檢查前端檔案位置、`/api/` 轉送、`upload_size.conf` 與 `client_max_body_size`。上傳收到 413 時先核對大小限制。
- 前端是單頁應用程式，找不到的路徑會導回 `index.html`，所以 `/.env`、`/.git/config` 也會回 `200`。判斷是否外洩要看內容開頭，不看狀態碼：`curl -s https://focusflow.ntub.edu.tw/.env | head -c 15` 顯示 `<!doctype html>` 代表安全，顯示 `#`、`NODE_ENV` 或 `[core]` 代表外洩，須立即修正並更換所有金鑰。2026-10-25 檢查兩者皆為 `<!doctype html>`。
- 待辦（低優先）：在 nginx 加上 `location ~ /\. { return 404; }`，讓以 `.` 開頭的路徑直接回 404，減少掃描程式反覆試探，也防止日後誤放進 `dist` 的隱藏檔被讀取。修改後先 `nginx -t` 再重讀設定。
- 檢查 HTTPS 回應標頭時，注意 `add_header` 的繼承範圍：在 `location` 區塊自行設定後，不會沿用外層的全部標頭。
- 憑證參考位置為 `/etc/nginx/ssl/focusflow.crt`、`focusflow.key` 與 `/opt/acme.sh`，以 TLS-ALPN-01（透過加密連線驗證網域控制權）申請。操作前查閱[憑證申請與回復步驟](2026-09-10_Lets_Encrypt憑證申請紀錄.md)，核對執行帳號、續約排程及是否會暫停 nginx。

## 連線排錯

- 查 HTTP 連線用 `curl -v http://<主機>`，避免只用會自動改成 HTTPS 的瀏覽器。
- 判斷封包是否到達主機，可在授權環境用 tcpdump（封包檢查工具）觀察，先確認網卡、篩選條件及權限：

```bash
tcpdump -ni <網卡> 'tcp[tcpflags] & tcp-syn != 0 and dst host <主機IP> and (dst port 80 or dst port 443)'
```

- CORS 是限制瀏覽器跨網站請求的規則；分別用允許與不允許的來源檢查 `Access-Control-Allow-Origin` 回應，不由設定名稱推定結果。
- LINE 回報網址若使用 ngrok（把外部連線轉送到本機服務的工具），核對 `ngrok.service`、轉送目標與 LINE 平台設定；暫時網址不是固定部署網址。

例：教師上傳影片收到 413 → 檢查 `client_max_body_size` 與 `upload_size.conf` → 調整後重讀 nginx 設定 → 以同一檔案重試上傳。
