## FR01｜P1：跨行程的備份唯一歸屬仍未成立

**位置：**[youtubeQuarantine.service.js:498](../../../../backend/src/services/youtubeQuarantine.service.js#L498)、[同檔:447](../../../../backend/src/services/youtubeQuarantine.service.js#L447)；查重見 [youtubeWorkOwnership.service.js:62](../../../../backend/src/services/youtubeWorkOwnership.service.js#L62)。

**重現（真實 Mongo、兩個獨立 Node 行程）：**建立兩筆 `failed/retrySafe=false` 項目；A、B 各自呼叫 `applyQuarantinedItem`，輸入同一個 `sharedYt001`。兩邊都在 mock YouTube 驗證回覆前暫停，確定已通過查重後一起放行。Video／Video、Video／ShortAsset 兩組均得到兩次成功，DB `assigned=2`。不是兩個 Promise 共用同一個模組鎖的測試。

**影響：**至少一筆內容播放到另一份備份。新增的 `backup_in_use` 檢查會在這種已形成的重複資料上拒絕清理，這項保護有效；但不會修正錯誤綁定，不能因此判定 R06 已結案。

**最小緩解：**本機改用獨立開發 DB，或讓開發帳號對這些正式集合無寫入權，確保所有套用入口都只有指定 writer。若必須多 writer，改為兩集合共用的持久備份所有權紀錄，以 YouTube ID 原子佔用，定義驗證失敗、DB 收尾失敗及重啟恢復；不可直接在 Video 加全域唯一索引破壞匯入共用語意。

## FR02｜P1：來源版本不能保護最後查詢之後的 unlink

**位置：**[localSourceCleanup.service.js:55](../../../../backend/src/services/localSourceCleanup.service.js#L55)、[同檔:57](../../../../backend/src/services/localSourceCleanup.service.js#L57)、[同檔:63](../../../../backend/src/services/localSourceCleanup.service.js#L63)；另一入口見 [shortAsset.service.js:759](../../../../backend/src/services/shortAsset.service.js#L759)。

`verifyOwnership` 完成後還要 await cleanup 開關。此時來源／狀態只能靠行程鎖維持；`localSourceVersion` 是可換新的版本，並不是其他 writer 必須遵守的持久操作鎖。最後的 fingerprint 能看出檔案被替換，卻看不出 DB 已把同一檔案改回必須保留的草稿。

**重現（真實 Mongo、兩個獨立行程）：**A 清理 `archived/archiveReason=course_deleted` 的已備份短片，暫停在最後一次設定查詢回傳前，這時所有權／引用驗證已完成。B 用真正的 `rollbackCourseDeletionArchive` 恢復為 `draft`；放行 A。實測 DB `status=draft`，但 `sourceExists=false`，A 回 `{cleaned:true, reason:'state_write_failed'}`。最後 DB 條件拒絕收尾，發生在不可逆刪檔之後，已來不及保護來源。

**影響：**本機 backend 不必存取正式站的磁碟；只要能改同一 DB 的短片狀態，就能讓正式站在草稿仍需原片時刪檔。

**最小緩解：**將共享 DB 的來源與短片狀態寫入一併限制在同一 writer，不能只停用本機 cleanup scheduler。若維持多 writer，cleanup、restore、重處理、換代、審核及封存回復都必須遵守同一 DB 操作所有權，持有到 unlink 與收尾完成；補讀一次版本仍有新的等待空窗，不能代替互斥與失敗恢復設計。

## FR03｜P1：舊上傳可把下一代 pending 成品標成 published

**位置：**[shortAssetPublish.service.js:219](../../../../backend/src/services/shortAssetPublish.service.js#L219)、[同檔:223](../../../../backend/src/services/shortAssetPublish.service.js#L223)、[同檔:244](../../../../backend/src/services/shortAssetPublish.service.js#L244)。

上傳結果本身使用 attempt 條件更新，但後續 `markShortAssetPublished` 仍只依 `_id` 寫 `status=published`。呼叫端使用 `return markShortAssetPublished(uploaded)`，finally 會在上架 Promise 完成前釋放來源鎖；讀到的 approved／generation／非 archived 狀態也未納入最後更新條件。

**重現 A（單行程、真實 Mongo）：**第 1 代已核准，上傳回寫成功；讓 `markShortAssetPublished` 暫停在 DB 寫入前。呼叫真正的 `recordShortAssetRegeneration` 換新來源並清除 YouTube ID，會成功建立第 2 代 pending。放行舊上架，實測 `{generationVersion:2, status:'published', reviewStatus:'pending', youtubeVideoId:null}`。

**修正：**上架用條件更新同時核對 generation、該代核准狀態、非 archived 與備份／attempt 身分；不符合時不得發布或更新腳本標籤。將最後上架納入狀態互斥，並等待其完成才釋放適用鎖。單純加 `await` 可縮小換代空窗，但封存使用不同狀態鎖，仍需最後 DB 條件，不能只修語法。

## FR04｜P2：另一 backend 看不到正在傳送的工作

**位置：**[youtubeUpload.service.js:687](../../../../backend/src/services/youtubeUpload.service.js#L687)、[同檔:694](../../../../backend/src/services/youtubeUpload.service.js#L694)；短片同樣依賴 [shortAssetRecovery.service.js:130](../../../../backend/src/services/shortAssetRecovery.service.js#L130)的 `isShortAssetUploadRunning`。

`runningUploadIds`／`runningShortAssetUploads` 只記本行程。DB 隔離條件會確認同一 attempt 仍為 uploading，卻不能分辨「另一行程還活著、上傳較久」與「重啟前留下的工作」。

**重現（真實 Mongo、兩個行程）：**A 已完成一次 mock PUT 的 bytes 傳送，暫停等成功回覆。B 呼叫 recovery，測試時傳入超過 stuck 門檻的 `now`，不用任意 sleep。B 回 `quarantined=1`；A 收到成功回覆後的 owner CAS 因 status 已是 failed 而失敗。結果 session／PUT 各 1 次，DB 仍 `failed/retrySafe=false`、沒有 YouTube ID。

**影響：**已上傳的影片遺失成功映射，必須人工隔離收尾。現有保護仍會拒絕自動重傳，這個實驗沒有出現第二次 PUT；不能把誤隔離描述成已證明重複上傳。

**最小緩解：**共享 DB 只由指定 writer 執行 recovery，本機禁用 recovery 是此項的直接止血；但 FR01／FR02 還需要限制手動路由與其他寫入。多 writer 的完整修正需持久 owner／heartbeat／lease 與過期接管規則，確保活躍長上傳不被誤判；只拉長 stuck 時限無法建立保證。

## FR05｜P2：低空間刪除的失敗收尾會被空間門檻擋住

**位置：**[youtubeLifecycle.service.js:301](../../../../backend/src/services/youtubeLifecycle.service.js#L301)、[同檔:334](../../../../backend/src/services/youtubeLifecycle.service.js#L334)；恢復入口見 [video.service.js:514](../../../../backend/src/services/video.service.js#L514)。

`state_write_failed` 後沒有獨立的收尾路徑；下一輪仍先套用「是否需要低空間刪檔」。所以「下輪以缺檔補寫」只在再次滿足刪除政策時成立，不是一般的故障恢復保證。

**重現（真實 Mongo、單行程）：**最長保留設 0、最短 14 天、空間門檻 1 GiB，影片上傳已 30 天。free=0 時清理，令 unlink 成功後的 `filePath:null` 回寫只失敗一次。下一輪 free=2 GiB：`cleaned=0`，檔案已不存在，但 DB 仍保留 filePath、沒有 localCleanupAt；呼叫 restore 得 `409 VIDEO_SOURCE_RESTORE_NOT_ALLOWED`。新一輪還把 `lastError` 清成 null。

**影響：**在空間持續充足、maxAge=0 的合法設定下，永遠不會自動補寫；最長保留非 0 時也可能等到很久以後。這是 F1-T7 的恢復缺口，與 F3 的 completed 重新處理功能無關。

**修正：**將已刪檔的 DB 收尾與新的清理選擇分開，持久記錄待收尾身分，或用可驗證的來源狀態建立獨立修復掃描；修復仍須保護新來源、共用引用及跨主機檔案歸屬。不得因目前磁碟已充足就略過收尾，未解故障也不應被空輪次清除。補 maxAge=0、空間恢復、服務重啟後的案例。

## FR06｜P2：最後空間檢查之後仍隔著多次查詢

**位置：**[localSourceCleanup.service.js:52](../../../../backend/src/services/localSourceCleanup.service.js#L52)、[同檔:55](../../../../backend/src/services/localSourceCleanup.service.js#L55)；callback 見 [youtubeLifecycle.service.js:310](../../../../backend/src/services/youtubeLifecycle.service.js#L310)。

`beforeDelete` 先讀 free space，才執行 `verifyOwnership`；後者再次查 owner、兩集合的檔案引用與備份引用，之後還讀開關。資料量或 DB 延遲大時，這不是最後刪除階段的空間值。

**重現（真實 Mongo、可控制空間 provider）：**兩次 free-space 讀取均回 0；第二次完成後，在最後引用查詢期間模擬另一工作釋放空間至 2 GiB。門檻為 1 GiB、maxAge=0，仍得到 `cleaned=1`，原片消失，free-space 總共只讀兩次。

**修正：**在完成耗時的所有權／引用查詢後才做最後 low_space 決策，與最終開關檢查放在刪除末端；必要時同步取得最後 statfs 結果，避免其後再插入 DB 等待。保留 max_age 獨立處理及未知空間不按 low_space 刪除。本項不是要求對任意外部磁碟活動做到零時間差，而是移除目前明確、多次 await 的過期決策區間。

## 共享 Atlas：哪些保證仍成立

條件更新（CAS）是「只有資料仍符合讀到的條件才寫入」，不同 backend 也會由 Mongo 對同一文件原子判斷。它不會自動把一段包含 HTTP、檔案 I/O 與多份文件的流程變成單一操作。

| 保證 | 兩個 backend 共用 DB 的結果 | 證據／限制 |
|---|---|---|
| 同筆 Video／ShortAsset 的同次上傳只佔用一次 | **成立**，前提為兩邊皆使用本版條件更新 | 本輪兩個 Node 行程刻意讀到同一快照後一起 CAS，兩種類型都只有 1 session／PUT；輸家不傳送 |
| unsafe、未到期、達上限、已上傳不能由舊候選重試 | **成立** | `uploadClaimQuery` 在 DB 核對 eligibility 與 observed 欄位；新 F2-T3／T4 通過 |
| 過期 attempt 不能覆寫上傳結果 | **成立於帶 owner 條件的回寫** | status＋attemptId＋filePath／generation 防護有效；不含 FR03 的另一步上架 |
| 同一來源快照只成功換一次版本 | **成立** | 隔離 Mongo 同快照雙 claim 只有一個成功；舊 candidate 不能刪新路徑／新保留期 |
| 同一 Video 同時補回兩份、failed 同時排程兩次 | **DB 條件有保護** | restore 比對 filePath／清理時間／版本／processing；queue 以 failed 及來源版本 CAS；不等於整段檔案操作有跨行程鎖 |
| cleanup、restore、換代、審核及引用變更整段互斥 | **不成立** | 行程內 source／file／source-status 鎖；FR02 在最後驗證後突破 |
| 一個 YouTube 備份只能屬於一筆上傳內容 | **不成立** | 跨集合查重＋行程內 youtube-id 鎖；FR01 兩種配對均 2 筆成功 |
| 長上傳不被另一 scheduler 隔離 | **不成立** | running 集合不是 DB owner heartbeat；FR04 |
| 清理全域只有一輪 | **只在各自行程成立** | 本版第一個 await 前設 running，已修原單行程空窗；另一 backend 仍有另一個 running |

**最低可行措施是隔離開發 DB。** 若必須看正式資料，使用唯讀身分／唯讀模式，且本機不能啟動任何會更新來源、備份或審核狀態的入口。僅保證 PM2 一個 instance、只關本機 cleanup、只不放 YouTube token，均不足以處理全部問題；quarantine、restore、換代、封存回復不全受這些開關限制。部署限制應涵蓋所有連到相同集合的 writer，也包含舊版 backend 與外部工具；本版 token 無法約束仍用無條件更新的舊程式。

## 舊文件相容性

- `attemptId`／`localSourceVersion` 的缺欄位與明確 null 均經驗證。使用 native insert 保留真實缺欄位，沒有先用 Mongoose defaults 補成看似新版的資料。
- 本輪補驗 Video、ShortAsset 的四種「類型 × missing/null」retry 組合，皆只建立 1 session／PUT，狀態成為 uploaded 並取得新的 attemptId；接續清理成功，Video 可補回同筆記錄。現有隔離 Mongo 測試也直接覆蓋未有來源版本的 uploaded 影片清理、補回與舊候選拒絕。
- `observedField` 區分 `$exists:false` 與 `$eq:null,$exists:true`，主要 CAS 入口使用 lean；這避免將 hydration 的預設 null 當作舊 DB 實際值。不要將這些讀取改回非 lean 而不補相容驗證。
- `youtubeUpload` 整個為 null／缺欄位的首次上傳，以及舊短片略過上傳後再重試，現有真實 Mongo 測試通過；整塊 `$set` 避免在 null parent 下更新子欄位。
- 已存在的重複備份不會自動遷移；預告與清理會拒絕，保留原片。未發現新欄位缺省本身造成舊文件無法操作；此結論只限上述 fixture 與程式路徑，未盤點 Atlas 歷史資料。
