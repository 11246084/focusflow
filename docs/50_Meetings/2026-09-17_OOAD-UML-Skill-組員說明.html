01為什麼要做這個

不是為了「自動畫圖」。是因為系統手冊的圖表出過幾類反覆發生的問題，靠人記規則記不住，而且兩個 AI 工具會各畫各的。

問題

分析類別圖與設計類別圖畫顛倒

第 5-4 章畫進了 <<Service>>、ObjectId；第 6-2 章卻停在純領域概念。兩章看起來只差幾個方法。

對策

判別器 A／B —— 依章節位置自動決定套哪組檢查，不需判斷作者意圖。

問題

官方規範的連接詞被誤讀

「循序圖或通訊圖」是二選一、「狀態機甚至時序圖」是延伸、「最好以圖示說明」是建議 —— 讀錯就會多畫或漏畫。

對策

章節契約表逐條標明指定／建議延伸／禁止，並附官方原文語意對照。

問題

圖與正文、圖目錄不同步

改了 .puml 沒重新匯出；新增圖忘了更新圖目錄；圖插在那裡但正文從沒提過。

對策

Artifact chain：六個落點、七項一致性檢查，附可直接跑的指令。

問題

內部流程被寫成 Use Case

「消費處理佇列」「清除快取」變成使用個案；系統自己被畫成 Actor，系統邊界失去意義。

對策

Actor 硬規則 + 內部流程改由功能性需求（FR-xx）登錄、循序／活動／狀態機承接。

問題

舊資料被當成現況證據

拿歷屆手冊、初評舊圖來推論現在的系統長什麼樣。

對策

事實來源分五級（程式碼 > schema > 現況文件 > 既有手冊 > 歷史文件），每張圖檔頭強制標 source 與 verified 日期。

問題

兩個 AI 工具規則不一致

Claude Code 畫一套、Codex 畫另一套，風格與判準都不同。

對策

規則寫成 repo 內的純文字檔，兩邊讀同一份、路徑一致（整合方式不同，見第 07 節）。

02怎麼運作

六個步驟。重點在 Step 2 ——「選哪一種圖」不是自由發揮，而是先查官方章節契約。

STEP 1確認脈絡屬哪個 OOAD 階段？放哪一章？
STEP 2選圖兩段式：先查章節契約，再走決策樹
STEP 3該不該畫跑 pre-draw 清單（9 區）
STEP 4製圖用 templates 骨架 + PlantUML 慣例
STEP 5配套文字「用途＋判讀」；互動圖另加編號步驟
STEP 6審查五層 review，前層不過不進下層

Step 2 的兩段式選圖

這張圖是否在系統手冊脈絡中？ ├─ 是 → 查 NTUB 章節契約表 │ ├─ 該章節有「指定」圖 → 直接採用，不得以 heuristic 否決 │ ├─ 該章節有「延伸」圖 → 依價值判斷是否採用 │ └─ 該章節未指定 → 走自由決策樹 └─ 否 → 走自由決策樹
為什麼這樣設計：自由決策樹裡有「線性流程不值得畫活動圖」這類判斷。但第 5-3 章官方明文指定要用活動圖描述使用個案 —— 這時那條判斷一律不適用。指定的圖就是要畫。

層檢查什麼例子

03規則分三層，強度分四級

這是整個 Skill 最重要的設計。UML 標準、學校規範、我們的專案慣例，是三件不同的事，不能混成同一套硬規則。

適用範圍 —— 這條規則是誰的規定

UML UML 2.x 規格

違反代表圖本身是錯的。例：元件圖必須有提供／需求介面。
不可移除

OOAD 方法論共識

不同學派有差異，但主流一致。例：內部技術流程不寫成 use case。
不可移除

DOC 文件寫作通則

與 UML 無關。例：每張圖要有配套的「用途＋判讀」文字。
不可移除

NTUB 北商 115 年規範

四技部（物件導向）大綱的限制。例：圖說在圖下方、格式 圖6-1-3 名稱。
整層可移除（換學校）

FF FocusFlow 專案慣例

路徑、檔名、文件型資料庫的處理方式。
整層可移除（換專案）

為什麼要分層

移掉 local/ 兩層，這個 Skill 就變成通用 OOAD 製圖規範，其他專案能直接用。也避免有人把「北商的規定」當成「UML 的標準」去教別人。

強制程度 —— 違反了會怎樣

標記意義Review 處置例子
MUST硬性規則不通過，必須修正系統本身不得當自己的 Actor
SHOULD建議可偏離，但要說明理由設計類別標註來源分析類別
MAY允許但不建議
缺少不構成缺陷		不檢查邊界／控制／實體標註、強健性圖、CRC 卡
HEURISTIC判斷輔助不得單獨作為退回理由「循序圖協作物件少於三個」
最容易犯的錯，Skill 自己先擋掉了：把 heuristic 當硬規則。例如「狀態機的狀態要存在資料庫」不是 UML 的要求 —— 通訊協定狀態機、工作階段狀態都是合法的建模對象。持久化只是用來排序哪些狀態機最值得畫的提示。同理，套件圖不必一對一對應資料夾，元件也不等於「可熱替換」。

04分析／設計畫顛倒，現在怎麼被擋下來

核心機制叫判別器。關鍵是判別器 F：不判斷作者想畫什麼，只看圖放在哪一章節。

讀 .puml 檔頭的 chapter: 欄位 ├─ chapter: 5-4 → 套分析層檢查（判別器 A、D） └─ chapter: 6-2 → 套設計層檢查（判別器 B、D、E）

目的是避免實作洩漏，不是禁止一切形式化表達。所以訊號分兩級。

A-1 強證據 · MUST

出現任一 → FAIL。這些只可能來自特定技術棧，問題領域裡沒有對應物。

  • 技術性 stereotype：<<Service>> <<Repository>> <<DTO>>
  • 技術後綴類別名：*Service *Controller *Mapper
  • 框架／語言／資料庫型別：ObjectId Promise VARCHAR
  • 儲存細節：index unique PK FK
  • 具體技術產物命名：端點路徑、資料表名、環境變數名

A-2 弱訊號 · HEURISTIC

單獨出現不會 FAIL，只給提示。不同 OOAD 學派對分析層的形式化程度本來就有差異。

  • 屬性帶型別 name : String —— 概念型別（金額、日期）是合法的領域敘述
  • 可見性符號 + - —— 部分工具會預設輸出
  • 操作帶括號 驗證權限() —— 責任仍可能是概念層級

三項全數出現且型別是具體語言型別 → A-3 · SHOULD WARNING，要求確認。仍非自動 FAIL。

B-1 設計層責任 · MUST

設計類別圖必須呈現超越純領域概念的具體軟體設計責任，並能說明分析責任如何落實到設計。

這是語意要求，不是記法要求。判定依據：讀完圖與配套文字，能不能回答「分析層識別出的責任，在設計層由誰承擔、以什麼方式承擔」。

不通過只有一種情形：與分析類別圖在責任層級上沒有差異，且配套文字也說不出責任如何落實。那就是一張放錯章節的分析類別圖。

B-2 設計層證據 · HEURISTIC

下列是設計責任的可能表現形式，只用於提示，任何一項都不是必要條件：

  • 屬性型別、方法簽章、可見性
  • 導航方向與多重性
  • 介面或抽象型別
  • 分析層不存在的技術／協調類別
  • 類別被拆分或合併
  • 可命名的設計模式
明文禁止：不得為了通過規則而強迫製造類別、拆分結構、加註型別或套用設計模式。小型系統的設計圖與分析圖結構相近，是合理結果，不是缺陷。
判別器檢查強度
C 假分離兩圖類別集合完全相同、只差方法列 → 必須文字說明原因MUST
D 資料庫綱要冒充六項訊號命中三項以上（一類別對一集合、只有欄位、_id／createdAt⋯）→ 移到第 8 章MUST
E 來源註記每個設計類別標來源分析類別，或標「技術新增」SHOULD
F 章節即層級依 chapter: 欄位決定套哪組檢查NTUB MUST
G 物件圖層級分析物件圖 vs 設計物件圖不得畫顛倒MUST
H 成對交叉檢查物件圖實例化的類別必須出現在同章節的類別圖中MUST
只有 A-1、B-1、C、D、F、G、H 會造成 FAIL。A-2、A-3、B-2、E 不會。

05第 5、6、7 章會怎麼套用

依《115 年系統手冊規範》大學部－系統手冊大綱（物件導向）。專科部的結構化分析大綱完全不採用。

節要求強度
5-1需求清單，須分功能需求與非功能需求兩部分NTUB 指定
5-2使用個案圖（Use Case Diagram）NTUB 指定
5-3活動圖（Activity Diagram）—— 官方原文：「使用個案描述：使用活動圖描述之」NTUB 指定
5-4分析類別圖（Analysis Class Diagram）NTUB 指定
5-4分析物件圖 —— 官方用「甚至」，屬延伸NTUB 延伸
—使用個案描述表、領域模型、B/C/E 標註、詞彙表本地補充
—禁止出現：設計層內容（型別、可見性、方法簽章、技術 stereotype）、資料庫欄位禁止
5-3 特別規則：活動圖是官方指定，使用個案描述表格是補充、不是替代。只有表格而沒有活動圖，不符規範。「線性無分支流程不值得畫活動圖」這條 heuristic 在 5-3 不適用。合規基線為一個 UC 一張圖（粒度仍是 open issue）。
節要求強度
6-1循序圖 或 通訊圖 —— 官方用「或」，擇一即可NTUB 指定
6-2設計類別圖（Design Class Diagram）NTUB 指定
6-2設計物件圖 —— 官方用「甚至」，屬延伸NTUB 延伸
—使用個案實現宣告、每張互動圖的編號步驟說明本地補充
—禁止出現：同一流程同時畫循序圖與通訊圖；停留在分析層的類別圖禁止
FocusFlow 目前的第 6 章章名寫「循序圖與通訊圖」，官方是「或」。已列入待修正清單 —— 兩者擇一即可，同流程畫兩張是反模式。
節要求強度
7-1佈署圖（Deployment Diagram）NTUB 指定
7-2套件圖（Package Diagram）NTUB 指定
7-3元件圖（Component Diagram）NTUB 指定
7-4狀態機 —— 必要NTUB 指定
7-4時序圖（Timing Diagram）—— 官方用「甚至」，屬延伸NTUB 延伸

06實際開發時怎麼用

這個 Skill 最有價值的地方不是畫圖，是回答「我改了這個，哪些文件跟 UML 會失效」。

情境一　我改了程式，接下來要更新什麼？

點下面的變更類型，看它會牽動哪些章節與圖。

共通動作：任何一張圖被改動，都要重跑 artifact chain 七項一致性 —— .puml → 匯出圖檔 → 圖號 → 正文引用 → 圖目錄，一個都不能漏。

情境二　Review 別人畫的 UML

做法

直接叫 Claude Code 跑 checklists/review.md 的五層，對單張或整個章節批次審。輸出會明確標示 FAIL／WARNING／提示三級，並附規則標記與處置。

好處

不用爭論「這樣畫對不對」—— 每個結論都指向一條有編號、有適用範圍標記的規則。是 UML 標準、學校規範，還是我們自己的慣例，一看就知道。

情境三　交付前檢查

孤兒檢查

有圖沒人引用？有需求沒圖涵蓋？realizes 指向不存在的編號？

格式合規

圖說在圖下方、格式 圖6-1-3 名稱（空格、無冒號）。Markdown 轉 Word 後位置要再確認一次。

狀態盤點

所有圖的 status 是否已從 draft 推進；implemented: planned 的內容圖上有沒有標示。

情境四　新增一張圖的完整動作

1. 決定圖號 圖{章}-{節}-{序}（同節內從 1 起編） 2. 建立 .puml，填妥檔頭宣告區塊 3. title 設為圖名（必須與檔名中的名稱一致） 4. 匯出圖檔，同名 5. 章節 Markdown 插入圖 + 圖說（圖下方） 6. 正文加入至少一處「如圖…所示」 7. 圖目錄新增一列 8. AI 協助產出 → 檔頭填 ai-assisted，使其可追溯

每張圖的檔頭長這樣

' ooad-phase:   物件設計
' chapter:      6-1          ← 決定套哪組防顛倒檢查
' realizes:     UC-03, UC-04 ← 追溯鏈的錨點；填不出來代表這是孤兒圖
' source:       backend/src/services/qa.service.js（程式碼）
' verified:     2026-09-16
' status:       draft        ← 產出一律是草稿，定稿要人工確認
' implemented:  yes
' ai-assisted:  yes / Claude Code / 依循序圖規格產出骨架

事實來源分五級，衝突時取高者：程式碼與設定 > schema 定義 > 現況文件 > 既有手冊 > 歷史文件。歷屆手冊、初評舊圖、舊會議紀錄不得作為現況證據。另外分析層（5-4）禁止用反向工程從程式碼產圖 —— 那正是類別圖畫顛倒的主因。

07Claude Code 與 Codex 怎麼用

規則是 repo 內的純文字檔，兩邊讀同一份。但載入方式不一樣 —— 這點要照實說。

Claude Code

自動觸發。SKILL.md 的 frontmatter 有 name 與 description，Claude Code 會把它列為可用 skill。當你說「幫我畫第 6 章的循序圖」「這張分析類別圖對不對」，它會自行載入並依 References 路由表取用需要的檔案。

也可以直接點名：/ooad-uml-diagramming

Codex

需要明確指路。Codex 沒有同樣的 skill 自動探索機制，所以要在 prompt 裡把路徑講清楚，例如：

請先讀 .claude/skills/ooad-uml-diagramming/SKILL.md，再依其 References 路由表取用需要的 reference，然後⋯⋯

規則內容、檔案路徑、判準完全相同，差別只在誰負責把檔案叫出來。

兩邊產出的圖都會帶同樣的檔頭宣告，走同樣的五層審查。所以 Claude Code 畫的圖，Codex 可以審；反之亦然。
