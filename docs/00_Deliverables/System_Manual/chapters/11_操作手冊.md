# 第11章 操作手冊

## 11-1 系統元件與安裝

### 11-1-1 元件與執行條件

表11-1-1　系統元件與基本執行條件

| 元件 | 路徑／入口 | 技術與用途 | 基本需求 |
|---|---|---|---|
| Backend | `backend/src/server.js` | Node.js、Express、Mongoose；REST API、權限、問答、通知與處理協調 | Backend 本身以 Node.js 18+ 為基準；MongoDB；預設 port 4000 |
| Frontend | `frontend/focus-flow/src/main.jsx` | React 19、Vite 8；學生／教師一般入口與 `/admin` 管理入口 | Vite 8 要求 Node.js `^20.19.0` 或 `>=22.12.0`；開發預設 port 5173 |
| AI Pipeline | `STT_Whisper/src/main.py`、`batch_main.py` | Faster-Whisper、分段、embedding、checkpoint 與批次處理 | Python 3.10+、FFmpeg；Gemini 僅在選用真實 embedding 時需要 |
| Database tools | `database/tools/` | collection／index 建置、資料匯入與交接工具 | 執行前確認 URI、database、collection、schema 與授權；不是常駐服務 |
| 正式部署 | `/opt/focusflow`（既有 VM 紀錄） | Nginx 提供前端與反向代理，PM2 管理 Backend | Rocky Linux 9、自架 GitHub Actions runner、HTTPS 憑證 |

同一開發工作站同時建置前後端時，應採用較嚴格的 Frontend Node.js 版本下限。硬體需求會隨影片長度、Whisper model、CPU／GPU 與同時處理量改變；repo 尚無完成實測的最低硬體基準。部署前應以代表性影片量測處理時間、記憶體、磁碟暫存與上傳空間，不可把開發機規格直接當正式最低需求。

### 11-1-2 本機安裝

從專案根目錄依序建立三個執行環境。PowerShell 建議使用 `npm.cmd`，避免執行原則阻擋 `npm.ps1`。

Backend：

```powershell
Push-Location backend
npm.cmd install
if (-not (Test-Path -LiteralPath .env)) { Copy-Item .env.example .env }
Pop-Location
```

Frontend：

```powershell
Push-Location frontend\focus-flow
npm.cmd install
if (-not (Test-Path -LiteralPath .env)) { Copy-Item .env.example .env }
Pop-Location
```

AI Pipeline：

```powershell
Push-Location STT_Whisper
if (-not (Test-Path -LiteralPath .venv)) { py -3 -m venv .venv }
& .\.venv\Scripts\python.exe -m pip install --upgrade pip
& .\.venv\Scripts\python.exe -m pip install -r requirements.txt
if (-not (Test-Path -LiteralPath .env)) { Copy-Item .env.example .env }
Pop-Location
```

每段均假設起點是專案根目錄；`Push-Location`／`Pop-Location` 會在同一 PowerShell 中恢復原目錄。指令只在 `.env` 不存在時複製範本，避免重跑安裝覆寫既有設定。安裝完成後，先檢查 Node.js、Python 與 FFmpeg 是否能在目前 shell 使用，再填寫 `.env`。`.env.example` 只提供欄位與開發預設，不代表正式環境已設定；`node_modules/`、`.venv/`、`dist/`、uploads、pipeline outputs 與 log 都是環境產物，不應當成原始碼交付。

### 11-1-3 設定分類與安全邊界

表11-1-2　設定分類與維運判讀

| 類別 | 代表欄位 | 維運判讀 |
|---|---|---|
| 基礎服務 | `NODE_ENV`、`PORT`、`MONGODB_URI`、`JWT_SECRET`、`ALLOWED_ORIGINS` | 正式環境需使用獨立強密鑰；CORS 應只允許實際前端 origin |
| QA／向量檢索 | `QA_VECTOR_SEARCH_MODE`、query／answer provider、index 名稱、active embedding contract | Atlas 模式不得在 index 或資料契約不相容時靜默降級；以 `/health.runtime.qa` 為準 |
| Pipeline | input／output 目錄、Whisper、Gemini、MongoDB、processing webhook | Backend 與 Pipeline 的 webhook secret 必須一致；真實資料寫入前核對目標 collection |
| LINE | channel secret、access token、Frontend Bot URL | Webhook 必須驗簽；歷史 live smoke 不代表現行 URL／credential 仍有效 |
| YouTube／Shorts | API key、OAuth client／refresh token、upload／recovery／cleanup flags | OAuth 與上傳是外部寫入；recovery／cleanup 預設關閉，不可未審核開啟 |
| 可選功能 | `VIDEO_BATCH_PIPELINE_ENABLED`、`HIERARCHICAL_RETRIEVAL_ENABLED`、`SHORT_SCRIPT_AUTOMATION_ENABLED` | 旗標應配合資料、index、provider 與驗收證據；程式存在不等於正式啟用 |
| 郵件 | SMTP host／user／password／from | 未設定時忘記密碼會顯示不可用；不得用個人密碼取代 app password |

不應在正式環境沿用 `.env.example` 的示意 JWT 值，也不可把部署主機的 `.env` 複製進文件。交接時只列出欄位名稱、保管人、輪替日期與驗證結果；秘密值應透過核准的密碼管理或主機權限交接。

## 11-2 系統管理與部署

### 11-2-1 本機啟動與停止

MongoDB 可連線且設定完成後，在不同終端啟動 Backend 與 Frontend：

```powershell
cd backend
npm.cmd run dev
```

```powershell
cd frontend\focus-flow
npm.cmd run dev
```

Backend 自動觸發影片處理時會優先使用 `STT_Whisper/.venv/Scripts/python.exe`。手動 Pipeline 的單支、批次與 resume 指令以 [Pipeline README](../../../../STT_Whisper/README.md) 為準；手動執行 uploader、DB setup 或 seed 可能寫入資料，必須先確認目標與授權。本機停止開發服務可在對應終端按 `Ctrl+C`，停止後再確認 port 4000／5173 沒有殘留程序。

### 11-2-2 健康檢查與故障定位

Backend 啟動後先讀取：

```powershell
Invoke-RestMethod http://127.0.0.1:4000/health
```

HTTP 200 只表示 health route 有回應，還須檢查：

- `runtime.qa`：檢索模式、provider、index 設定、data contract compatibility、`readyForAsk`、warnings 與 hard failures。
- `runtime.line`：readiness、delivery mode 與缺少設定；`backend_only` 不能宣稱 LINE live reply 可用。
- `runtime.multimodal`：視覺 citation 的 collection／index 與現行接入限制。
- `runtime.shortsSync`：是否啟用、最後嘗試／成功時間及 degraded 狀態。
- `runtime.youtubeUpload`：啟用狀態、credential check、recovery／cleanup 旗標與最近錯誤。

建議故障定位順序為：確認實際進程與 port → 讀 `/health` → 檢查 PM2／Backend 結構化 log → 檢查 MongoDB／Atlas 與外部 provider → 以單一最小案例重現。不得只看 launcher PID、`.env.example` 或歷史文件就判定 runtime 正常。

常見症狀與處理：

表11-2-1　常見症狀、安全檢查與處理

| 症狀 | 優先檢查 | 安全處理 |
|---|---|---|
| Frontend 顯示無法驗證登入狀態 | Backend、API base URL、網路、`/auth/me` | 先按「重新驗證」；暫時性 5xx／斷線不應要求使用者清除 session |
| QA 無法回答 | 課程是否 published、Enrollment、可回答影片、`runtime.qa` | 先修復 readiness／資料範圍，不以 memory 或 template 冒充 Atlas／Gemini |
| 影片長時間 queued／failed | Batch item、影片 processing、Pipeline log、檔案是否仍存在 | 僅對 UI 顯示可重試的失敗執行單項 retry；避免重複建立影片 |
| LINE 不回覆 | webhook URL、簽章、channel 設定、`runtime.line` | 先做核准的 webhook verify；不要在 log 或截圖顯示 token |
| Shorts 空白 | Enrollment、課程／ShortAsset published、YouTube playable 狀態、sync snapshot | 空狀態可能是合法結果，不可繞過修課過濾直接列頻道內容 |
| YouTube 狀態不確定 | persisted `youtubeUpload`、health、YouTube Studio | 可能已送出 bytes 的錯誤不得盲目 retry，先人工確認是否已建立影片 |

### 11-2-3 正式部署流程與回滾邊界

目前 `.github/workflows/deploy.yml` 會在 `main` push 後由 self-hosted runner 於 `/opt/focusflow` 拉取程式、安裝 Backend production dependencies、建置 Frontend、修復 SELinux context、以 PM2 重啟 Backend、reload Nginx，最後檢查 Backend QA readiness 與 Nginx API proxy。這是現有自動化流程描述，不表示每次 workflow 都已成功，也不是本階段執行部署的授權。

正式部署前應留存：欲部署 commit、變更摘要、相容的 migration／index 計畫、備份識別碼、當前旗標快照、回滾 commit 與責任人。部署後至少確認：

1. PM2 的 `focusflow-backend` 為 online，沒有持續重啟。
2. VM 本機 `/health` 回應且 `runtime.qa.readyForAsk` 符合本次服務目標。
3. HTTPS 網域可載入 Frontend；`/api/v1/courses` 未帶 token 時由 Nginx 正確代理並回 401，而非 SPA HTML。
4. 以核准測試帳號完成登入與一項不造成外部寫入的 read-only smoke。
5. 若本次涉及 Atlas、Gemini、LINE、YouTube 或處理 pipeline，另依其驗收規格執行，不由一般 health 取代。

程式版本回滾應切回已知可用 commit、重建 Frontend並重啟 Backend；若變更包含 schema、index 或資料遷移，必須使用該次變更預先定義的 data rollback，不可只回退程式。憑證回滾另依 [2026-09-10 Let's Encrypt 紀錄](../../../40_Operations/deployment/2026-09-10_Lets_Encrypt憑證申請紀錄.md)；改回自簽後瀏覽器會再次警告，僅供緊急復原。該紀錄亦指出 port 80 對外仍不通，公開連結須明確使用 `https://`。

### 11-2-4 例行維運清單

表11-2-2　例行維運清單

| 頻率 | 檢查項目 | 異常時 |
|---|---|---|
| 每次部署 | commit、workflow、PM2、Nginx、`/health`、API proxy、CORS | 停止擴大驗收，依回滾計畫復原 |

| 憑證到期前 | issuer、`notAfter`、cron 與 acme.sh hook | 2026-11-15 前須確認第一次實際續約；目前只有設定存在的證據 |
| 權限異動 | VM、runner、Atlas、YouTube、LINE、SMTP 使用者 | 立即撤銷離組人員、輪替秘密並驗證服務 |

## 11-3 交付、備份與還原

### 11-3-1 交付清單

- 原始碼與 lock files，以及可對應的 commit／release 標記。
- Backend、Frontend、Pipeline 的 `.env.example`；真實秘密值另行安全交接。
- MongoDB schema／index 契約、OpenAPI、Pipeline artifact contract 與本系統手冊。
- Frontend production build 的重建指令，不以未知來源的 `dist/` 取代原始碼。
- UML／架構圖可編輯原檔、正式圖片及圖表版本紀錄。
- 測試原始輸出、題庫、旗標快照、部署與回滾證據，以及已知限制清單。

校方範本提到的 MDF／LDF 是 SQL Server 格式；FocusFlow 使用 MongoDB，不應建立空白 MDF／LDF 充數。最終交付格式應由指導老師確認為 MongoDB 可還原備份、去識別化測試資料或 Atlas backup 證據。

### 11-3-2 備份範圍與建議程序

目前 repo 未提供已完成實測的正式 `mongodump`／`mongorestore` runbook，也未保存 production 還原演練證據。下列為交付前必須定版並實測的程序，不可寫成既有正式能力：

1. 確認來源環境、database 名稱、資料 owner、保留期限與是否允許匯出個資。
2. 使用 Atlas 原生備份或權限受限的 MongoDB 備份帳號建立時間點備份；備份識別碼與 checksum 留在維運紀錄，URI／密碼不入紀錄。
3. 至少涵蓋 app-owned collections、課程／修課、影片 metadata、文字／視覺／Parent segments、對話／訊息、問答歷史、通知、ShortAsset／腳本、批次與 avatars。Pipeline 可重建 artifacts 與本地影片來源須另訂保留政策。
4. `.env`、OAuth refresh token、TLS private key 與 SMTP secret 應使用加密秘密備份，與資料庫備份分開存放並限制存取。
5. 記錄建立時間、commit、schema／embedding generation、index 定義、檔案數量與資料筆數；備份成功訊息不等於可還原。

### 11-3-3 還原與驗證

1. 預設先還原到隔離的新 database／cluster，不直接覆蓋 production。
2. 還原前核對備份來源、checksum、MongoDB 版本、目標容量與寫入授權；暫停會改寫同一資料集的服務或 job。
3. 還原後重建並確認 regular／vector indexes，核對 collection counts、代表性關聯、Enrollment 授權、影片 processing、embedding contract 與 ShortAsset 狀態。
4. 以隔離帳號執行登入、課程可見性、read-only QA citation 與管理查詢；不得在 scope 不明時呼叫真實 YouTube upload、LINE push 或 Gemini 付費流程。
5. 驗證通過且經資料 owner 核准後，才切換 Backend 的目標連線；再執行 `/health`、proxy 與角色 smoke。若失敗，停止切換並保留舊環境。
6. 還原紀錄須包含 RPO／RTO 實測值、遺漏資料、執行人與核准人，數值以實際演練結果填寫。

刪除課程或影片不是備份策略。影片刪除可能連動資料清理與將 FocusFlow 上傳的 YouTube 影片轉為 private；轉 private 後 Backend 沒有自動還原入口，需由授權人員至 YouTube Studio 處理。因此所有破壞性操作都應先確認範圍、備份及可逆性。
