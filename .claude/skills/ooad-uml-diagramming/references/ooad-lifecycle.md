# OOAD 模型生命週期

> 通用層。此檔不含 NTUB 或 FocusFlow 特例。

物件導向系統分析與設計（Object-Oriented Analysis and Design, OOAD）的五個模型與六個階段。

## 五個模型

| 模型 | 解決的問題 | 一句話判準 |
|---|---|---|
| 需求模型（Requirement Model） | 系統要為誰、做到什麼 | 講「什麼」，不講「怎麼做」 |
| 分析模型（Analysis Model） | 問題領域有哪些概念與責任 | 講「責任」，不講「技術」 |
| 設計模型（Design Model） | 由哪些物件、以什麼結構與順序完成 | 講「怎麼做」，可含技術 |
| 實作模型（Implementation Model） | 落在哪些檔案、介面與資料結構 | 講「在哪裡」 |
| 測試模型（Test Model） | 怎麼證明需求被滿足 | 講「憑什麼相信」 |

## 階段對照

| 階段 | 核心模型 | 主要產物 | 前一階段輸入 | 交給下一階段 |
|---|---|---|---|---|
| **需求分析**<br>Requirements Analysis | 需求模型 | 功能性需求（`FR-xx`）、非功能性需求（`NFR-xx`）、行為者清單、使用個案圖、使用個案描述、活動圖、系統循序圖、詞彙表 | 訪談、問卷、現況調查 | `UC-ID` + `FR/NFR-ID`；主要流程與例外流程 |
| **物件分析**<br>Object Analysis | 分析模型 | 領域模型、分析類別圖、分析物件圖、邊界／控制／實體分類、強健性圖、CRC 卡 | `UC-ID` 與使用個案描述中的名詞／動詞 | 分析類別清單（含責任與關聯） |
| **系統設計**<br>System Design | 設計模型－架構層 | 系統架構圖（非 UML）、套件圖、元件圖、佈署圖、子系統切分、技術選型記錄 | 分析類別 + `NFR-ID` | 套件／元件邊界、對外介面、佈署拓撲 |
| **物件設計**<br>Object Design | 設計模型－細節層 | 使用個案實現、循序圖、通訊圖、設計類別圖、設計物件圖、狀態機圖 | 架構邊界 + 分析類別 | 類別、屬性型別、方法簽章、狀態轉換規則 |
| **實作**<br>Implementation | 實作模型 | 元件清單與職責、檔案↔類別對映、API 規格、資料庫綱要（非 UML）、索引設計、關鍵機制虛擬碼 | 設計類別 + 狀態機 + 佈署拓撲 | 可被測試的具體元件與端點 |
| **測試**<br>Testing | 測試模型 | 測試計畫、測試層級矩陣、需求—測試追溯矩陣、測試個案與證據 | `FR/NFR/UC-ID` + 元件編號 | 驗收結論與缺口清單（回饋需求模型） |

## 依賴方向

前五階段單向細化：`需求 → 分析 → 設計 → 實作`。

測試模型橫跨全部：同時消費需求模型（驗收標準）與實作模型（被測物），把缺口回饋給需求模型。

## 兩處最常斷裂的接縫

| 接縫 | 斷裂徵狀 | 修補方式 |
|---|---|---|
| 分析 → 設計 | 分析類別消失，設計類別憑空出現 | 設計類別須註記由哪個分析類別演化，或標「技術新增」 |
| 設計 → 實作 | 循序圖的物件在元件清單找不到對應檔案 | 循序圖每條生命線須可對映到實作模型的一個元件 |

## 階段歸屬的快速判斷

問三個問題：

1. **這個東西在沒有系統的世界裡也存在嗎？** → 是：分析模型或更早
2. **換一種技術實作，它還成立嗎？** → 是：需求或分析模型；否：設計模型或更後
3. **它指向一個具體的檔案、端點或集合嗎？** → 是：實作模型

`[OOAD:HEURISTIC]` 這三問是輔助，不是判準。跨階段的產物（例如同時說明責任與技術的表格）是正常的，只要標清楚哪一段屬哪一層。
