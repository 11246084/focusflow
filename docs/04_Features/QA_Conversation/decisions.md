# 對話功能優化設計決策

這份文件記錄學生網頁版對話功能（看影片時向 AI 提問的那一欄）的優化討論：現況、和市面產品的差距、可參考的開源專案，以及逐題定案的結果。它讓接手的人或 AI 不用重讀對話就能接續；範圍、做法與第一批的細部設計都已在 2026-11-15 定案，可以開始實作；合併到 main 與部署仍須 Weihao 當次授權。功能是否完成只看[目前狀態](../../current-status.md)。

範圍只含網頁版的對話欄，不含 LINE 對話、檢索方法（見[多模態檢索](../Multimodal_Retrieval/decisions.md)）與播放器章節（見[學生端播放介面](../Student_Player_UX/decisions.md)）。

## 名詞

- **串流輸出**：回答邊產生邊顯示，不是等整段寫完才一次出現。
- **追問**：依賴前文才看得懂的問題，例如上一題問「什麼是監督式學習」，下一題問「那它的缺點呢」。
- **追問改寫**：檢索前先把追問補成完整的問題，例如把「那它的缺點呢」改成「監督式學習的缺點是什麼」。
- **FAQ 快取**：相似的問題已經答過時，直接回傳之前的回答，不再呼叫模型。

## 和市面產品的差距

比較對象是通用聊天產品（ChatGPT、Gemini、Claude）與資料或影片問答產品（NotebookLM、Perplexity、YouTube 影片問答、Coursera Coach）。這部分依 Claude 既有的了解整理，沒有逐一查證各產品的最新版本；要引用到報告或系統手冊前須先查證。

依對使用感受的影響排序：

1. 沒有串流輸出。
2. 追問改寫靠規則，沒涵蓋的說法（例如「再講詳細一點」「舉個例子」）會被當成獨立問題去檢索。
3. 系統不知道學生正在看哪支影片的哪一秒，答不出「剛剛這段在講什麼」。
4. 回答的操作少：不能複製、評分、對成功的回答重新產生、編輯問題或中止。
5. 沒有範例問題與建議追問。
6. 輸入框不能換行。
7. 對話不能改名、刪除、搜尋。
8. 回答不支援表格、程式碼區塊與公式。

「點來源直接跳到影片那一秒」是通用聊天產品沒有的，屬於本系統的特色，優化時保留。

### 兩個會影響排程的限制

1. **改提示詞或回傳格式的項目，需要 Gemini 可用才能驗證。** 這類變更可能讓原本答得好的題目變差，上線前要用[問答品質評測](../QA_Evaluation/README.md)的題庫重跑比較。目前 Gemini 專案達每月花費上限，無法執行。這類變更還要同步檢查 FAQ 快取命中路徑與 LINE（兩者共用同一套回答流程）。
2. **回答目前不能真的逐字串流。** 模型回傳的是一整包 JSON，要等整包回來才能解析出回答文字與引用。要逐字顯示就得改變回答的產生方式，屬於上面第 1 類。進度提示不受這個限制。

### Claude 的評估

全部項目無法在一天內做完並驗證。寫程式本身也許趕得完，但改提示詞的項目卡在 Gemini 無法驗證，硬上線有讓回答品質變差而沒人發現的風險。建議依「要不要改提示詞」切成兩批（已定案，見第 6 項）。

## 行內互動元件的參考：ChatGPT 的 Intelligent UI（2026-11-15 查詢）

Weihao 指定行內互動元件參考 ChatGPT 的 Intelligent UI。它是 OpenAI 在 2026-10-07 隨 GPT-6 推出的回答方式：回答可以混合文字、圖表、可點的按鈕、表單與互動內容，版面由模型依問題決定，簡單的問題仍然只回文字。OpenAI 的官方頁面在查詢環境連不上，這段依搜尋結果對官方說明頁與 [Search Engine Journal 報導](https://www.searchenginejournal.com/chatgpt-gpt-6-intelligent-ui/592249/)的摘要整理。

開源仿作有兩個（見上表）。它們的共同做法是：**先定義一組固定的元件，模型只能從中挑選與排列，前端負責畫出來**。兩者的差別在自由度：Thesys 的版本以固定元件為主；CopilotKit 的版本還允許模型直接寫 HTML 與 JavaScript，放在隔離的 iframe 裡執行。

套用到本專案有三種做法：

| 做法 | 內容 | 優點 | 缺點 |
|---|---|---|---|
| A. 自訂區塊 | 在現有回答的 JSON 多加一個 `blocks` 欄位，模型從少數幾種區塊挑選（例如比較表、步驟、小測驗、選擇題、建議追問）；前端自己寫這幾種元件；`answer` 欄位保留純文字版 | 沿用現有的回答流程；Gemini 會保證 JSON 格式正確；LINE 與 FAQ 快取繼續用純文字版；不加新套件 | 元件要自己寫；回答仍是整段出現，不能邊產生邊畫 |
| B. 引入 OpenUI | 模型改輸出 OpenUI Lang，前端用它的函式庫畫 | 可以邊產生邊畫；元件種類多 | 回答格式整個換掉，引用來源、FAQ 快取、LINE、答不出來的處理都要重做；Gemini 寫 OpenUI Lang 的正確率、能否用在 Vite 都還沒查證 |
| C. 整套搬仿作 | 直接採用其中一個仿作 | — | 兩個都是 Next.js，其中一個還要 Python 後端，和本專案架構不合 |

不論哪一種，**不執行模型產生的 HTML 或 JavaScript**：這是給學生用的系統，模型的輸出會受課程內容與學生提問影響，直接執行有被注入惡意內容的風險。

#### 第 15 項：進度提示 API 的形式

**決策**：

- 新增 `POST /conversations/:conversationId/messages/stream`，一個請求直接回 SSE，不採 LibreChat 的兩段式。原本的 API 保留。
- 後端建立好這一題的兩則訊息後，先送一個 `accepted` 事件，帶使用者訊息與助理訊息的 ID。前端收到就確定後端已受理。
- 進度步驟只有兩個：`searching`（搜尋課程片段）與 `writing`（撰寫回答），都不帶數字。FAQ 快取命中時不送步驟或只送 `searching`，接著直接送 `done`。
- 錯誤分三種情況：①開始回答前就被擋下的（額度用完、字數超過、沒有權限），照現在回一般的 HTTP 錯誤，前端現有的處理可以沿用；②回答產生失敗，送 `done` 且內容帶 `failed: true`，和現有 API 一致；③標頭送出後的非預期錯誤，由這條路由自己攔截並送 `error` 事件。
- `done` 的內容是現有 API 的完整回應（含 `success`、`message`、`data`）。
- 後端用一個選填的回呼參數把步驟通知傳進問答流程，沒有傳就不做事，LINE 不受影響。
- 每 15 秒送一行保持連線的註解。
- 前端在 `api.js` 新增串流用的函式，沿用既有的標頭、cookie 與登入過期處理，頁面裡不直接呼叫 `fetch`。
- 這條路由的回應不經過共用的成功／錯誤回應函式，在 [API 設計規則](../../../.claude/rules/api-design.md)與 OpenAPI 註明為例外，OpenAPI 的回應類型寫 `text/event-stream`。

**理由**：兩個步驟都對應實際花時間的工作（檢索、模型撰寫），不會出現瞬間閃過的假步驟。`done` 與現有回應相同，前端收到後的處理可以完全沿用；測試比對兩條 API 時先排除訊息 ID、時間戳與延遲數字。

例：學生送出「什麼是過擬合」→ 依序收到 `accepted`、`stage: searching`、`stage: writing`、`done`（回答與來源）。

測試要另寫一個讀取 SSE 的輔助函式，現有的測試工具只會把回應當成 JSON 讀。

**上線前要在 VM 確認的事**（需要 Weihao 執行，Claude 無法連 VM）：用 `nginx -T` 檢查 `gzip_types` 是否包含 `text/event-stream`、`/api/` 是否設了 `proxy_cache`、是否忽略 `X-Accel-*` 標頭。任何一項成立，進度提示都會被累積到最後才出現。

#### 第 16 項：學生中途離開或連線失敗時怎麼處理

**決策**：

- 開始回答前，後端先建立一則狀態為 `pending` 的助理訊息；回答完成或失敗時更新同一則。訊息內容是必填欄位，`pending` 期間放一段固定的佔位文字，前端看到 `pending` 就畫等待畫面、不顯示這段文字。組對話歷史時排除 `pending` 的訊息。
- 瀏覽器斷線後，後端仍把回答做完並更新訊息。
- 前端載入對話時看到 `pending` 的訊息，就顯示等待畫面並每隔幾秒重新讀取，直到它變成完成或失敗。
- `pending` 訊息的最後更新時間超過 2 分鐘就視為中斷（例如後端在回答途中被重啟），顯示「重新產生」按鈕。
- 重試 API 放寬為接受兩種情況：上述中斷的 `pending` 訊息，以及建立超過 2 分鐘仍沒有任何回覆的使用者訊息。重試開始前先做一次**帶條件的更新**來佔位：只有「狀態是 `pending` 而且最後更新時間早於 2 分鐘前」才更新成功，同時把最後更新時間改成現在；更新不成功就回 409，不執行回答。
- 連線失敗時不重送問題。已經收到 `accepted` 事件的，直接依其中的訊息 ID 定時重新讀取對話，照上面的 `pending` 規則處理。還沒收到 `accepted` 的，重新讀取對話，看送出前最後一則已知訊息之後有沒有新的使用者訊息：有，照 `pending` 規則處理；沒有，才把問題放回輸入框讓學生自己再送。
- 重新讀取也失敗時（網路整個斷掉），顯示「連線中斷，正在重試」，每隔幾秒再試，不清掉學生的問題。
- 只有新路由回 404 或 405（代表後端還是舊版）時，才自動改用現有 API。
- 第一批不提供中止按鈕。

**理由**：重送的風險是同一題扣兩次額度，而每日只有 5 次。用「對話裡有沒有這一題」來判斷後端收到了沒，不需要新增資料庫欄位與索引（新增索引屬於 Shared Atlas 的索引變更，要另外授權）。帶條件的更新是為了避免兩種互撞：原本的回答其實只是慢、還在執行，或學生連按兩次重試；沒有它，同一題會產生兩筆提問紀錄並扣兩次額度。它用的是訊息既有的欄位，不需要新索引。2 分鐘的依據：查詢向量最多 8 秒三次、回答最多 20 秒兩次，合計約 65 秒，再留資料庫查詢的餘裕；資料庫在 Atlas 上的實際耗時沒有量過，實作時要再確認。

**已知的殘餘風險**：連線失敗後立刻重新讀取時，請求可能還在路上、訊息尚未建立，學生再送一次就會重複。發生機率低，第一批接受；之後若要根治，再加上由前端產生的請求識別碼。另一個殘餘風險：原本的回答若超過 2 分鐘仍在執行，學生按了重試後，原本那次完成時仍會寫入並多記一筆提問。

#### 第 17 項：「問目前這段」怎麼運作

**決策**：

- 只有按「這段在講什麼」按鈕才會使用播放位置。按鈕送出時附上範圍標記（`scope: "current_segment"`）與目前的影片、秒數。學生自己打字的問題一律照現在的方式處理，第一批不從文字判斷。
- 新舊兩條 API 都接受這組欄位。
- 「有播放位置」的定義：學生已選定影片，而且播放器回報得出秒數；暫停中也算。前端要新增接線，讓對話欄能向 YouTube 播放器與本機播放器取得目前秒數。
- 建立訊息之前，後端先做一次**片段預檢**：把前端傳來的影片對到這門課已授權的影片清單，對不到就當作沒有播放位置；對得到，就只讀那一支影片的片段（不讀向量欄位），篩出目前秒數前後各 60 秒內的片段，涵蓋目前秒數的那一段排第一。不用前端傳來的影片代碼直接查資料庫。篩到的片段直接交給問答流程，不再重查。
- 這條路徑不做追問改寫、不做向量搜尋、不讀不寫 FAQ 快取；每日額度檢查照常執行。
- 預檢篩不到片段時，回一般的錯誤（新的錯誤碼，要補進 [API 設計規則](../../../.claude/rules/api-design.md)的錯誤碼表），前端顯示「這個位置沒有可用的課程內容」。不留訊息、不扣額度，也不退回整門課檢索。前端不把「這段在講什麼」放回輸入框。
- 影片還沒處理完成時，前端不顯示這顆按鈕。
- Gemini 撰寫失敗時，這條路徑不退回樣板回答，記為失敗、不扣額度。做法是在回答產生函式加一個選填參數，一般提問與 LINE 不傳就維持現況。測試環境把回答來源設成樣板時，樣板就是正常回答，不受這條規則影響。
- 問答紀錄與診斷資訊標明這一題是依播放位置取片段。

**理由**：按鈕是明確的訊號，不會誤判；指示詞的判斷留到有真實提問資料後再評估。預檢放在建立訊息之前，是因為現有流程先建立使用者訊息、之後才載入課程片段，不提前就做不到「不留訊息」。預檢沿用現有的課程權限與影片範圍檢查，依影片查片段已有索引，不需要新增。樣板回答只會引用第一段逐字稿，對「這段在講什麼」沒有幫助，卻會扣掉一次額度；Gemini 不可用時學生每按一次就損失一次，所以這條路徑改為失敗不扣。篩不到片段也是同樣的道理：現有流程把「沒有可回答的內容」算成一次提問，學生在片頭或沒人說話的段落按一下就會少一次，而且根本沒有呼叫模型，所以改成事先擋下。前後 60 秒是起始值，實作後用真實影片調整。

**要先知道的影響**：這類提問不會產生查詢向量。短影片自動選題會用提問的向量做分群，所以這些題目不會被算進去。

#### 第 18 項：開場建議問題

**決策**：空白的新對話顯示最多 3 顆按鈕：

1. 「這段在講什麼」（有播放位置才顯示，走第 17 項的路徑）
2. 「這門課主要在教什麼？」
3. 「這門課有哪些重要的名詞？」

後兩題照一般提問處理，會讀寫 FAQ 快取；三題都照常扣每日額度。學生送出第一個問題後按鈕消失。用常見問題當建議的做法移到「之後再評估」，條件是先有教師審核或隱藏的機制。

**理由**：常見問題存的是學生的原始輸入，可能含人名或不當用語，目前也沒有任何畫面公開顯示過它們；直接放到每位同學的開場畫面有隱私風險。另外它的次數欄位只在快取命中時增加，新問題是 0，而且課程影片一重新處理就全部清空，實際上常常湊不滿 3 題。固定的後兩題以整門課為對象，第一位學生問過之後，其他人點選大多會命中快取，回答快也不花模型費用。

**要寫進實作說明的限制**：對話已有歷史時 FAQ 快取會停用，所以建議按鈕只能出現在空白對話；日後若要搬到對話中途，快取的好處就不成立。課程有影片還在做多模態處理時快取也會停用。

**上線前要實測的風險**：「這門課主要在教什麼？」是總結型的問題，檢索只取最相關的 15 段，模型可能回答資料不足。答不出來的回覆不會進快取，卻會扣額度，等於每位學生點一次扣一次。Gemini 可用後先在真實課程實測這兩題；答不出來就換題目，換好之前這兩顆不上線。

#### 第 19 項：來源時間軸的顯示條件

**決策**：

- 回答引用 2 個以上、而且來自同一支影片的片段時，在來源清單上方畫一條時間軸，標出各片段的位置，點擊跳轉。
- 影片長度取自前端已有的影片清單；該影片沒有長度資料時不畫時間軸，只顯示現有的來源清單。
- 時間軸畫出全部來源，包含來源清單預設收合起來的那些。
- 來源跨多支影片時，每支符合條件的影片各畫一條，最多 3 條。

**理由**：只有一個來源時時間軸沒有額外資訊。沒有長度就不畫，是避免用猜的長度畫出位置錯誤的標記。這項不改後端。

#### 第 20 項：第一批的順序與一天的預期

**決策**：第一批的順序為：①複製回答 → ②多行輸入 → ③開場建議的兩題固定題 → ④進度提示（含第 16 項的 `pending` 訊息） → ⑤問目前這段與它的按鈕 → ⑥來源時間軸 → ⑦語音輸入 → ⑧朗讀回答。

驗收①改成「至少 2 個」的原因：第③項上線時只有兩題固定題，「這段在講什麼」要等第⑤項；第⑤項上線後，沒有播放位置時也只有兩顆。依第 18 項的實測結果，這兩題也可能延後上線，那時第③項就跟著順延。

**理由**：審查指出最可能超時的是「問目前這段」，它要同時改問答核心流程、兩條 API 的契約、兩種播放器的接線與測試。把它排在進度提示之後，前四項做完就已經可以單獨上線。語音輸入移到後面，是因為後端回應帶有禁止使用麥克風的標頭（[安全標頭](../../../backend/src/middleware/securityHeaders.middleware.js)），前端頁面由 nginx 提供，是否也帶同樣的標頭要先在 VM 確認；若有，要先調整才能用麥克風。

預期：一天內完成①～④的把握較高，⑤很可能需要第二天，⑥～⑧視剩餘時間。
