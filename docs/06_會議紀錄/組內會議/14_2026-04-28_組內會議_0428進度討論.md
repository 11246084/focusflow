- 會議日期: 2026-04-28
- 會議時間: Notion 未記載
- 會議類型: 組內會議（進度討論）
- 與會者: 邱偉豪、張庭語、鍾百陶、張家瑜

## 討論內容

1. 期末報告與 Demo 策略

- 背景：期末展示需要降低現場網路、伺服器延遲及突發錯誤造成的風險。
- 內容：
  - 優先將完整系統操作流程預錄成影片並嵌入簡報。
  - 現場仍準備可執行系統的筆電；若評審要求實際操作，再提供 Live Demo、QR Code 或行動裝置體驗。
  - Demo 先確保主要成功流程可以穩定呈現，不在短時間內投入過多資源處理極端情況。
- 結論傾向：以預錄 Demo 為主要展示方式，Live Demo 作為備援與評審互動方案。

2. 系統架構、影片流程與環境變數

- 背景：團隊檢視學生端、網頁前端、後端 API、資料庫及影片處理之間的關係。
- 內容：
  - 教師上傳影片後，由後端接收，再交由影片託管與 AI 分析、Embedding 流程處理。
  - API Key 與金鑰等敏感資訊必須放在 `.env`，不得硬編碼在程式碼中。
  - 會議比較 Gemini、OpenAI 與 Claude 的適用情境，並討論多模態需求、Token 限制及成本。
- 結論傾向：簡報需清楚說明技術選擇的原因，程式設定則以環境變數集中管理。

3. 角色權限與 GitHub 開發流程

- 背景：系統需要區分管理員、教師與學生；同時，多人直接在 `main` 開發可能造成衝突。
- 內容：
  - 管理後台應與學生、教師前台分開，後續再依時間補強登入驗證、加密與權限控制。
  - GitHub 可採個人分支開發，並指定熟悉架構的成員處理合併與衝突。
  - 分支流程不是硬性規定，團隊可依實際協作效率決定，但需確保 `main` 維持可執行。
- 結論傾向：先跑通核心流程，同時建立不易互相覆蓋的版本控制方式。

4. 期末簡報與書面報告分工

- 背景：期末審查需要同步準備簡報與完整書面文件。
- 內容：
  - 簡報需包含系統架構、Demo 影片、模型選擇理由與 API 流程。
  - 書面文件需整理架構細節、技術堆疊、設計理念與開發過程。
- 結論傾向：簡報與書面文件分開負責，簡報初稿於下週二前完成。

## 決議事項

1. 期末展示以預錄系統 Demo 為主，現場可執行環境作為備援。
2. API Key、金鑰及其他敏感設定統一放入 `.env`，不得硬編碼。
3. GitHub 開發可使用個人分支並指定合併負責人，確保 `main` 維持可執行。
4. 期末產出分為簡報與書面文件兩條工作線，依分工同步推進。
5. 短期優先完成可順暢展示的核心流程，安全與極端錯誤處理依剩餘時間補強。
