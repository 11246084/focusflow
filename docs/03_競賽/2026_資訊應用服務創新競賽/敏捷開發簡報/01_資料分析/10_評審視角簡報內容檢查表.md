## 逐題檢查

欄位：①評審為什麼可能問 ②已有證據 ③不足 ④建議回答 ⑤處理方式

### Q1 為什麼選 Kanban，不選 Scrum？

1. 鈦坦自己用 Scrum，評審想確認選擇有理由。
2. 【事實】附件 3：整體 Kanban、特定模組短週期迭代；Notion 08-17 自我審查頁指出「全組 Sprint」說法不準確並改寫；3～4 月每次教授檢視都調整方向。
3. 【待團隊確認】選擇理由（課業時間安排不固定、需求隨每週檢視調整）沒有書面決策紀錄。
4. 團隊確認前，只描述做法：「我們的需求常在每週教授檢視後調整，所以用看板讓工作隨時可見、隨時重排；需要反覆驗證的 AI 模組，在模組內做短週期實驗。」團隊確認後，才加上理由。
5. **正文第 3 頁**。

### Q2 看板真的影響工作管理，還是只是任務清單？

1. 鈦坦對 Kanban 的定義包含「發現瓶頸並改善」。
2. 【事實】會議行動項目直接連到任務卡（08-04 連 13 張）；任務卡寫逐日進度與「不可誤稱」；09-18 內部測試清單的項目在 10-23 變成看板任務。
3. 沒有 WIP 限制、沒有瓶頸分析紀錄；43% 任務沒有負責人；123 張中 92 張封存，沒有實際完成日。
4. 強調看板串接「決策 → 工作 → 回報」；被問到 WIP 或瓶頸時，照實說目前沒有，列為改善方向。
5. **正文第 4 頁**；WIP、封存、負責人空白留口答。

### Q3 每週教授檢視如何影響下一階段的開發決策？

1. 評審想確認檢視會議會產生決策，而不只是報告進度。
2. 【事實】教授會議 28 次有決議欄：03-31 放棄寵物機制、06-16 改為老師上傳自動轉 YouTube、08-04 提出模型停用風險、09-10 凍結新功能並啟動班級測試。
3. 會議決議與後續 commit 之間沒有直接連結，需人工對照。
4. 舉「會議決議 → 隔週做了什麼」的例子：08-04 → 08-09 程式切換；09-10 → 09-21 開放學生試用。
5. **正文第 3、5 頁**。

### Q4 需求變更有沒有前後對照紀錄？

1. 學術評審重視可驗證的變更紀錄。
2. 【事實】08-25「試用版建議」：組員 11 條意見逐條回應，YouTube 上傳與 LINE 多輪從「有餘力再做」改為「本輪必做」；規格 v1.0 → v1.1 → v1.2 有 commit；複評 12 題有後續處理總表。
3. 這些多為**團隊內部建議**與**教授／評審意見**；學生試用回饋沒有對照紀錄。
4. 用「來源／原本／改成」三欄表，明確標出回饋來源。
5. **正文第 7 頁**。

### Q5 技術問題如何轉化為開發任務？

1. 評審想看問題是否進入工作流程。
2. 【事實】案例 A：報告記錄風險 → 會議決策 → 08-07 任務卡；09-18 內部測試清單 → 10-23 任務卡標「來源：系統測試問題清單」。
3. 沒有 GitHub Issue；Notion 到 GitHub 是單向連結。
4. 「問題先記在 Notion（報告或清單），決定處理就開看板任務並寫來源。」
5. **正文第 5 頁**（案例 A 的「決策 → 開始處理」）。

### Q6 測試結果是否真的影響下一輪迭代？

1. 這是判斷「有沒有依回饋調整」的核心。
2. 【事實】baseline 人工複核把問題分成程式、題目、搜尋三類，並寫明「依 baseline 調整，但不得放寬課程隔離」；09-02～09-06 依序修正問答契約、建立評測工具、做 8 輪檢索診斷再整合。另：09-09 正式問答驗證第一次失敗、同日修正。
3. 調整後的正式驗收證據尚未建立。
4. 用案例 B 的四步（暴露問題 → 分析來源 → 不放寬標準 → 多輪調整）回答；重點是**依原因決定怎麼改**，不是展示通過率。
5. **正文第 6 頁**。

### Q7 5 天完成模型遷移的證據是否完整？

1. 產業評審會懷疑「5 天」是否只挑了好看的區間，或把部署說成全部完成。
2. 【事實】分四段：
   - 外部公告：最早可能停用日 08-10（公告發布日【待確認】）。
   - 團隊發現：08-02 最早紀錄（報告、PR #5）；08-04 會議決策；08-07 開任務。
   - 程式切換：08-09 PR #6 合併並自動部署、Pipeline 同日完成、371 項測試通過。
   - 正式完成：09-09 資料重建、部署加資料契約檢查、正式問答驗證（第一次失敗後修正）。
3. PR #6 建立後 1.5 分鐘合併，**沒有審查紀錄**；PR 自承未做 Gemini 真實連線、正式資料庫驗證與資料重建；08 月是否評估其他模型【待確認】。
4. 「會議決定後 5 天完成程式切換並部署；正式環境的資料重建與驗證在一個月後的 09-09 完成，部署流程也因此加入檢查。」不說 Code Review，不說 08-09 全部完成。
5. **正文第 5 頁**同時標 08-09 與 09-09；**備用頁 B1** 放完整表。

### Q8 案例 B 的測試結果是否具有可信度？

1. 學術評審會問題目、標準、是否同一批題目、有沒有原始紀錄。
2. 【事實】baseline（09-01）四類證據齊全：題庫、設定快照、原始結果、人工複核；結果 0 PASS／11 WEAK／3 FAIL；PASS／WEAK／FAIL 有書面定義；複核分工（一人審正確性、一人審引用與時間點）。
3. 【事實】調整後的結果只有 commit `915dcf1` 訊息記載 13 PASS／1 WEAK／0 FAIL（09-06），Q09 已改寫，沒有原始結果檔與複核表；依團隊自己的證據規則不算驗收；剩下 1 題 WEAK【待確認】。
4. 正文只講 baseline 與改善過程；被問到「改善後多少」時回答：「有一次整合驗證記錄在 commit，但原始結果沒有存檔、其中一題題目也依教材修正過，依我們自己的規則不能算正式驗收，正式驗收證據還在補。」
5. 正文**不放** 13／14；**備用頁 B3** 標「非正式整合驗證紀錄」。

### Q9 GitHub commit 集中在一位成員，如何說明團隊協作？

1. 評審會懷疑是一人專案。
2. 【事實】commit 483／149／44／24；專案面板依模組設負責人；案例 A 的 Pipeline commit 由另一位組員完成；案例 B 人工複核由兩人分工。
3. 部署負責人在附件 3、Notion、GitHub 三處不一致【待確認】；會議紀錄、文件、測試等非程式工作沒有統一統計。
4. 承認分布不均，說明整合與部署集中、各模組有負責人，舉案例中其他組員的實際貢獻；不用 commit 數證明平均分工。
5. **備用頁 B4**；正文不放 commit 數。

### Q10 AI 輔助產生的程式碼由誰審查、整合與驗證？

1. 分支名 `codex/*` 與文件都顯示大量使用 AI 工具。
2. 【事實】03-24 會議定「ChatGPT 規劃 → Codex 實作」並要求說明 AI 與人為貢獻的分界；04-24 全組任務「理解初評階段 AI 生成的程式碼」；decisions.md 每項寫組員同意日期；測試與正式驗收由組員執行。
3. PR #6 等 PR 沒有審查紀錄；cookie 案例的「獨立審查」是組員還是 AI 工作階段【待確認】。
4. 「需求、完成條件與設計決策由組員定案並寫理由；AI 依工作說明實作；組員跑測試並做正式驗收。」**不宣稱每個 PR 都有人工審查**；把「合併前至少一位組員審查」列為改善項。
5. **備用頁 B5**；正文第 10 頁列改善項。

### Q11 沒有 GitHub Issue，如何證明需求追蹤？

1. 產業界習慣 Issue → PR 的追蹤方式。
2. 【事實】需求與缺陷在 Notion 看板；進度報告附 PR、commit、Actions 連結（案例 A）。
3. 單向連結，commit 不寫任務編號。
4. 「需求追蹤在 Notion 看板，目前由 Notion 單向連到 GitHub；下一步讓 commit 回寫任務編號。」
5. **正文第 10 頁**列改善項；細節口答。

### Q12 CI 關卡尚未完整建置，如何誠實說明？

2. 【事實】deploy.yml：push main 自動部署；09-09 起部署後健康檢查；10-24 起部署前同來源檢查；155 次執行、148 成功。
3. 沒有自動測試關卡、沒有自動回滾、沒有 PR 觸發。

5. **正文第 9、10 頁主動說明**。

### Q14（新增）你們說的「回饋」是誰的回饋？

1. 評審可能把「組員建議」或「評審意見」誤解為使用者回饋，進而追問使用者數據。
2. 【事實】三類來源：
   - 團隊內部建議：08-25 試用版建議（11 條）、09-18 內部系統測試清單（團隊以示範帳號測試）、08-17 附件 3 自我審查。
   - 教授／評審意見：教授會議 28 次、10-22 複評 12 題。
   - 實際學生試用回饋：09-21 開放試用、09-22 上線「回報問題」功能。
3. 學生試用的人數、回饋內容與依回饋修改的項目都沒有整理【待確認】。初評前的需求調查問卷（系統手冊附錄）屬開發前的需求調查，不是試用回饋。
4. 依來源分開講；學生試用只講機制與現況，不說「使用者回饋改變了產品」。
5. **正文第 7 頁**三欄呈現。
