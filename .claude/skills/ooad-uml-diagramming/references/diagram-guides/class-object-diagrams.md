# 靜態結構指南：類別圖與物件圖

## 先固定抽象層級

- **領域模型**：問題領域概念與關係，不含系統技術責任。
- **分析類別圖**：由需求與使用個案推導系統責任；不得反向工程實作細節。
- **設計類別圖**：由目前設計／程式碼驗證類別、介面、操作與協作責任。
- **物件圖**：上述某一層在特定時間點、特定情境下的實例快照。

完整防顛倒規則仍以 `../analysis-vs-design.md` 為準。

## 類別納入準則

只納入至少符合一項的類別：承擔 diagram brief 的責任、保存情境所需狀態、定義協作契約、或是理解關係不可缺少的領域概念。工具函式、框架基類與無關欄位通常不納入。

## 關係語意

| 關係 | 使用時機 | 常見錯誤 |
|---|---|---|
| Association | 結構上持有或可導航到另一類別 | 把一次方法參數也畫成永久關聯 |
| Dependency | 暫時使用對方的型別、操作或契約 | 所有呼叫都升格為 association |
| Composition | 整體控制部件生命週期，部件不可合理獨立存在 | 只因資料庫有內嵌欄位就使用 |
| Aggregation | 有共享整體／部分語意且確實需要空心菱形 | 當作一般「has-a」預設箭頭 |
| Generalization | 子型別符合 is-a，能替代父型別 | 只為共用欄位而繼承 |
| Realization | 類別實作介面契約 | 介面只是同名類別，沒有契約證據 |

- `[UML:MUST]` association／aggregation／composition 標示可由證據支持的多重性；未知時先查證，不猜精確數字。
- `[OOAD:MUST]` 設計操作應能與重要循序圖訊息或介面契約對照。
- `[DOC:SHOULD]` 屬性只保留會影響責任、狀態或關係判讀者，不把 schema 全欄位抄成類別圖。

## 物件圖

- `[UML:MUST]` 使用 `實例名 : 類別名` 並給出與情境相關的槽位值。
- `[OOAD:MUST]` 實例化的類別與連結必須存在於同層級類別圖；實例值不得與該情境矛盾。
- `[DOC:MUST]` 在圖說寫明時間點、前置狀態與本快照要證明的設計關係。
- 不把物件圖畫成「類別圖去掉 methods」；沒有具體值與情境就不成立。

## Review questions

1. 這是領域、分析、設計還是 instance snapshot？是否混層？
2. 每個類別是否真的承擔本圖問題中的責任？
3. 關係種類、方向與多重性是否有語意與證據，而不是視覺偏好？
4. 設計操作能否被循序訊息、介面或程式碼支持？
5. 物件快照是否能由同章類別圖合法實例化？
