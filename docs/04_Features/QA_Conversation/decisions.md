# 對話功能優化設計決策

這份文件記錄學生網頁版對話功能（看影片時向 AI 提問的那一欄）的優化討論：現況、和市面產品的差距、可參考的開源專案，以及逐題定案的結果。它讓接手的人或 AI 不用重讀對話就能接續；範圍與做法已在 2026-11-15 定案，細部設計的題目待下一輪提出。功能是否完成只看[目前狀態](../../current-status.md)。

範圍只含網頁版的對話欄，不含 LINE 對話、檢索方法（見[多模態檢索](../Multimodal_Retrieval/decisions.md)）與播放器章節（見[學生端播放介面](../Student_Player_UX/decisions.md)）。

## 名詞

- **串流輸出**：回答邊產生邊顯示，不是等整段寫完才一次出現。
- **追問**：依賴前文才看得懂的問題，例如上一題問「什麼是監督式學習」，下一題問「那它的缺點呢」。
- **追問改寫**：檢索前先把追問補成完整的問題，例如把「那它的缺點呢」改成「監督式學習的缺點是什麼」。
- **FAQ 快取**：相似的問題已經答過時，直接回傳之前的回答，不再呼叫模型。

## 和市面產品的差距

比較對象是通用聊天產品（ChatGPT、Gemini、Claude）與資料或影片問答產品（NotebookLM、Perplexity、YouTube 影片問答、Coursera Coach）。這部分依 Claude 既有的了解整理，沒有逐一查證各產品的最新版本；要引用到報告或系統手冊前須先查證。

依對使用感受的影響排序：

1. 沒有串流輸出。
2. 追問改寫靠規則，沒涵蓋的說法（例如「再講詳細一點」「舉個例子」）會被當成獨立問題去檢索。
3. 系統不知道學生正在看哪支影片的哪一秒，答不出「剛剛這段在講什麼」。
4. 回答的操作少：不能複製、評分、對成功的回答重新產生、編輯問題或中止。
5. 沒有範例問題與建議追問。
6. 輸入框不能換行。
7. 對話不能改名、刪除、搜尋。
8. 回答不支援表格、程式碼區塊與公式。

「點來源直接跳到影片那一秒」是通用聊天產品沒有的，屬於本系統的特色，優化時保留。

## 2026-11-15 新增的目標（Weihao）

Weihao 希望用**一天**把對話功能優化完，範圍除了上面列的差距，還要具備三類能力。下表把每一類換成這個系統裡具體可做的東西，並標出要不要改回答的提示詞（給模型的指示）或回傳格式。

| 能力 | 在本系統的具體做法 | 改提示詞或回傳格式 |
|---|---|---|
| 行內互動元件 | **來源時間軸**：回答引用多個片段時，在回答下方畫一條可點擊的時間軸 | 否，用現有的來源資料 |
| 行內互動元件 | **小測驗卡**：學生要求出題時，回答變成可以作答的選擇題 | 是 |
| 多模態輸入 | **語音輸入**：按麥克風說話，轉成文字填入輸入框（瀏覽器內建功能） | 否 |
| 多模態輸入 | **問目前這段**：送出問題時帶上正在播放的影片與秒數；另加一顆「這段在講什麼」按鈕 | 否，只影響檢索範圍 |
| 多模態輸入 | **上傳圖片或截圖提問** | 是，而且要新增上傳與圖片理解的費用 |
| 多模態輸出 | **朗讀回答**（瀏覽器內建功能）；影片片段跳轉已經有 | 否 |
| 猜你想問（開場） | 顯示這門課最常被問的幾題（用現有的常見問題 API），沒有資料時顯示固定的通用題 | 否 |
| 猜你想問（回覆後） | 在同一次回答呼叫多回傳一個「建議追問」欄位，不多呼叫一次模型 | 是 |
| 問題模糊時先確認 | 在同一次回答呼叫讓模型可以改回傳「選擇題」，學生點選後再回答 | 是 |
| 進度提示 | 後端在每個實際步驟完成時通知前端：理解問題 → 搜尋課程片段 → 找到 N 個片段 → 撰寫回答 | 否，但要新增一條會持續傳送事件的 API |

### 兩個會影響排程的限制

1. **改提示詞或回傳格式的項目，需要 Gemini 可用才能驗證。** 這類變更可能讓原本答得好的題目變差，上線前要用[問答品質評測](../QA_Evaluation/README.md)的題庫重跑比較。目前 Gemini 專案達每月花費上限，無法執行。這類變更還要同步檢查 FAQ 快取命中路徑與 LINE（兩者共用同一套回答流程）。
2. **回答目前不能真的逐字串流。** 模型回傳的是一整包 JSON，要等整包回來才能解析出回答文字與引用。要逐字顯示就得改變回答的產生方式，屬於上面第 1 類。進度提示不受這個限制。

### Claude 的評估

全部項目無法在一天內做完並驗證。寫程式本身也許趕得完，但改提示詞的項目卡在 Gemini 無法驗證，硬上線有讓回答品質變差而沒人發現的風險。建議依「要不要改提示詞」切成兩批，見 Q1。

## 行內互動元件的參考：ChatGPT 的 Intelligent UI（2026-11-15 查詢）

Weihao 指定行內互動元件參考 ChatGPT 的 Intelligent UI。它是 OpenAI 在 2026-10-07 隨 GPT-6 推出的回答方式：回答可以混合文字、圖表、可點的按鈕、表單與互動內容，版面由模型依問題決定，簡單的問題仍然只回文字。OpenAI 的官方頁面在查詢環境連不上，這段依搜尋結果對官方說明頁與 [Search Engine Journal 報導](https://www.searchenginejournal.com/chatgpt-gpt-6-intelligent-ui/592249/)的摘要整理。

開源仿作有兩個（見上表）。它們的共同做法是：**先定義一組固定的元件，模型只能從中挑選與排列，前端負責畫出來**。兩者的差別在自由度：Thesys 的版本以固定元件為主；CopilotKit 的版本還允許模型直接寫 HTML 與 JavaScript，放在隔離的 iframe 裡執行。

套用到本專案有三種做法：

| 做法 | 內容 | 優點 | 缺點 |
|---|---|---|---|
| A. 自訂區塊 | 在現有回答的 JSON 多加一個 `blocks` 欄位，模型從少數幾種區塊挑選（例如比較表、步驟、小測驗、選擇題、建議追問）；前端自己寫這幾種元件；`answer` 欄位保留純文字版 | 沿用現有的回答流程；Gemini 會保證 JSON 格式正確；LINE 與 FAQ 快取繼續用純文字版；不加新套件 | 元件要自己寫；回答仍是整段出現，不能邊產生邊畫 |
| B. 引入 OpenUI | 模型改輸出 OpenUI Lang，前端用它的函式庫畫 | 可以邊產生邊畫；元件種類多 | 回答格式整個換掉，引用來源、FAQ 快取、LINE、答不出來的處理都要重做；Gemini 寫 OpenUI Lang 的正確率、能否用在 Vite 都還沒查證 |
| C. 整套搬仿作 | 直接採用其中一個仿作 | — | 兩個都是 Next.js，其中一個還要 Python 後端，和本專案架構不合 |

不論哪一種，**不執行模型產生的 HTML 或 JavaScript**：這是給學生用的系統，模型的輸出會受課程內容與學生提問影響，直接執行有被注入惡意內容的風險。

| 10 | SSE 的連線、中止與錯誤處理以 LibreChat 為參考，凍結期間由 Claude 唯讀研究；不引入 Vercel AI SDK | 架構最接近。回答產生已經自己呼叫 Gemini，引入 AI SDK 等於換掉這一層 |

| 12 | 語音輸入與朗讀用瀏覽器內建功能，不經過後端、不用付費語音服務；瀏覽器不支援時不顯示按鈕。實作時實測各瀏覽器的支援程度；若錄音會送到瀏覽器廠商的伺服器辨識，介面上加一句說明 | 不增加費用，也不用新增後端 |
| 13 | 問題模糊時，由模型在同一次回答呼叫判斷要不要先確認；最多確認一次，選項最多 4 個並附「都不是，我自己說明」。確認那次不扣每日額度、不存進 FAQ 快取；LINE 維持現況 | 不多花一次模型費用。限制一次避免學生被連續反問；每日只有 5 次，確認被扣會讓學生不敢問 |

## 目前這一輪待答題目

第二輪：第一批的細部設計。SSE 的題目依 [LibreChat SSE 研究](evidence/2026-11-15_librechat-sse-research.md)提出。五種區塊的欄位定義屬於第二批，等 Gemini 可用、開始第二批前再問。

### Q8：進度提示 API 的形式

**問題**：是否新增 `POST /conversations/:conversationId/messages/stream`，一個請求直接回 SSE，不採 LibreChat 的兩段式？

**建議答案**：是。事件有三種：`stage`（進度，內容是步驟代碼與選填的數字，例如 `{ "step": "retrieved", "count": 6 }`）、`done`（內容和現有 API 的回應完全相同）、`error`（內容和現有的錯誤格式相同）。每 15 秒送一行保持連線的註解。前端用 `fetch` 讀取資料流，不加新套件。

**理由**：本專案一題只呼叫一次模型，不需要斷線續傳，兩段式要多管理一套背景工作狀態。`done` 與現有回應相同，前端收到後的處理可以完全沿用，測試也能直接比對兩條 API 的結果一致。

例：學生送出「什麼是過擬合」→ 依序收到 `stage: understanding`、`stage: searching`、`stage: retrieved（6）`、`stage: writing`、`done`（回答與來源）。

### Q9：學生中途離開或連線失敗時怎麼處理

**問題**：是否採「瀏覽器斷線後，後端仍把回答做完並存進對話；第一批不提供中止按鈕；SSE 連不上時前端自動改用現有 API」？

**建議答案**：是。學生重新打開對話時，從對話紀錄看到那一題的回答。

**理由**：提問額度已扣、模型費用已花，回答應該保留。中止按鈕牽涉額度要不要退，留到之後。自動退回現有 API 讓正式站的 nginx 設定萬一不適合 SSE 時，學生仍然能提問，只是看不到進度。

### Q10：「問目前這段」怎麼運作

**問題**：是否採下面的規則？

**建議答案**：是。

- 前端每次送出問題都附上目前播放的影片與秒數（沒有在播放就不附）。
- 後端只在兩種情況使用它：學生按了「這段在講什麼」按鈕，或問題裡有「這段、這裡、剛剛、現在、目前」這類指示詞。其他問題照現在的方式檢索整門課。
- 使用時，直接取目前秒數前後各 60 秒內的片段當作來源，不做向量搜尋；取不到片段時退回一般檢索。
- 這類回答不讀也不寫 FAQ 快取。

**理由**：一般問題如果也限定在目前位置，會漏掉其他影片裡更好的答案。「這段在講什麼」的答案取決於播放位置，不同學生問同一句話應該得到不同回答，所以不能進快取。直接依時間取片段不需要查詢向量；但撰寫回答仍然要呼叫 Gemini，花費上限解決前只能用模擬回答驗證。前後 60 秒是起始值，實作後用真實影片調整。

### Q11：開場建議問題的顯示規則

**問題**：是否採「空白的新對話顯示最多 3 題，依被問次數由高到低；常見問題不足 3 題時用通用題補滿；有影片正在播放時，第一顆固定是『這段在講什麼』」？

**建議答案**：是。學生送出第一個問題後建議就消失，不在對話中途再出現（回覆後的建議追問屬於第二批）。

**理由**：三題以內不會把輸入框往下擠太多。把「這段在講什麼」放第一顆，是讓學生第一眼就發現系統知道他看到哪裡，這是本系統和通用聊天產品最大的差別。

### Q12：來源時間軸的顯示條件

**問題**：是否採「回答引用 2 個以上、而且來自同一支影片的片段時，在來源清單上方多畫一條時間軸，標出各片段的位置，點擊跳轉；其他情況只顯示現有的來源清單」？

**建議答案**：是。來源跨多支影片時，每支影片各畫一條，最多 3 條。

**理由**：只有一個來源時時間軸沒有額外資訊。時間軸用現有的來源資料就能畫，不改後端。
