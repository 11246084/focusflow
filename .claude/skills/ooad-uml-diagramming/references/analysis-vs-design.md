# 分析類別圖 vs 設計類別圖：防顛倒判別器

> 通用層（判別器 A–E、G、H）+ NTUB 層（判別器 F）。
> 這是本 skill 最需要機器可檢查的部分。已知失效模式：兩張圖畫顛倒。

## 先確認層級

| | 分析類別圖（Analysis Class Diagram） | 設計類別圖（Design Class Diagram） |
|---|---|---|
| 回答 | 問題領域有哪些**責任** | 這些責任由哪些**程式類別**實現 |
| 屬性 | 概念名稱，**無型別** | 有型別、有可見性 |
| 操作 | 責任敘述（「驗證提問權限」） | 方法簽章（含參數與回傳型別） |
| 技術詞彙 | **禁止** | **應該**出現，並標註設計模式 |
| 類別數量 | 較少，聚焦核心概念 | 較多，含輔助類別 |
| 一對一？ | **不是**。可拆可併 | — |

---

## 判別器 A：分析類別圖的實作洩漏

判別的目的是**避免實作洩漏（implementation leakage）**，不是禁止一切形式化表達。
因此訊號分兩級，強度不同，處置也不同。

### A-1　強證據 `[OOAD:MUST]`

出現任一即判定為實作洩漏，必須移除或移至設計類別圖。這些訊號只可能來自特定技術棧，
在問題領域中沒有對應物。

| 訊號 | 偵測方式 | 範例 |
|---|---|---|
| 技術性 stereotype | `<<...>>` 屬技術詞彙 | `<<Service>>` `<<Repository>>` `<<DTO>>` `<<Controller>>` `<<Schema>>` `<<Component>>` |
| 技術後綴類別名 | 類別名結尾 | `*Service` `*Repository` `*Controller` `*DTO` `*Model` `*Mapper` `*Factory` `*Adapter` `*Handler` |
| 框架／語言／資料庫型別 | 出現於屬性或參數 | `Promise` `Buffer` `Optional` `List<>` `Map<>` `ObjectId` `UUID` `VARCHAR` `JSONB` |
| 儲存與持久化細節 | 屬性註記 | `index` `unique` `sparse` `default` `nullable` `PK` `FK` |
| 具體技術產物命名 | 類別或屬性名 | 端點路徑、資料表名、環境變數名、套件名 |

### A-2　弱訊號 `[OOAD:HEURISTIC]`

**單獨出現不構成 FAIL**。形式化的型別與操作表達在分析層仍可能是合理的抽象敘述，
不同 OOAD 學派對分析層的形式化程度本就有差異。

| 訊號 | 範例 | 為何不是硬規則 |
|---|---|---|
| 屬性帶型別標註 | `name : String` | 概念型別（`金額`、`日期`）是合法的領域敘述 |
| 可見性符號 | `+ 驗證權限` | 部分工具預設輸出可見性，未必代表設計意圖 |
| 操作帶括號 | `驗證提問權限()` | 責任仍可能是概念層級，只是寫成了操作形式 |

處置：輸出提示，不阻擋。
> 提示：這張圖使用了型別／可見性／操作記法。若這些仍屬概念層級的抽象敘述，請在圖說說明。

### A-3　合併證據 `[OOAD:SHOULD]`

A-2 的三項弱訊號**全數出現**，且型別為具體語言型別而非概念型別 → 列為 WARNING，
要求確認是否已跨入設計層。仍非自動 FAIL。

### 允許出現

概念屬性名、概念型別、責任敘述（動詞片語）、關聯與多重性、繼承、
分析層 stereotype（`<<boundary>>` `<<control>>` `<<entity>>`，若專案採用）。

## 判別器 B：設計類別圖的層級檢查

### B-1　設計層責任 `[OOAD:MUST]`

> 設計類別圖必須呈現**超越純領域概念的具體軟體設計責任**，並能說明
> **分析責任（analysis responsibility）如何落實到設計**。

這是一條**語意**要求，不是記法要求。判定依據是：閱讀這張圖與其配套文字後，
能否回答「分析層識別出的責任，在設計層由誰承擔、以什麼方式承擔」。

**不要求任何特定記法存在。** 型別標註、方法簽章、可見性、導航方向、介面、
技術類別 —— 這些都是設計層責任的**可能表現形式**，任何一項都**不是**必要條件。
一張以其他方式清楚表達設計責任的圖同樣通過。

不通過的情形只有一種：這張圖與分析類別圖在**責任層級上沒有差異**，且配套文字
也無法說明分析責任如何落實到設計。此時它是一張放錯章節的分析類別圖。

> 與判別器 E 的分工：B-1 是**圖層級**的 `MUST`（整張圖能否說明責任落實）；
> E 是**逐類別**的 `SHOULD`（每個類別標註來源分析類別或「技術新增」）。
> E 是達成 B-1 的常見做法之一，不是唯一做法。

### B-2　設計層證據 `[OOAD:HEURISTIC]`

下列是設計層責任的常見表現形式，用於**提示與排序**，**不是通過條件**，
也**不要求其中任何一項必須存在**：

1. 屬性帶型別標註
2. 方法簽章
3. 可見性符號
4. 關聯標註導航方向與多重性
5. 出現介面（interface）或抽象型別
6. 出現分析層不存在的技術／協調類別
7. 分析類別被拆成多個，或多個被合併
8. 套用可命名的設計模式並在圖上標註

> `[OOAD:MUST]` **不得為了通過規則而強迫製造類別、拆分結構、加註型別或套用設計模式。**
> 一個小型系統的設計類別圖與分析類別圖結構相近，是合理的結果，不是缺陷。
> 若各項證據皆不明顯，僅輸出提示，由作者判斷是否需要細化。

處置：
> 提示：這張設計類別圖與分析層的結構差異不明顯。若系統規模本就如此，請在圖說說明；
> 若尚未完成物件設計，可考慮檢視責任分派。

## 判別器 C：假分離偵測

`[OOAD:MUST]` 若分析與設計兩圖的**類別集合完全相同**（名稱與數量一致），且唯一差異是設計圖多了方法列：

- **不自動退回**（小型系統可能確實如此）
- 但**必須**在圖說以文字說明「為何設計層未產生任何結構變化」
- 無說明 → 不通過

檢查方式：抽出兩張圖的類別名稱集合，比對是否完全相同。

---

## 判別器 D：資料庫綱要冒充類別圖

`[OOAD:MUST]` 同時出現下列**三項以上**即判定為資料庫綱要，必須移出類別圖、改置於資料庫設計章節。

- [ ] 每個「類別」與一個集合／資料表一一對應，無多無少
- [ ] 完全沒有操作，只有欄位
- [ ] 出現 `_id` `__v` `createdAt` `updatedAt` 等儲存層產物
- [ ] 關聯全部是「存一個 ID」而非物件參考
- [ ] 完全沒有繼承、沒有多型
- [ ] 出現資料庫特有型別名（`ObjectId` `VARCHAR` `TINYINT` `JSONB` `BSON`）

**關鍵差異**：設計類別圖建模「記憶體中的物件與行為」，資料庫綱要建模「持久化的資料結構」。
兩者**不是**一對一：一個類別可跨多個集合，一個集合也可只是某類別的一部分；
非持久化的控制類別、服務類別不會出現在資料庫綱要中。

---

## 判別器 E：來源註記

`[OOAD:SHOULD]` 設計類別圖的每個類別須可回答「你由哪個分析類別演化而來，或是純技術新增」。

純技術新增是**正當的**，但必須標示（可用 note 或圖說表格），不得靜默出現。

---

## 判別器 F：章節位置即層級宣告

`[NTUB:MUST]` 在系統手冊脈絡中，**不需判斷作者意圖，只看圖放在哪一章節**：

| 位置 | 層級 | 套用檢查 |
|---|---|---|
| 5-4 的任何類別圖／物件圖 | 分析層 | 判別器 A、D |
| 6-2 的任何類別圖／物件圖 | 設計層 | 判別器 B、D、E |
| 兩者皆有 | — | 判別器 C、H |

這條規則讓檢查可完全自動化：讀圖源檔頭的 `chapter:` 欄位即可決定套哪組規則。

---

## 判別器 G：物件圖的層級

`[OOAD:MUST]` 物件圖同樣會被畫顛倒。

| | 分析物件圖（Analysis Object Diagram） | 設計物件圖（Design Object Diagram） |
|---|---|---|
| 槽位值 | 概念層級的例子值 | 具體型別的真實值 |
| 出現的類別 | 僅分析類別 | 可含技術／協調類別 |
| 連結 | 概念關聯的實例 | 具導航方向的參考 |
| 用途 | 說明複雜領域關係的具體樣貌 | 說明某執行時點的物件配置 |

分析物件圖套用判別器 A（同樣分強證據與弱訊號）；設計物件圖套用判別器 B-1（須能說明
它在展示哪個設計層情境，而非僅為領域概念的實例）。

---

## 判別器 H：成對圖的交叉檢查

`[OOAD:MUST]` 若 5-4 與 6-2 都繪製了類別圖與物件圖，檢查四張圖的層級一致性：

- 5-4 的物件圖**不得**實例化只在 6-2 出現的類別
- 6-2 的物件圖**不得**只實例化分析類別（那代表設計層沒有新增任何東西）
- 5-4 物件圖的類別必須全部出現在 5-4 類別圖中
- 6-2 物件圖的類別必須全部出現在 6-2 類別圖中

---

## 執行順序

```
1. 讀圖源檔頭 `chapter:` 欄位 → 判別器 F 決定層級
2. 分析層 → 判別器 A-1（強證據，FAIL）
            → 判別器 A-2/A-3（弱訊號，提示或 WARNING）
            → 判別器 D（資料庫綱要）
   設計層 → 判別器 B-1（設計層責任，FAIL）
            → 判別器 B-2（設計層證據，僅提示）
            → 判別器 D → 判別器 E（來源註記）
3. 若兩張都存在 → 判別器 C（假分離）
4. 若有物件圖 → 判別器 G、H
```

只有 A-1、B-1、C、D、F、G、H 會造成 FAIL。A-2、A-3、B-2、E 不會。

## 提示級訊號（不得單獨退圖）

`[OOAD:HEURISTIC]`

- 設計類別圖與分析類別圖呈 1:1 對應，是可疑訊號，但在小型系統可能合理 → 觸發判別器 C 的說明要求即可
- 分析類別圖若採用 B/C/E，三類數量嚴重失衡可能代表責任分析不足 → 僅提示
- 設計類別圖類別數少於分析類別圖，通常代表過度簡化 → 僅提示
