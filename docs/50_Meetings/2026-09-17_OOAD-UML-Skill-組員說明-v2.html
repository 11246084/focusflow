03UML 規則分層，強度分級

這些成熟規則仍由 ooad-uml-diagramming 擁有。UML 標準、學校規範、專案慣例是不同來源，Orchestrator 不會另寫一套。

適用範圍 —— 這條規則是誰的規定

UML UML 2.x 規格

違反代表圖本身是錯的。例：元件圖必須有提供／需求介面。
不可移除

OOAD 方法論共識

不同學派可有差異。例：內部技術流程不寫成 use case。
不可移除

DOC 文件寫作通則

與 UML 無關。例：每張圖要有「用途＋判讀」配套文字。
不可移除

NTUB 北商 115 年規範

大學部物件導向大綱。例：圖說在圖下，格式 圖6-1-3 名稱。
換場景可整層移除

FF FocusFlow 專案慣例

專案路徑、檔名、文件型資料庫與現況證據的處理方式。
換專案可整層移除

單一規則來源

Orchestrator 只負責路由與整合，不複製 UML 規則。完整定義仍以 Specialist 的 references/ 為權威來源。

強制程度 —— 違反了會怎樣

標記意義Review 處置例子
MUST硬性規則不通過，必須修正系統本身不得當自己的 Actor
SHOULD建議可偏離，但要說明理由設計類別標註來源分析類別
MAY允許但不建議；缺少不構成缺陷不檢查邊界／控制／實體標註、強健性圖、CRC 卡
HEURISTIC判斷輔助不得單獨作為退回理由「循序圖協作物件少於三個」
最重要的界線：heuristic 只能提示，不得否決官方指定圖，也不得偽裝成 MUST。狀態是否持久化、套件是否一對一對應資料夾，都不能單獨成為退回理由。

04分析／設計類別圖防顛倒

這組判別器繼續由 UML Specialist 執行。關鍵是：不猜作者想畫什麼，先看圖放在哪一章。

讀 .puml 檔頭的 chapter: 欄位 ├─ chapter: 5-4 → 套分析層檢查（判別器 A、D） └─ chapter: 6-2 → 套設計層檢查（判別器 B、D、E）

A-1 強證據 · MUST

出現任一 → FAIL。這些只可能來自特定技術棧，問題領域裡沒有對應物。

  • 技術性 stereotype：<<Service>> <<Repository>> <<DTO>>
  • 技術後綴：*Service *Controller *Mapper
  • 框架／語言／資料庫型別：ObjectId Promise VARCHAR
  • 儲存細節：index unique PK FK
  • 端點路徑、資料表名、環境變數名等技術產物

A-2 弱訊號 · HEURISTIC

單獨出現不會 FAIL，只給提示。不同 OOAD 學派對分析層形式化程度本來就有差異。

  • 屬性帶型別 name : String
  • 可見性符號 + -
  • 操作帶括號 驗證權限()

三項全數出現且型別是具體語言型別 → A-3 · SHOULD WARNING，仍非自動 FAIL。

B-1 設計層責任 · MUST

設計類別圖必須呈現超越純領域概念的具體軟體設計責任，並能說明分析責任如何落實到設計。

這是語意要求，不是特定記法要求。只有圖與文字都說不出責任如何落實，才是不通過。

B-2 設計層證據 · HEURISTIC

型別、方法簽章、導航方向、介面、技術類別、拆分／合併與設計模式，都只是可能證據，不是必要條件。

禁止為通過規則造假：不得強迫製造類別、拆分結構、加型別或硬套設計模式。
判別器檢查強度
C 假分離兩圖類別集合完全相同、只差方法列 → 必須文字說明原因MUST
D 資料庫綱要冒充一類別對一集合、只有欄位、_id／createdAt 等訊號命中三項以上 → 移到第 8 章MUST
E 來源註記每個設計類別標來源分析類別，或標「技術新增」SHOULD
F 章節即層級依 chapter: 決定套哪組檢查NTUB MUST
G 物件圖層級分析物件圖 vs 設計物件圖不得畫顛倒MUST
H 成對交叉檢查物件圖實例化的類別必須出現在同章節類別圖MUST
只有 A-1、B-1、C、D、F、G、H 會造成 FAIL。A-2、A-3、B-2、E 不會。

06實際開發怎麼用：直接說文件目標

平常從 project-documentation 開始，不必先替工作分類成哪一種 UML。語句裡的動詞會決定模式，也會決定是否能修改檔案。

PLAN · 先盤點與規劃
「我要開始做第五章，該從哪裡開始？」

Orchestrator 先查第五章契約、現有章節、圖表與證據，回覆缺口與順序；不因為看到 UML 就直接開始畫。

CREATE · 盤點後完成
「根據目前專案幫我完成第五章。」

先確認現況與 Source of Truth，再完成獲准範圍。需要 UML 時才由 Specialist 執行 pre-draw、製圖與 review。

REVIEW · 診斷，不偷改
「我覺得這張圖好像不太對。」

先定位圖、章節契約與來源證據，再跑五層 review；只提出問題時，不會默默改成實作任務。

DISCUSS · 保持唯讀
「先跟我討論這章怎麼做，不要直接修改。」

保留 Discuss 模式，只說選項、取捨與建議，不修改章節、圖片、PlantUML 或程式碼。

Source of Truth 與盤點結果

先看目前事實

現行程式碼、route、schema、測試與 runtime 證據優先；舊圖、歷屆手冊與會議紀錄只是輸入，不是實作證明。

先分類再動手

既有產物會被分成：核對後可沿用、需要修正、缺少、選配。不是用圖的數量湊完整。

保留工作模式

Discuss／Plan 到盤點與規劃為止；Create／Modify 才繼續產出。Review 不會自動變成修改。

UML artifact chain 仍由 Specialist 把關

.puml 母稿 ↓ 同名匯出 圖檔 ↓ 編號與標題一致 圖號／圖說 ↓ 正文至少一次指名引用 章節正文 ↓ 名稱、路徑、編號一致 圖表目錄 ↓ 回到 Orchestrator 整合整章與回報缺口
每次改圖都重跑七項一致性：.puml、匯出圖檔、圖號、標題、圖說位置、正文引用、圖表目錄。生成成功不代表整條 artifact chain 已完成。

每張 UML 圖的追溯檔頭

' ooad-phase:   物件設計
' chapter:      6-1
' realizes:     UC-03, UC-04
' source:       backend/src/services/qa.service.js（程式碼）
' verified:     2026-09-17
' status:       draft
' implemented:  yes
' ai-assisted:  yes / 依循序圖規格產出骨架

直接叫 UML Specialist：保留，但降級使用

Specialist

已知圖種、章節、證據與輸出目標，且只需要專門製圖時，可直接點名。

Debug

正在除錯 PlantUML 語法、樣式、圖號或 artifact chain 的單點問題時使用。

Review

要依五層 review 批次審查既有 UML，且不需要整章盤點與整合時使用。

不是正常起點：「我要整理第五章／第六章」這種整章文件目標，不應直接跳到 ooad-uml-diagramming。否則 Specialist 看不到非 UML 缺口、文件模式與整合責任。
