# 第13章 感想

## 13-1 個人心得

鍾百陶：這學期我手上同時抓著兩條線：一條是系統架構和AI 問答的主流程，另一條是整組的進度。初評結束後，影片自動上傳YouTube、短影音腳本的自動生成與審核上架、忘記密碼和登入鎖定、學生每日提問上限，都陸續落到我這邊。正式網域的HTTPS 憑證、上線前的問答檢查，還有系統手冊複評版的第1～3 章，也是我負責的。

讓我印象最深的，是七月那次測試。我們準備了一批需要跨片段歸納的問題，結果AI 幾乎每一題都回「資料不足」。一開始我以為是模型不夠聰明，追下去才發現問題出在我們自己身上：每次只挑3 個片段丟給模型，一整門課將近6,700 字的逐字稿，真正被拿來回答的不到200 字。這就像請人讀完一本書的心得，卻只給他看封底的簡介，怎麼可能答得好？片段數調到15 之後，情況好了很多。可是「好了很多」到底是多少？光憑感覺說不清楚，所以八月我們建了一份50 題的固定題庫，事實題、跨片段歸納題和教材裡根本沒有答案的題目都放進去，請人逐題評分。第一輪（8/24）拿到4.35 分（滿分5），我依評分時抓到的「答不完整」和「不該拒答卻拒答」修改prompt，第二輪（9/3）升到4.68，兩輪都沒有出現編造教材以外內容的情形。題目一多，重複提問的成本也跟著冒出來，我們就和庭語一起做了FAQ 快取。

不過我得老實說，這個分數只代表那份題庫、那次設定下的表現，還不算正式驗收。第10 章裡「課程問答與來源片段」這一項，目前也還沒完成人工實測。短影音的情況類似：到9 月25 日為止，系統產生了5 份腳本，3 份通過教師審核，2 支短片已經上架，但第10 章裡短影片的選題、送審和審核流程，都還列在待測清單上。

憑證那一關則是另一種頭痛。學校不開放port 80，大家最常用的certbot 根本驗證不了網域。卡了一陣子，最後改用acme.sh 走443 埠做TLS-ALPN-01 驗證，總算拿到Let's Encrypt 的正式憑證，也設好了自動續約的排程。至於續約是不是真的會自己完成，要等11 月第一次到期前才知道，到時候我會再盯一次。

說起來，這段經驗改變了我對RAG 的想像。我原本以為答案好不好主要看模型，實際做下來才發現，檢索幾個片段、prompt 怎麼寫、快取什麼時候該清掉，每一樣都會直接反映在答案上。當組長也讓我學到一件事：模組之間的介面得在分工時就講清楚，每週教授會議前也最好先對過一次進度。不然前端、後端、Pipeline 各自做完，湊在一起才發現接不起來，那種感覺真的很洩氣。

系統還有地方可以再磨。現在改了設定、模型或prompt，FAQ 快取不會自己失效，得靠人手動清除；或許可以把設定版本也放進快取鍵裡。至於短影音，我會傾向先把第10 章的流程測完、多收一些老師的審核回饋，再決定要不要把自動化的範圍放大。

邱偉豪：後端API 的架構、權限控管、LINE Bot 和正式環境的部署，大多是我在顧。初評之後，我接著做了角色登入、站內通知和頭貼，修課授權與學生名單管理，還有LINE 的多輪追問與跨課程隔離。學生試用版的後端規格書和驗收，由我主導。系統手冊第5～11 章的改寫和UML 重繪，也是我負責的。

準備學生試用的那段時間，我腦中一直繞著同一個問題：怎麼保證學生只看得到自己修的課？規格書從草案一路改到v1.2，中間跟組員來回討論，最後依團隊的八項決議定案。實作時我守著一條很簡單的原則：只要條件不明確，就先拒絕，也就是所謂的fail-closed。寫完之後，再用固定題庫和驗收紀錄一項一項對。這樣做很花時間，但我覺得對要交給學生用的系統來說，慢一點反而比較安心。9 月21 日開放試用時，兩門課、27 位學生的修課指派都是照這套規則建立的。

部署時也踩過一個很典型的坑。某個功能在本機跑得好好的，一上正式環境就出錯，查了半天才發現 .env 根本不會跟著程式碼一起部署，YouTube 憑證只躺在我的電腦裡。從那次之後，我判斷正式環境的狀態一律看 /health 和管理員的系統服務頁，不再相信設定範本上寫了什麼。

技術上，我學會用GitHub Actions 把部署自動化，也摸熟了VM 上的Nginx、PM2 和SELinux。不過收穫最大的，可能是診斷問答檢索時養成的習慣：每一輪實驗都先寫下假設，跑完再記結果。有了這份紀錄，跟組員或教授討論時，我手上有東西可以攤開來講，不必只靠「感覺應該是這樣」。

整理第10 章時，我對「測過」這兩個字也變得比較謹慎。30 個測試個案裡，有21 項目前只從程式層面確認了邏輯，另外9 項，像是忘記密碼、LINE 綁定、影片上傳和手機操作，都還沒實際操作過。自動化測試全數通過，只能說明程式照我們寫的方式在跑，不代表使用者真的用得順。所以這份表格我刻意把兩種狀態分開標，寧可看起來不夠漂亮，也不想讓它看起來比實際更完整。

往後看，最急的是把第10 章剩下的人工測試補齊。LINE Webhook 目前還是走ngrok 通道，我想跟指導教授討論，改走正式網域是不是更穩。另外，後端的request／response 格式和OpenAPI 文件是否一致，現在還沒有自動化測試把關，這塊可以補上契約測試。

張庭語：我負責的主要在AI Pipeline：抽音訊、用Whisper 轉文字、把逐字稿切段，再交給Gemini 做Embedding。初評之後，工作範圍往外擴了不少，包括Pipeline的工作追蹤與斷點續跑、Chunk 策略與STT 準確度優化、Parent Embedding 與階層式檢索、多影片批次上傳、網頁版的多輪對話問答、FAQ 快取，以及正式環境的檢索診斷。AI 問答與LINE Bot 的流程測試、會議紀錄和競賽企劃書的整理，也由我負責。

長影片是最磨人的。一支一兩個小時的影片跑到一半出錯，以前只能整支重來，眼看著進度條歸零，心裡實在很難平靜。後來我加了checkpoint 和resume 機制，讓Pipeline 可以從斷掉的地方接著跑，這個問題才算解決。

切段則是另一個麻煩。固定長度的切法常常把一個完整的概念從中間劈開，學生問的剛好是那個概念，系統卻只撈得到前半段。為了這個，我做了兩層的Parent／Leaf結構：Parent 先找出大概在講哪一塊，Leaf 再提供精確的逐字稿和時間戳。萬一Parent那層出狀況，系統會自動退回Leaf 檢索，至少不會讓新機制把原本能用的問答拖下水。

做下來我慢慢體會到，這條流程裡幾乎每一步都是取捨。切得越細，找得越準，可是片段數、儲存空間和API 費用也跟著往上堆。而且這些改動都會牽動後端，所以我們後來習慣先把Data Contract 寫清楚再動工。這個做法看起來多繞了一步，實際上省下的溝通成本，比花掉的時間多得多。

多輪對話也讓我學到，「程式能跑」和「對話接得上」是兩回事。我寫了一組穩定性測試，專門檢查追問時上下文有沒有接好，但第10 章裡「最近對話、新對話與追問」這一項，目前還沒完成人工實測。像「它」、「剛才講的那個」這種代名詞，機器測試很難判斷回答到底對不對，最後還是得靠人一題一題看。

如果還有時間，我很想把影像內容真正接進問答。音訊和畫面的向量目前只是預留，問答用的還是逐字稿，可是很多老師的重點其實寫在投影片或黑板上，光靠語音是抓不到的。另外，那份50 題的題庫目前只跑過兩輪，我希望它能變成固定的例行檢查，每次調整切段策略，都拿同一份題目重跑，才知道到底有沒有變好。

張家瑜：使用者打開FocusFlow 看到的畫面，大部分出自我手上。初評後，我陸續做了學生教學短片牆、Topbar 的通知與使用者選單、個人資料頁、全站的RWD 響應式排版、管理員專用的登入入口、教師短影片審核頁，還有問題回報與意見回饋的入口。學生試用期間的回饋收集由我負責。另外，我也整理了Logo 的SVG 版本和網站Favicon，寫了教師數位分身短影音的腳本範例和模板，簡報和系統手冊第4、12、13 章也是我負責的。說起來，我花最多心力的，其實是專題前期的UI/UX 設計。那時系統還只是一張架構圖，最後會長什麼樣子，誰也說不準。Logo、配色、首頁、登入頁，到學生、教師、管理員三種角色各自的Dashboard，我都跟組員來回討論、修改。我不希望它看起來像一套冷冰冰的校務系統，所以加了3D 的元素，包含按鈕和動態背景，希望學生點進來的第一眼，會覺得這是一個願意多停留一下的地方，而不是又一個得交作業的平台。可是設計做得越久，我越發現好看和好用常常在互相拉扯：動畫一多，手機就開始卡；資訊塞得太滿，學生反而找不到提問的按鈕。每次卡在這種取捨裡，我都會回頭問自己：使用者打開這一頁，最想先做的到底是什麼？

手機版排版則是一場消耗戰。側邊導覽列和課程列表的按鈕，在小螢幕上老是擠出邊界。我把導覽改成橫排，重新安排按鈕換行的方式，連通知選單的位置也挪了，就這樣一頁一頁修。管理員入口原本它跟一般使用者共用同一個登入頁，學生很可能誤點進去，所以我另外做了 /admin 專用登入頁，也把後端回傳的「角色不符」錯誤，改寫成使用者看得懂的提示。

回頭看，我在前端上最大的進步，大概是學會把畫面拆成能重複使用的元件。像短影片審核頁的步驟指示，同一個元件在桌面版和手機版會長成不同的樣子。跟後端分頭開發時，我通常先用假資料把畫面和流程做出來，等API 格式確定了再接上去，兩邊就能同時往前走，不用互相等。

## 13-2 團隊反思

四個月前，FocusFlow 還只是一個能在本機展示的MVP。到了2026 年9 月21日，系統已經部署在學校的虛擬機上，兩門課、27位學生可以從 https://focusflow.ntub.edu.tw 進來試用。第1 章預期的主要流程，包括登入與課程列表、教師上傳影片與處理、有找到依據時附上可跳轉時間戳的AI 問答、LINE 綁定與提問，也都已經做出來了。回頭看這段路，我們覺得最大的改變，是慢慢學會拿證據說話：問答品質好不好，拿50 題的固定題庫來評分；功能能不能用，看正式環境的健康檢查；需求要改，先寫進規格書、經過團隊決議，再動手寫程式。

話說回來，「做出來」和「驗收完成」之間還有一段距離。第10 章的30 個測試個案，多數目前只確認了程式邏輯，問答、LINE、影片上傳、短影片流程和手機操作等9 項，也還沒完成人工實測。我們選擇把這些狀態如實寫出來，而不是一律標成「通過」。這是試用期接下來最主要的工作。

當然，也有不少地方做得不夠好。四個人的工作節奏本來就不同，提交紀錄大量擠在8、9 月，如果前期的分工追蹤能更即時，後面應該不會那麼趕。文件也是，平常沒有跟著程式碼一起更新，送件前一次補齊，累的是自己。還有一點我們感觸特別深：AI 工具給的建議常常聽起來很有道理，可是適不適合FocusFlow，最後還是得由我們自己回頭對照需求來判斷。

接下來，我們會先把第10 章剩下的人工測試補齊，一邊收集學生試用的回饋，一邊為校內觀摩展和校外競賽做準備。這個系統還稱不上完成，不過已經有真正的學生在用它，對我們來說，這比任何一次展示都更有分量。
