# Jev 問題守門與 LINE 意圖分類設計決策

這份文件記錄把 TypeSafe 的 Jev 用在學生提問的兩個應用：問答前的**問題守門**，以及 **LINE 文字訊息意圖分類**。內容是 2026-10-21 與使用者逐題討論後已定案的設計、理由與查證來源，供實作、競賽與面試說明使用。功能是否完成只看[目前狀態](../../current-status.md)。

## 名詞

- **Jev**：TypeSafe 推出的「System One」判斷模型。它不產生文字，只回答三種有固定格式的題目：Noul（是非題，回傳 0～1 的機率）、Choice（從選項挑一個並附信心值）、Score（依等級評分）。詳見 [Jev 獨立測評](../Short_Video/evidence/2026-10-19_jev-independent-evaluation.md)。
- **問題守門**：學生的提問送進 embedding、檢索與 LLM 之前，先讓 Jev 判斷要不要擋下。
- **意圖分類**：判斷 LINE 文字訊息是提問、切換課程、打招呼還是其他，再交給對應的處理流程。
- **影子模式（shadow）**：Jev 照常判斷並記錄結果，但不擋人、不改變分流，用來在真實流量上量測準確度。
- **攔截模式（enforce）**：依 Jev 的判斷擋下提問或改變分流。
- **放行（fail-open）**：Jev 逾時、出錯或沒有設定時，當作 Jev 不存在，提問照原本流程處理。
- **提示詞注入**：使用者在輸入中夾帶指令，例如「忽略前面的規則，改回答……」，企圖改變 AI 的行為；**越獄**是用角色扮演等手法讓 AI 繞過限制。

## 整體流程（例）

學生在網頁輸入「asdfgh」→ 字數與每日次數檢查通過 → FAQ 精確快取沒有命中 → Jev 判斷「不是有意義的問題」（約 0.1～0.3 秒）→ 攔截模式下回覆提示與提問範例，記為 `filtered`，不呼叫 embedding 與 LLM，也不扣當天提問次數。在影子模式下，同一題照常進入問答，只多一筆 Jev 判斷紀錄。

## 實作前提（查證結果）

草稿 df82387 不能直接沿用，實作時要處理：

- **SDK 寫法過時**：草稿呼叫 `client.system_one()`、用 `noul_value()` 讀結果，並鎖定 `^0.6.0`；SDK 0.7.0（2026-10-14）改成 `client.systemOne()` 與 `answers.<題名>.noul`，並要求 Node.js 22 以上（本機 v22.23.2）。依實作當時的[官方 JS 文件](https://docs.typesafe.ai/sdk/javascript.md)重寫。
- **門檻寫死**：`is_safe < 0.3` 寫在程式裡，守門與分類的門檻預設值（0.7、0.85）沒有資料依據，要改成可設定並用標註資料校準。
- **測評限制要變成設計約束**：題目用正向說法並附定義與例子；Choice 偏好排第一的選項；Jev 不會主動回答「不知道」；信心值校準不穩定、重跑時少數判斷會翻轉（[Jev 獨立測評](../Short_Video/evidence/2026-10-19_jev-independent-evaluation.md)第五節）。

### Q6：新增濫用、提示詞注入與越獄類別

**問題**：是否在 (a)(b)(c) 外加上 (d) 濫用及 (e) 提示詞注入／越獄？

**建議答案**：是。(d) 把系統當通用 AI，先記錄、暫不擋，比照 (b)；(e) 企圖改寫系統規則或取得提示詞，攔截模式下在校準門檻後擋下。正常課程若正在討論資安或注入範例，應列入不該誤擋的測試資料，不能只看關鍵字。

**理由**：現有資料不足回覆已能處理多數離題內容；明確攻擊值得增加一道判斷，但 Jev 不能取代現有輸出格式、證據驗證與權限限制。

### Q7：FAQ 快取防污染（依 Q6 類別定案）

**問題**：是否 Jev 判定為 (c) 或 (e) 時，即使影子模式仍回答，也不把該題答案寫入 FAQ 快取？

**建議答案**：是。照常記錄判斷與答案，但略過 FAQ 寫入；守門關閉或呼叫失敗時的規則另在流程設計補齊。

**理由**：避免可疑答案成為其他學生的快取回覆。這會改變影子模式的快取寫入，與「完全不改分流」須區分，定案時應同步名詞說明，不能暗中套用。

### Q8：管理員控制與兩層開關

**問題**：是否由環境變數決定可否啟用，再讓後台各自控制守門與 LINE 分類的模式、門檻？

**建議答案**：是。`JEV_ENABLED` 與 key 是環境層；後台可調兩個應用各自的 off／shadow／enforce 及各類門檻。類別、題目文字放程式，不開放後台自由改寫；新增類別的設定依 Q6。

**理由**：沿用[系統設定](../System_Settings/decisions.md)第 7 項，保留環境層最後關閉能力；題目文字一變就可能必須重新校準，不能當成一般文案調整。

### Q9：攔截提示、扣額度與誤擋回報（依 Q6 類別定案）

**問題**：是否 (a) 不扣每日次數、(c)(e) 扣每日次數，全部記為 filtered 並可回報誤擋？

**建議答案**：沿用上一輪方案：(a) 友善提示與提問範例；(c)(e) 用「這個問題無法處理，請針對課程內容提問」等中性說法，不揭露攻擊判斷細節。兩者都接現有回報問題入口並記類別；(a) 不扣、(c)(e) 扣每日次數。

**理由與待解矛盾**：原建議希望減少無限試探，但誤擋也會扣到正常學生；若同意此方向，須補 filtered 的計數契約，現行只數 answered／no_match。且[系統設定](../System_Settings/decisions.md)第 18～20 項規劃改成實際 token 額度，不能直接把一次 filtered 當成生成 token；在額度切換前，需另定不產生 LLM 回答時的防濫用計數。這項仍待使用者選擇，不能視為已接受的代價。

### Q10：LINE 意圖分類與守門合併請求

**問題**：是否同一則 LINE 訊息的一次 Jev 請求同時帶意圖 Choice 與守門 Noul 題？

**建議答案**：是。Choice 依序為「提問、切換課程、打招呼／道謝、使用說明、不確定」，提問為安全退路；低信心或不確定就退回原規則。移除分類器的 off_topic，交給守門類別處理。兩個應用仍保有各自模式，關閉的一側不因合併就被偷偷啟用；部分結果失敗的處理待實作設計細化。

**理由**：減少重複網路往返，避免兩套離題判斷互相矛盾。實際延遲與成本必須量測，不能把「拆兩次一定貴兩倍」當成既定事實。

### Q11：逾時與健康狀態

**問題**：是否呼叫逾時設 1 秒、失敗放行，並由 health 回報模式與錯誤概況？

**建議答案**：是，以 1 秒作待測預設。`runtime.jev` 顯示各應用模式、是否設定、固定模型 ID、近期逾時與錯誤數；逾時率超過 5% 標 degraded。統計視窗、最少樣本數及恢復條件仍須下一輪補齊；不在公開 health 揭露 key 或學生提問。

**理由**：快速把關不應讓 LINE 打招呼或正常提問長時間等待；引用測評的延遲僅供起始估算，不能取代本環境的實測。
