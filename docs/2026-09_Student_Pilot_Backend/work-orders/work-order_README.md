# 施工單目錄說明

本目錄存放學生試用版後端的施工單。施工單負責把已定版規格轉換成可執行的工作項，不取代規格書，也不得擴張需求。

## 施工單何時建立

施工單應在規格書完成定版後、開始修改程式前建立或校正。若規格仍有未決事項，施工單只能標記為草案，不得作為開工依據。

正確順序：

```text
規格書定版
→ 施工單逐項對齊規格
→ 衝突與缺口完成決議
→ 施工單核准
→ 開始實作
```

## 每份施工單至少包含

1. 對應的規格書版本、日期與範圍。
2. 明確納入與排除的工作。
3. 工作項編號、依賴關係與固定執行順序。
4. 預計修改的程式位置。
5. 每個工作項的驗收條件與測試。
6. 批次之間的停止點與核准條件。
7. 禁止事項、資料寫入邊界與 feature flag 限制。
8. 已知衝突、阻塞條件與需要決策的人員。

## 文件責任邊界

| 文件 | 回答的問題 |
|------|------------|
| [規格書](../2026-09_Student_Pilot_Backend_Spec.md) | 要做什麼、為什麼、完成標準是什麼 |
| 施工單 | 如何拆解、依什麼順序施工、修改哪裡、如何測試 |
| [驗收證據](../evidence/evidence_README.md) | 實際執行後，如何證明符合驗收條件 |

## 衝突處理

本任務固定採用：

```text
規格書 > 施工單 > 現有程式碼 > 實作者推論
```

發現衝突時應列出文件或程式位置、具體差異與影響，停止該工作項並等待決議。不得以較容易實作、現有測試會通過或個人認為較合理為由自行選擇。

## 命名建議

```text
YYYY-MM-DD_<規格版本>-work-order.md
```

同一規格若需要修訂，優先在既有施工單中保留版本與變更紀錄，避免建立內容重複但責任不明的多份施工單。
