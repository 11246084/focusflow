# 對話功能優化設計決策

這份文件記錄學生網頁版對話功能（看影片時向 AI 提問的那一欄）的優化討論：現況、和市面產品的差距、可參考的開源專案，以及要逐題定案的問題。它讓接手的人或 AI 不用重讀對話就能接續；目前第一輪題目還沒回答，請 Weihao 逐題回覆。功能是否完成只看[目前狀態](../../current-status.md)。

範圍只含網頁版的對話欄，不含 LINE 對話、檢索方法（見[多模態檢索](../Multimodal_Retrieval/decisions.md)）與播放器章節（見[學生端播放介面](../Student_Player_UX/decisions.md)）。

## 名詞

- **串流輸出**：回答邊產生邊顯示，不是等整段寫完才一次出現。
- **追問**：依賴前文才看得懂的問題，例如上一題問「什麼是監督式學習」，下一題問「那它的缺點呢」。
- **追問改寫**：檢索前先把追問補成完整的問題，例如把「那它的缺點呢」改成「監督式學習的缺點是什麼」。
- **FAQ 快取**：相似的問題已經答過時，直接回傳之前的回答，不再呼叫模型。

## 現況（2026-11-15 查證，`dev` b55f8e6）

學生送出問題 → 前端呼叫 `POST /conversations/:id/messages` → 後端改寫追問、檢索、產生回答 → 整段回答與來源一次回傳 → 前端顯示回答與可點擊的來源片段。

| 項目 | 現況 | 位置 |
|---|---|---|
| 多輪對話、歷史清單、新對話 | 有；按課程分開，第一句問題自動當標題 | [對話服務](../../../backend/src/services/conversation.service.js) |
| 回答附來源、點擊跳到影片秒數 | 有；標示文字、聲音、畫面 | [學生課程頁](../../../frontend/focus-flow/src/pages/StudentCourses.jsx) 的 `QAPanel` |

## 和市面產品的差距

比較對象是通用聊天產品（ChatGPT、Gemini、Claude）與資料或影片問答產品（NotebookLM、Perplexity、YouTube 影片問答、Coursera Coach）。這部分依 Claude 既有的了解整理，沒有逐一查證各產品的最新版本；要引用到報告或系統手冊前須先查證。

依對使用感受的影響排序：

1. 沒有串流輸出。
2. 追問改寫靠規則，沒涵蓋的說法（例如「再講詳細一點」「舉個例子」）會被當成獨立問題去檢索。
3. 系統不知道學生正在看哪支影片的哪一秒，答不出「剛剛這段在講什麼」。
4. 回答的操作少：不能複製、評分、對成功的回答重新產生、編輯問題或中止。
5. 沒有範例問題與建議追問。
6. 輸入框不能換行。
7. 對話不能改名、刪除、搜尋。
8. 回答不支援表格、程式碼區塊與公式。

「點來源直接跳到影片那一秒」是通用聊天產品沒有的，屬於本系統的特色，優化時保留。

| 專案 | 授權 | 可參考的部分 | 查證方式 |
|---|---|---|---|
| [LibreChat](https://github.com/danny-avila/LibreChat) | MIT | 後端 Express 加 Mongoose、前端 React，和本專案最接近；串流、編輯後重送、對話搜尋 | 讀 GitHub 頁面與 `api/package.json`；還沒讀原始碼 |
| [Vercel AI SDK](https://github.com/vercel/ai) | 未確認 | 官方的 Express 串流範例（`streamText` 加 `pipeUIMessageStreamToResponse`），前端用 `useChat` 接收 | 讀 GitHub 上的範例文件；官方網站在查詢環境連不上 |
| [assistant-ui](https://github.com/assistant-ui/assistant-ui) | MIT | 聊天介面的 React 元件庫；操作列（複製、重新產生、編輯）的互動設計 | 讀 GitHub 頁面 |
| [Vane](https://github.com/ItzCrazyKns/Perplexica)（原名 Perplexica） | MIT | 回答附引用；舊版有獨立的 API 把對話紀錄交給模型產生建議問題 | 建議問題的做法只在第三方保存的舊版程式看到，現行版本未確認 |
| Streamdown | 可能是 Apache-2.0 | 串流途中還沒寫完的 Markdown 怎麼顯示 | 只有第三方頁面的說法 |

不建議參考：Open WebUI（前端 Svelte、後端 Python，且 v0.6.6 起授權加了不得移除品牌標示的條款）；影片問答類只找到個人小專案，沒有成熟的對照對象。Onyx、RAGFlow、Dify 這次沒有查到足夠資料。

LibreChat 的限制：規模大，用 TypeScript 與 Express 5（本專案是 Express 4、純 JavaScript），適合看做法、不適合整段搬；它的「斷線後接續回答」依賴 Redis，本專案沒有。它沒有「先檢索再回答」的流程，所以帶播放位置、追問改寫與建議追問都沒有可對照的做法。

## 目前這一輪待答題目

第一輪只問不需等其他答案的題目。各項的細部設計（串流的傳輸格式、播放位置怎麼影響檢索、評分資料怎麼用）依本輪答案在下一輪提出。

### Q1：優化的目的與成功標準

**問題**：目的是否定為「讓學生願意在看影片時持續提問，而且追問得到的回答對得上前文」，展示效果為次要？

**建議答案**：是。成功標準訂兩條：①送出問題後 2 秒內畫面開始出現回答文字（FAQ 快取命中時整段直接出現）；②一組固定的追問題目（例如「再講詳細一點」「舉個例子」「剛剛這段在講什麼」）都能得到和前文或目前播放位置相關的回答。

**理由**：目的決定順序。如果以展示為主，串流的觀感最重要；如果以學生實際使用為主，追問與播放位置同樣重要。兩條標準分別對應等待體驗與回答對不對得上，都可以實際測量。

### Q2：這一批要做哪些項目

**問題**：是否採「前端三項（複製、多行輸入、範例問題）＋帶播放位置簡單版＋串流輸出」為這一批的範圍，其他項目列為之後？

**建議答案**：是。之後再評估的有：用模型改寫追問、建議追問、讚／倒讚、對話改名與刪除、成功的回答重新產生、編輯問題、表格與程式碼排版、對話搜尋。

**理由**：前端三項成本最低；帶播放位置是影片問答特有、通用聊天產品做不到的；串流對每一次提問的感受都有影響。用模型的兩項會增加每題費用，在花費上限解決、看得到實際用量之前不適合決定。

### Q3：實作順序

**問題**：順序是否為「①前端三項 → ②帶播放位置 → ③串流」？

**建議答案**：是，三步各自獨立提交與驗收。

**理由**：前兩步不改回應格式，風險低，可以先上線讓學生用到。串流要動回應格式、FAQ 快取命中路徑與 nginx 設定，放最後並單獨測試；它出問題時不會拖住前兩步。

### Q4：串流的做法是否以 LibreChat 為主要參考

**問題**：串流是否先讀 LibreChat 的原始碼，整理它的做法與本專案的對照，再提出設計？不引入 Vercel AI SDK？

**建議答案**：是。凍結期間由 Claude 唯讀研究 LibreChat 的串流、中止與訊息儲存時機，結果寫成本資料夾的研究紀錄，下一輪再依紀錄提出本專案的串流設計。暫不引入 AI SDK。

**理由**：LibreChat 的架構和本專案最接近，做法可以直接對照。本專案的回答產生已經自己呼叫 Gemini，引入 AI SDK 等於換掉這一層，影響範圍比加串流本身還大。研究只讀外部程式、不改本專案，符合凍結期間的限制。

### Q5：重新產生要不要算一次提問額度

**問題**：之後若開放「成功的回答也能重新產生」，每次重新產生是否扣一次每日提問額度？

**建議答案**：扣。失敗的回答重試維持現況不變。

**理由**：重新產生會再呼叫一次模型，費用和新問題相同；不扣的話學生可以用它繞過每日 5 次的限制。這題先定案，是因為它會影響 Q2 把「成功的回答重新產生」排在這一批還是之後。
