# Diagram brief

> 製圖前的最小契約。目的是先固定「讀者要看懂什麼」，再決定圖種與細節；不是額外的交付章節。

## 使用規則

- `[OOAD:MUST]` 先寫一句可回答的設計問題，再選圖。
- `[DOC:SHOULD]` 一張圖只回答一個主要問題。兩個獨立觸發、兩個生命週期或兩種架構視角應拆圖。
- `[DOC:MUST]` 每個元素與關係都要有目前證據，或明確標為 `partial`／`planned`。
- `[FF:MUST]` 新增或重繪時，建立檔案前先決定 `vX-x`；不得完成後才補猜版本。
- `[DOC:HEURISTIC]` 元素數與版面上限只用來提醒拆圖，不得單獨否決官方指定圖。

## 可複製模板

```text
讀者／用途：
主要問題：（一句話）
OOAD 階段／章節：
候選圖種／選擇理由：
範圍內：
範圍外：
主情境或核心結構：
必要替代／錯誤情境：
候選元素與證據：
  - 元素／關係 → source 路徑或規格 → implemented 狀態
realizes：
verified：
版面預算：（約略的 participant／class／package 數，只作拆圖提示）
輸出：圖號、顯示名稱、vX-x、圖源格式（.puml／.mmd）、renderer、匯出格式、正文／圖目錄位置
未決事項：
```

## 完成條件

brief 可讓另一位審查者不看對話也能回答：

1. 為何是這個圖種，而不是相鄰圖種？
2. 圖的邊界與讀者是誰？
3. 哪些內容由目前實作支持，哪些只是規劃？
4. 為何需要一張圖，或為何必須拆成多張？
5. 這次建立的是哪個版本，將落到哪些 artifact？
