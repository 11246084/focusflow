## 討論內容

1. 營運計畫與效益分析

- 背景：本次參加競賽所使用的計畫書架構中，第五章要求撰寫營運計畫與效益分析。教授提醒這一章不能只做概略描述，需要以可查證的假設精算成本與可能收益。
- 內容：
  - 先設定合理的使用情境，例如每月使用人數、課程數量、影片處理量與提問次數，再估算每月消耗。
  - 成本需區分固定成本與變動成本，至少包含公有雲 VM、LLM API、Embedding API、儲存空間及網路流量。
  - 公有雲部分需比較 AWS、GCP、Azure 的 VM 規格與每月租用費用，再換算成一學期及一年的成本。
  - 模型目前使用 Gemini 等雲端大語言模型開發；若正式部署改用 Gemma 等本地開源模型，可減少長期 API 費用，但仍需計入主機硬體、維護與用電成本。
  - 教授已另外建立專題專用的 API 專案並提供新的 API。後續可直接查看該專案的獨立使用量，盤點每支影片及每次問答的 LLM、Embedding 消耗，提高成本估算準確度。
  - 收益除了可用訂閱費、授權費或維護服務費等方式預估，也可將系統替代助教回覆問題所節省的工時與薪資列為可量化效益。
  - 最後以每月成本、可能收益及節省的人力價值計算損益平衡點，作為計畫書第五章的數據依據。
- 結論傾向：先建立「每月使用假設 → 每月成本 → 可能收益與節省效益 → 損益平衡」的試算表，再延伸為每學期與每年度估算。

2. 人與 AI 協作及問答成本控制

- 背景：AI 能快速產生實作方案，但不會主動判斷額外成本是否值得。
- 內容：
  - 提升檢索候選數量可能改善回答品質，但也會增加 token 消耗，需由人決定品質提升是否值得成本。
  - 後端目前已有 FAQ 快取基礎，會議中的下一步是繼續完善及驗證，而不是從零建立。
  - 第一層處理字面相同的問題，直接回傳既有答案；第二層比對語意相近的問題，命中後也可沿用先前結果，避免重複執行完整檢索與 LLM 回答流程。
  - FAQ 與答案必須綁定課程，避免不同老師、不同年度或不同課程的答案混用。
  - 後續需記錄 FAQ 命中次數、減少的 API 呼叫、token 與回應時間，確認快取帶來的實際效益。
- 結論傾向：完善並驗證既有的課程級 FAQ 快取，同時評估成本、課程隔離與回答正確性。

3. AI Pipeline Phase 2 進度

- 背景：Phase 2 的主軸不是立刻增加更多 AI 模型，而是先將現有 Pipeline 升級成可管理、可恢復、可評估及可維護的流程，再逐步改善檢索與回答品質。
- 內容：
  - 前三項已完成：流程狀態管理、執行批次與輸出版本管理，以及中斷續跑與 checkpoint 恢復。Pipeline 已能記錄各階段狀態、保存每次 Run 的輸出，並從失敗階段繼續執行。
  - 下一項先強化 MongoDB 上傳，補上批次寫入、Upsert、重複資料防護、暫時性失敗重試及上傳結果摘要。
  - 接著進行影片內容分段優化。目前主要依固定字數、秒數或 Segment 數切分，完整概念可能剛好被切在兩個 Chunk 中間，造成搜尋只找到一半內容。
  - 分段優化將加入 Chunk Overlap 與 Sliding Window，讓相鄰區塊保留共同內容；並評估短、中、長三種 Hierarchical Chunk，分別支援精準問題、一般概念題與摘要題。
  - Chunk 重疊會增加分段數量，因此需同步記錄 Chunk、Embedding、儲存空間與 API 成本的增加比例。
  - 分段完成後再依序處理文字與影片混合檢索、成效評估、成本與額度監控，最後才進行檢索候選數量與 Reranker 實驗。
  - 原本將候選結果由 Top 5 擴至 Top 20 的做法先延後，之後比較 Top 5、Top 10、Top 15、Top 20 的命中率、回答品質、token、時間與成本，再決定最合適的方案。
- 結論傾向：依「MongoDB 上傳強化 → 影片分段優化 → 混合檢索 → 成效評估 → 成本監控 → 檢索與重新排序實驗 → 完整問答流程」的順序推進；不預設 Top 20 一定較好，而以評估數據決定。

4. Shorts 頁面與課程過濾

- 背景：家瑜依 Notion `Shorts開發0714` 的內容報告目前完成成果，並提出兩個後續需要思考的問題。
- 內容：
  - 問題一：系統要如何製作 Short，需再確認短片的生成方式與時機。
  - 問題二：Short 要如何依學生修課內容過濾，例如修讀 A 課程的學生不應看到 B 課程的 Short。
