# 第6章 設計模型

第5章以使用個案與活動圖說明「使用者要完成什麼」，本章屬物件設計（Object Design），說明 FocusFlow 以哪些參與者與設計類別完成這些使用個案：6-1 以循序圖（Sequence Diagram）呈現每個使用個案的訊息往返、權限檢查與例外分支；6-2 以設計類別圖（Design Class Diagram）說明分析責任如何落實為後端服務與資料物件，並以一張設計物件圖（Design Object Diagram）呈現一次網頁問答完成後的實例快照。後端依 routes → controllers → services → models 分層，本章只描述到「服務與資料物件」層級；完整欄位、索引與參照限制見第8章，程式檔案職責見第9章。

## 6-1 循序圖（Sequential diagram）

本節依規範「循序圖或通訊圖擇一」採用循序圖，與第5章 UC-01～UC-09 一一對應（表6-1-2）。一個使用個案若包含多個獨立觸發（例如「開啟影片」與「送出提問」），依觸發拆成子圖，子圖沿用同一使用個案的圖號並加上 a、b、c，共 21 張。每張圖的參與者統一抽象為使用者、前端、後端 API、資料庫與外部服務五類，責任如表6-1-1；後端內部的 service 分工不在循序圖展開，改由 6-2 的設計類別圖說明。

表6-1-1　循序圖參與者與責任

| 參與者 | 對應元件 | 在循序圖中的責任 |
| --- | --- | --- |
| 使用者（學生、教師、管理員） | 瀏覽器操作者或 LINE 使用者 | 觸發操作、提供輸入、閱讀結果與錯誤訊息 |

表6-1-3　圖6-1-1a 步驟對照

| 步驟 | 發生什麼 | 錯誤碼或結果 |
| --- | --- | --- |
| 1～2 | 學生填寫姓名、Email、密碼並送出 `POST /auth/register` | — |
| （灰框） | 後端驗證欄位格式、密碼至少 8 字，角色只允許 student | 不合規 → 400 `VALIDATION_ERROR` |

圖6-1-1b 登入與帳號鎖定循序圖

表6-1-4　圖6-1-1b 步驟對照

| 步驟 | 發生什麼 | 錯誤碼或結果 |
| --- | --- | --- |
| 1～2 | 使用者輸入 Email、密碼與角色，送出 `POST /auth/login` | — |
| （灰框） | 檢查角色參數，並查詢該 Email 是否在鎖定期間（後端記憶體計數） | — |
| 3～4 | 鎖定中：不查帳號、不比對密碼，直接拒絕 | 429 `TOO_MANY_LOGIN_ATTEMPTS` |
| 5～6 | 未鎖定：以 Email 查詢帳號與密碼雜湊 | — |
| 7～8 | 帳號不存在或密碼錯誤：失敗次數加一並回傳剩餘次數 | 401 `INVALID_CREDENTIALS`；本次達門檻 → 429 |
| 9～10 | 密碼正確但帳號停用或所選角色不符 | 403 `USER_INACTIVE`／`ROLE_MISMATCH`，不發 token |
| 11～13 | 寫入 login 使用紀錄，回傳 JWT，前端導向對應角色首頁 | 200 |

設計理由：鎖定檢查排在查詢帳號之前，鎖定期間即使密碼正確也不比對；帳號不存在與密碼錯誤走同一分支、回應相同，外界無法由錯誤訊息推知 Email 是否已註冊；角色比對放在密碼驗證之後，未通過驗證者無從得知帳號角色。JWT 只攜帶使用者 id，之後每次請求由後端重新確認帳號存在且啟用（見圖6-1-9a 步驟 3）。

![影片上傳與批次追蹤循序圖](../images/圖6-1-3a-影片上傳與批次追蹤循序圖-v1-0.png)

表6-1-7　圖6-1-3a 步驟對照

| 步驟 | 發生什麼 | 錯誤碼或結果 |
| --- | --- | --- |
| 1～3 | 教師一次選 1～10 支本機影片，以單一 multipart 請求上傳；後端確認可管理課程並建立 VideoBatch（creating） | 無管理權 → 403 `COURSE_MANAGE_DENIED`；超過 10 支 → 400 `VIDEO_BATCH_LIMIT_EXCEEDED` |
| 4 | （loop）同課程已有相同檔案或檔案不合規，該項標記後繼續下一檔 | duplicate／failed 與錯誤碼 |
| 5 | （loop）通過驗證者建立 Video 並掛入課程 | processing.status = queued |

設計理由：每處理完一個檔案就保存一次批次狀態，某一檔失敗不會回滾已成功的項目；批次狀態由各影片的處理狀態彙整而來，不另外維護一份可能互相矛盾的狀態。貼 YouTube 網址建立影片的 API 仍保留，但教師上傳頁不提供此入口，故未繪入。

設計理由：刪除影片前必須先清除 FAQ 快取，確保不會留下引用已刪除影片的快取答案；提問紀錄與使用紀錄屬歷史資料，不隨影片刪除。所有操作完成後都讀回實際資料，不以前端的樂觀更新代替結果。
